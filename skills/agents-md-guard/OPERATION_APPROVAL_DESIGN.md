# E: 操作対象と人間の承認を結合する設計案

状態: 非正典・未承認・未実装。A〜Dの修正と分離した提案。2026-10-05。

## 問題と目的

AGENTS.mdを読んだことと、特定の操作が承認されたことは別である。現行の読込ガードは前者を確認する。後者を読込マーカーやAI自身が生成する「承認済み」JSONで代用しない。共通契約はAGENTS.md §3・§6・§7を用い、AI固有の確認画面だけを共通の実行仲介へ接続する。

通常の作業ルート内の読取・依頼済みの編集・検証には、個別承認を追加しない。削除、履歴改変、公開・送信、ルート外書込、導入、認証・秘密情報操作は対象と影響を確定して扱う。利用者が具体的に依頼済みの操作では既存の承認を利用する。pushはfresh fetch後に確定した送信全体の最終承認を必須とする。

## 信頼境界

承認を発行するbrokerはAIの作業プロセスと別権限で動かし、利用者の確認UIに直接接続する。承認状態、署名鍵、監査記録はAIの書込可能なリポジトリ・一時ディレクトリ・設定領域へ置かない。単にルート外へ移すだけでは保護にならず、同じ利用者権限の任意shellから改変できる構成は不採用とする。ACLと実行主体を分けるか、実行環境の承認機構で同等の分離を実現する。

AIは要求を作れるが承認を発行できない。UIはAIの文章だけを信用せず、brokerが検査した具体的な対象を表示する。現在のホストの許可確認を接続できるかは各クライアントごとに検証する。接続できなければAIが会話の「はい」を勝手に署名に変換しない。利用者管理の独立した実行経路へ返す。

hookは要求・拒否・状態表示のadapterであり、唯一の強制境界にしない。任意shellやMCPから外部書込できる環境では、hookやgit pre-pushだけで迂回を防げない。実行仲介を通さないプロセスの書込・ネットワーク・認証能力をsandboxまたはOS権限で制限する必要がある。Docker導入だけで承認の正しさを保証しない。

## 要求の内容

共通要求にschema_version、request_id、session_id、repo_realpath、operation、AGENTS.mdハッシュ、対象と影響、期限を含める。パスは絶対パスと実体パスを記録し、リンク・junctionを解決する。秘密値、トークン入りURLを確認画面やログへ出さない。

| 操作 | 承認に結合する対象 |
|---|---|
| ファイル削除・移動・上書き | 実体パス、対象一覧、再帰範囲、変更前内容のハッシュ、予定差分・上書き先、復元可能性 |
| ルート外書込 | 上記と書込先絶対パス、目的、ルート外である表示 |
| インストール | 名前・版・取得元、導入先、実行するinstallerと引数、権限、付随するスクリプトの影響 |
| 外部書込・MCP・送信 | サービス、アカウント、リソースID、宛先、本文・差分ハッシュ、公開範囲 |
| 認証・秘密情報操作 | 設定先、操作種別、露出先、必要な権限。秘密値自体は記録しない |
| Git push | 下記の送信manifest全体 |

Git push用manifestはremote名だけでなく実際のpush URL、送信先ref、ローカルref、HEAD OID、送信元OID、fresh fetchで取得した送信先OID、fetch時刻、incoming/outgoing全OID、全ref更新を含む。Gitは複数push URL・refspec・push.followTags等で送信範囲が変わるため、初期版は単一送信先・単一branch refspecを明示して固定する。それ以外は黙って追加送信せず別要求とする。

incomingあり、対象外commitあり、non-fast-forward、削除ref、新規非branch ref、force、--no-verify、hooksPath回避は通常AI push経路で拒否する。必要な履歴改変は対象OIDと影響を示して利用者管理の別経路へ返す。stage/commitの範囲確認をpush承認で代用しない。

## 実行の順序

1. brokerが実状態からmanifestを構成する。pushは対象remoteのfresh fetchに成功してから構成する。
2. 利用者UIがexact targetと影響を表示する。承認は要求IDとmanifestハッシュへ結合する。
3. brokerが期限付き・一回限りの承認を保護領域へ保存する。AIの自己申告、リポジトリ内ファイル、単純な会話文字列は承認の証拠にしない。
4. 実行直前に対象とmanifestを再検査する。HEAD、差分、remote URL/ref/OID、送信commit集合、対象パス・リンクの変化、期限切れは承認を失効させる。
5. brokerが競合実行を排除して承認を原子的に消費し、固定した引数で操作する。失敗しても自動再利用せず、実状態を再確認する。
6. 実行結果と前後状態を監査記録へ残す。push成功は送信先の反映OIDを確認する。利用者確認から実行までにサーバーが変化し得るため、クライアントの再確認だけで完全な競合防止を保証せず、サーバーの保護と通常fast-forward制約も用いる。

## 受入条件

- AIが作った承認ファイルや読込マーカーでは危険操作を許可できない。
- 承認した具体的対象が変わると実行を拒否し、再確認に戻る。
- 通常の依頼済みの編集・検証に不要な確認を追加しない。
- 生のshell、別名、スクリプト、MCP、Git以外のAPI経路を評価し、仲介外の能力が残る場合は未解消と報告する。
- 人間確認の実ログ、拒否、成功、失効、再利用拒否を実ホストで確認してから「操作承認を強制」と評価する。
