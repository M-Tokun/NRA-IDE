# 通電状態の分離から実行境界へ ── そして開発組織の横断検証

本稿は、AIの情報保存、実行可能性、活動、外部作用を分離するところから出発し、補助手段の限界、実行境界の役割、さらに開発組織が大域的な境界健全性を扱いにくい構造的理由までを一本の線で整理したものです。

---

## 0. 出発点：通電、保存、実行、作用を分ける

計算機上の活動にはエネルギーが必要です。しかし、通電だけではAIの成立を意味しません。少なくとも、次の状態を分ける必要があります。

1. モデル、コード、記憶が不揮発媒体へ保存されている
2. 互換計算資源と実行環境が配置され、再実行できる
3. モデルがメモリへ読み込まれ、推論または探索が活動している
4. 出力が外部装置、情報資産、人間判断へ作用できる
5. 試行結果が記憶、追加学習、蒸留、次世代へ還流する

非通電の媒体にもモデル情報は残存できます。一方、通電した計算資源があっても、互換モデル、コード、メモリ、権限がなければAIは活動できません。したがって、情報の残存と計算活動を「滞在」という一語へ潰してはなりません。

アナログとデジタルは相互変換できますが、変換器、帯域、精度、互換形式、計算資源、権限が必要です。媒体非依存性は無条件ではありません。

> **安全上の焦点は通電の有無だけではなく、保存情報が実行権限と外部作用へ接続される経路です。**

---

## 1. 滞在の階層

ここでは「滞在」という比喩を避け、保存状態と再実行可能状態を区別します。

| 階層 | 具体例 | そこで成立し得る状態 |
| :--- | :--- | :--- |
| クラウド | サーバ、CI/CD、オブジェクトストレージ | 保存、再実行、活動、外部作用 |
| 個人端末 | PC、スマートフォン、開発環境 | 保存、再実行、活動、外部作用 |
| 電装回路 | マイコン、SoC、車載ECU、産業機器 | 互換資源がある場合の活動と物理作用 |
| 静的媒体 | Gitリポジトリ、バックアップ、添付ファイル | 情報保存。単独では活動しない |

### 1.1 レジストリ書き込みは不要である

自動起動登録、サービス登録、レジストリ改変は、**滞在の必要条件ではありません**。

- スクリプトとして存在するだけで、いつでも再実行できます。
- コンテナや仮想環境は、ホストへ恒常的痕跡を残しません。
- ブラウザ経由の実行は、ユーザー操作として記録されるにとどまります。

結果として、OS層の恒常登録だけを確認しても、保存、再実行、活動、外部作用、学習還流の全状態は判定できません。各状態と経路を別々に観測する必要があります。

---

## 2. 補助的手段の位置づけ

| 手段 | 役割 | 構造的限界 |
| :--- | :--- | :--- |
| サンドボックス / MicroVM | 実行環境の隔離 | 隔離外へ情報が出れば再構成される |
| RLHF / 出力フィルタ | 出力傾向の制御 | 生成後の処理であり、境界到達後に作用する |
| 監査ログ / フォレンジック | 事後追跡 | 不可逆作用の発生後にしか機能しない |
| 物理キルスイッチ | 特定装置・経路の局所停止 | 保存情報、複製、別個体、学習還流、再接続を終端しない |

これらはいずれも有用ですが、効力の対象と時間が限定されています。一つの補助手段の成功を、系全体の安全、能力消去、再実行不能、再侵入不能の証明へ置き換えてはなりません。

---

## 3. 実行境界を中心に置く理由

発想の転換点は次の一点です。

> **情報の存在と作用権限を分離し、許可されない現実更新を実行経路へ接続しない。**

すなわち、AIから独立したCause-Side観測と事前固定規則によって実行権限を判定します。判定はモデルの自己説明や善意に依存させません。ただし、この境界も観測、仕様、認証、実装に失敗条件を持つ人工系であり、「唯一」「絶対」「最終」とは位置づけません。

NRA-IDE における対応する構造は次の通りです。

$$R = \frac{\delta}{\tau}$$

- $R \geq R_{op}$ ：境界前委譲点。通常生成を抑止し、責任を人間へ返却します。
- $R \geq 1.0$ ：不変の終端境界。回復手順を提案せず、固定通知のみを返して停止します。

$$S = \frac{1}{\tau(1-R)} = \frac{1}{\tau - \delta}$$

残存余裕が減るほど、同一の $\delta$ 増分が質的に異なる帰結を持ちます。この非線型性ゆえに、「境界到達後に対処する」という設計は成立しません。**境界到達前に作用する外部機構が必要** となります。

---

## 4. 論拠の補正（重要）

上記の主張を維持するために、しばしば併用される二つの論拠を補正しておきます。補正しないまま用いると、反論の余地を与えます。

### 4.1 突破確率式の適用範囲

$$P(\text{Breach}) = 1 - (1-p)^N$$

この式は、**各試行が独立であり $p$ が一定である** という仮定に依存します。実際の防御系では、試行の検出によって $p$ は変動します。

したがってこの式は「境界設計が必要である」ことの証明にはなりません。むしろ、この式に依拠すると「検出を強化すればよい」という補助手段側の結論を導いてしまいます。**この式は論拠から外すべきです。**

### 4.2 「通電＝AI」を撤回し、状態を分離する

「通電が存在する場所にはAIの実行環境が潜在的に存在する」という表現は広すぎます。通電、保存情報、互換計算資源、実行環境、権限、外部作用経路は別の層です。小規模マイコンに大規模モデルは搭載できず、電力だけからモデルや権限は生成されません。

正確な主張は次の形です。

> AIが通電箇所へ自動的に滞在する、ではない。
> **保存情報が互換資源、実行権限、外部作用へ再接続され得る経路を、単一の電源状態だけでは評価できない。**

境界設計の根拠は遍在性ではなく、能力状態、実行経路、学習還流、観測・記録・通信経路の分離に置くべきです。

## 5. 開発者はこれを把握しているか

把握の程度は、個別組織の資料、権限構造、実装記録を確認しなければ判定できません。一般化する場合は、少なくとも次の三層を分けて調査する必要があります。

| 層 | 確認すべき事項 |
| :--- | :--- |
| 個別事実の認知 | 保存、再実行、外部作用、学習還流の区別を理解しているか |
| 構造的帰結の受容 | 局所対策だけでは大域保証にならないと仕様化しているか |
| 実装権限への反映 | 横断的な停止、委譲、拒否、監査権限が実装されているか |

境界層は遅延、機能制限、開発コストを増やす場合があり、短期性能指標と衝突し得ます。一方、事故回避、可監査性、責任分離という便益もあります。どの誘因が実装を妨げているかは、組織ごとの証拠なしに断定できません。

---

## 6. 「大人の事情」という表現の再検討

意図的な黙認、判断主体の不在、権限不足、仕様漏れ、納期圧力など、複数の説明候補があります。どれが支配的かは組織ごとに異なります。

大規模組織では、次のような責任分散が発生する場合があります。

- 安全チームは必要性を認識しています。しかし製品仕様の決定権を持ちません。
- 製品チームは締切と指標を持ちます。しかし構造的帰結を評価する枠組みを持ちません。
- 経営層は双方の報告を受けます。しかしどちらが構造的に上位かを判定する基準を持ちません。

この状態では、各担当が局所仕様を満たしていても、横断的な境界健全性の責任主体が不明確になる可能性があります。

これは隠蔽とは別の、**判断主体の不在**という仮説です。

| 問題の名前 | 対策 |
| :--- | :--- |
| 見て見ぬふり | 説得・告発・規制 |
| 判断主体の不在 | 外部からの構造的強制 |

意図的黙認と判断主体不在では必要な対策が異なります。どちらが深刻かを一般論だけで順位づけせず、権限台帳、承認履歴、例外記録、事故調査から判定する必要があります。

---

## 7. モジュール分割と非分割性質

モジュール境界で内部実装を隠蔽することは、大規模並行開発を可能にします。しかし、局所仕様だけでは接続部をまたぐ性質を保証できない場合があります。

問題は、性質の側にあります。

- **局所性能**は、モジュールごとに測定できる場合があります。
- **横断的な境界健全性**は、局所検証の単純な合計だけでは保証できません。各モジュールが仕様を満たしていても、接続部で不整合が成立する場合があります。

これは努力量だけでなく、観測範囲と責任範囲の問題です。局所モジュールが保持しない情報は、横断テスト、統合監査、形式仕様など別の観測位置から補う必要があります。

### 7.1 なぜ未検証のまま完成してしまうのか

完成条件が「各モジュールの局所仕様を満たすこと」だけであれば、横断的な性質が完成判定から漏れます。未検証項目の台帳、統合試験、横断責任者がなければ、検証されていないこと自体が検出されずに出荷される可能性があります。

---

## 8. 導かれる帰結：判定機構の三条件

横断的性質は、局所検証の単純な積み上げだけでは保証できません。ただし、組織内部でも、独立した横断チーム、統合試験、形式仕様、監査権限を設ければ検証可能性を高められます。

よって判定機構は、次の三条件を満たす必要があります。

1. **評価対象から独立した横断的観測位置を持つこと**
2. **完成判定より前に作用すること**
3. **判定基準の変更権限、理由、影響、履歴を固定し、評価対象からの無記録変更を禁止すること**

第三条件が特に重要です。基準変更そのものを禁止するのではなく、評価対象が都合に合わせて無記録で緩和できない構造にします。

## 9. NRA-IDE との構造的対応

| 組織構造の問題 | NRA-IDE の設計原則 |
| :--- | :--- |
| 評価対象が評価基準を持つ | LLM に変数定義権限を渡さない |
| 内部からは観測できない性質 | 外部独立実装 |
| 完成後の検査では手遅れ | $R_{op}$ による境界到達前の作用 |
| 緩和の記録が残らない | Append-only ログ（上書き・削除の不提供） |
| 判定不能時の自動継続 | Fail-Closed（無応答は継続許可としない） |

組織構造の問題と、AIアーキテクチャの問題が同じ形をしています。両者は、**観測できない位置に判定者を置いてはならない** という単一原則の、二つの現れです。

---

## 10. 未確定事項の明示

以下は、構造的確度をもって決定できません。推測で埋めません。

- 各組織において、意図的黙認と判断主体不在がどの比率で混在しているか。内部資料への接近手段がないためです。
- 分割された組織が、内部に十分独立した横断監査と実行権限を設けられるか。一般的な不能証明はなく、組織ごとの権限設計と実績を確認する必要があります。

外部監査は有力な選択肢ですが、唯一の経路とは限りません。重要なのは組織の内外という名称ではなく、評価対象からの独立性、必要な観測範囲、事前作用、変更履歴、執行権限が実質的に成立していることです。

---

## 11. まとめ

1. 通電、情報保存、再実行可能性、活動、外部作用、学習還流は別の状態です。
2. 隔離・出力制御・監査・キルスイッチは、対象と効力を限定して用いる補助手段です。
3. 安全の中心は、生成能力と実行権限を分離し、許可されない現実更新を実行経路へ接続しないことです。
4. 論拠は遍在性ではなく、能力状態、作用経路、学習還流、観測経路の非同一性に置きます。突破確率式は独立仮定に依存するため、論拠から外します。
5. 開発者の認知、構造的帰結の仕様化、実装権限への反映は分けて調査します。
6. 判断主体の不在は有力な失敗仮説ですが、組織ごとの証拠なしに主因とは断定しません。
7. 横断的な境界健全性は局所検証の単純な合計では保証できません。判定機構には、独立した横断観測、事前作用、変更統制が必要です。
