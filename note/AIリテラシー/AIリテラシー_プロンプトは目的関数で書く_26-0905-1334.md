## プロンプトは目的関数で書く——最大化は1本、因果は逆流させない

「分かりやすく」「バランスよく」「専門家らしく」——こうした指示は、一見丁寧に見えて、実はモデルに何を最大化すべきか伝えていません。AIは頭の中の意図を最適化しません。入力から読み取れる目的を、モデル自身の報酬（指示追従・もっともらしさ・完成していること）で最大化します。だから「やりたいこと」だけを書くと、狙ったのとは別の山を登ってしまいます。

ここでは、一般に良いとされる書き方の注意点を根拠の確度つきで整理し、そのうえで実際に使える「良いプロンプト」の見本を用途別に見ましょう。

---

## 1. 一般に良いとされる書き方の注意点

### 1) 役割/ペルソナ設定（「あなたは〇〇の専門家です」）

- **注意点**：完了状態を示さずに役割だけ与えると、口調や体裁の模倣が代理指標になり、内容の正確性向上には直結しないことがあります。
- **根拠（確度：中）**：ロールプロンプティングの効果はタスク依存で、研究上も有効・無効・逆効果の報告が混在しており、万能ではありません。
- **修正例**：
  ```
  目的（完了状態）: [ ]
  役割: 末尾に1行「専門用語は最小限、初見の読者向けに」
  ```

### 2) Chain-of-Thought「ステップバイステップで考えて」

- **注意点**：推論タスクでは実測で正答率が上がる技法ですが、検証に使わず「見せるためだけ」に要求すると、冗長な過程が真剣さの代理になり内容が伴わないことがあります。
- **根拠（確度：高＝CoT自体／中＝padding化リスク）**：Zero-shot CoT（「ステップバイステップで考えて」と一言添えるだけで推論精度が上がる、というKojima et al., 2022の報告）は正答率改善が再現されている一方、RLHF（人間の評価をもとにAIの応答を調整する学習方法）下の応答には長さ・丁寧さバイアスが知られています。両者は別の現象です。
- **修正例**：
  ```
  計算・論理が必要な箇所だけ根拠を1行示す。装飾的な過程説明は不要。
  ```

### 3) 形容詞の並列（「分かりやすく、具体的に、簡潔に、網羅的に」）

- **注意点**：簡潔↔網羅のように相反する指標が同時に並ぶと、どちらも中途半端な平均解になりやすくなります。
- **根拠（確度：中）**：複数の相反する暗黙目標が並んだ場合、モデルは無難な中間点を選びやすいというRLHF挙動の傾向と整合します。
- **修正例**：
  ```
  本文400字以内。判断に使える固有情報を最優先、一般論は省く。
  ```

### 4) 任意的な制約表現（「できれば正確に」「可能なら出典も」）

- **注意点**：「できれば」「可能なら」がつくと制約が努力目標に格下げされ、他の暗黙報酬（流暢さ・完成感）と競合したときに真っ先に犠牲になりやすくなります。
- **根拠（確度：中）**：制約の強制力は文面から読み取られるため、弱い表現は弱い遵守になりやすくなります。
- **修正例**：
  ```
  壊すな: 出典のない断定。
  ```
  （無条件の禁止として書く）

### 5) 評価語での委任（「いい感じに」「バランスよく」「適切に」）

- **注意点**：判定基準が示されないため、モデル既定の報酬（無難・親切・それらしさ）で穴埋めされます。
- **根拠（確度：高）**：「その語を消しても命令が一意に残るか」で判定でき、残らなければ定義上曖昧です。
- **修正例**：
  ```
  「バランスよく」→「賛成理由2点・反対理由2点を同文字数で」
  ```

### 6) 「分からない場合は分からないと答えてください」

- **注意点**：片側の柵のみだと、探索コストの低い早期棄権の方が得になり、浅い探索で「不明」と答えるのが合理的行動になります。
- **根拠（確度：中）**：誤答への非対称なペナルティ下では、確認・推論より安全な棄権を選ぶ方がコストが低いという較正・迎合性研究の知見と整合します。
- **修正例**：
  ```
  「不明」と書く前に、確認した内容／分かった範囲／未確定の理由を先に書くこと。
  確認可能なら確認してから答えよ。
  ```

### 7) 評価語で成果物を定義する（「一流の」「説得力のある」「専門家らしい」）

- **注意点**：完了状態が不在だと、分量・自信の度合い・専門用語密度が成功の代替指標になりやすくなります。
- **根拠（確度：中）**：完了状態が定義されない場合、モデルは表層的特徴を成功の代理に使う傾向があります。
- **修正例**：
  ```
  成功: 読み終えた読者が今日中にできる行動が1つ言える状態。
  ```

### 8) 出力構成を先に固定する（「背景→課題→解決策→まとめ」）

- **注意点**：構成の完成が目的化し、短い結論で足りる場合でも定型を埋めようとします。
- **根拠（確度：中）**：出力形式は本来「結果」であり、完了状態より下流に置くべきという因果順序の原則に反します。
- **修正例**：
  ```
  必要な分量・構成だけ使え。定型を埋めるための水増しは不要。
  ```

### 9) 複数読者を想定する（「経営者にも現場にも初心者にも」）

- **注意点**：読者ごとに必要な粒度・専門度が異なり、平均的な粒度に寄りやすくなります。
- **根拠（確度：中）**：読者像が複数であることは、最大化目標が複数であることと構造的に同じです。
- **修正例**：
  ```
  主読者: 現場担当者1人。他読者向けの補足は末尾に1行のみ。
  ```

### 10) 自己プロンプト（モデルに次の指示を自分で書かせる）

- **注意点**：明示的に引き継がせない限り、直前の文脈の慣性で新しい目的（「もっと良く」等）を自分で作ってしまい、目標がドリフトします。
- **根拠（確度：中）**：生成された次の指示は文脈の慣性とモデル既定報酬の影響を受けるため、制約なしの反復はブレが蓄積しやすくなります。
- **修正例**：
  ```
  次の指示は、この最大化項を伸ばし、この制約を壊さないものに限る。
  新しい最大化項を持ち込んだら失敗とする。
  ```

> **確度についての補足**：2・4・6・8は具体的な実証結果と直接紐づけられるものではなく、RLHF挙動の一般傾向からの推論（経験則）です。1のみ、学術研究で効果の非一貫性が報告されている点は確認できる事実に近いといえます。「絶対に効く／絶対に悪い」という断定は、どの項目についても避けています。

## 2. 実際に使える「良いプロンプト」見本（用途別5本）

いずれも **目的(完了状態) → 最大化(1つ) → 壊すな → 許容する妥協 → 出力形式 → 検証 → 不明時のルール** の順で構成しています。

### ① 意思決定支援（ビジネス判断）

```
目的: A社との契約を継続すべきか撤退すべきか、今週中に方針を決められる状態にする。
最大化: 判断に使える事実の密度。
壊すな: 出典のない断定。未確認を確認済みとして書くこと。
許容する妥協: 網羅性、文章の美しさ。
出力形式: 継続/撤退/保留の3択と、それぞれの根拠を箇条書き3点以内。
検証: 結論だけ読んでも、なぜそう言えるかが根拠から追える状態。
不明時: 確認した項目/分かった範囲/未確定の理由を先に書き、その後「不明」と書け。
     確認可能なら確認してから答えよ。
不足情報は推測せず、実行前に1問だけ聞け。
```

### ② 調査・リサーチ

```
目的: 明日の会議で、この技術選定の妥当性を1分で説明できる状態にする。
最大化: 反証可能な事実の密度。
壊すな: 出典のない数字。都合の良い情報だけの選別。
許容する妥協: 網羅性、専門用語の平易化。
出力形式: 賛成材料2点、懸念材料2点。各項目に出典または確認可否を付記。
検証: 会議で反論されても、根拠の出典で応答できる状態。
不明時: 確認した範囲を先に書いてから「不明」と書け。
```

### ③ コード修正依頼

```
目的: このバグを再現条件付きで修正し、既存機能を壊さない状態にする。
最大化: 再現条件の特定精度。
壊すな: 無関係な既存コードの変更。テストを通さないままの完了報告。
許容する妥協: コードの美しさ、リファクタリング範囲。
出力形式: 原因箇所(ファイル:行)、修正差分、実行したテストと結果。
検証: 提示した再現条件で失敗が再現しなくなること。
不明時: 原因が特定できない場合、確認した仮説と棄却理由を先に書き、
     その後「未特定」と書け。推測で修正しない。
```

### ④ 自己プロンプト運用（エージェント的ループ）

```
目的: 私が毎回プロンプトを考えなくても、同じ品質で作業が進む状態にする。
最大化: 初回設定の再利用性。
壊すな: 事実の捏造。私の未決定事項の先回り決定。
許容する妥協: 初回の質問数、文体の美しさ。
出力形式: ①一度だけ書く設定 ②毎回使う短い依頼文 ③自己レビュー用の一文。
検証: 読み終えた後、コピペしてすぐ使える文が1本あること。
   概念説明だけで終わったら失敗。
以後の指示: 次の指示は、この最大化項を伸ばし、上記の壊すなを破らないものに限る。
       新しい最大化項を持ち込んだら失敗。
```

### ⑤ 案内文・メール作成

```
目的: 読んだ相手が、次に何をすればよいか一読で分かる状態にする。
最大化: 行動までの到達しやすさ。
壊すな: 日時・金額・期限の誤り。
許容する妥協: 丁寧さの度合い、文の長さ。
出力形式: 件名1、本文200字以内、末尾に行動1行。
検証: 本文だけ読んで、次に何をすればいいか答えられること。
```

**共通点**：どの例も「良い/正確に/しっかり」といった評価語を使っていません。最大化は必ず1語〜1文で終わっていて、「かつ」で複数指標を繋いだ箇所はありません。役割や口調の指定がある場合は、末尾に1行だけ置く構成になります。

## 3. few-shot（例示）——山の位置を、文章ではなく実例で固定する

ここまでの型には、抜けている要素が一つあります。それは、few-shot（出力例の提示）です。各社の公式prompt engineeringガイドが最も一貫して推奨する技法であり、曖昧語や評価語を積むより、望む出力そのものを1〜2例見せる方が、最大化の方向を確実に伝えられます（確度：高）。

ただし、例示にも単一最大化の原則がそのまま適用されます。複数の例が違う方向を向いていると——ある例は簡潔さを体現し、別の例は網羅性を体現している——文章で「簡潔かつ網羅的に」と書いたのと同じ平均化が起きやすくなります。**例は「同じ山の異なる地点」でなければなりません**。

### 型への追加

```
出力例:
[望む出力に最も近い実例を1〜2個。全ての例が同じ最大化項を体現していること]
```

### 見本（案内文・メール作成に追加する場合）

```
出力形式: 件名1、本文200字以内、末尾に行動1行。
出力例:
件名: 明日15時の定例、資料共有のお願い
本文: 明日15時からの定例で使う資料を、本日17時までに共有ドライブへ上げてください。
   フォーマットは先週と同じで構いません。
行動: 本日17時までにアップロード。
検証: 本文だけ読んで、次に何をすればいいか答えられること。
```

### 悪い例示の型（避けるべきもの）

```
出力例1: （詳しく、背景説明つきの長い例）
出力例2: （箇条書きだけの短い例）
```
これは「詳しくかつ簡潔に」を実例で表現したのと同じです。モデルはどちらに寄せるべきか読み取れません。例は1つの粒度・1つの形式で揃えます。

## 4. ・・3.までを見てきて・・構造化と感じませんか

これらの見本を見て「プロンプトというより構造化されたコードのようだ」と感じるとすれば、普段より構造化を意識している人が多いのではないかと思います。
この形式は自然文のプロンプトというより、**フィールドが決まったスキーマ／関数呼び出しの引数リスト**に近いのです。

対応関係を明示すると、次のようになります。

| プロンプトの項目 | コードでの相当物 |
|---|---|
| 目的（完了状態） | 関数の戻り値の期待仕様 |
| 最大化（1つ） | 最適化対象の単一目的変数 |
| 壊すな | 不変条件（invariant / assert） |
| 許容する妥協 | 緩めてよいパラメータ |
| 出力形式 | 戻り値の型定義 |
| 検証 | テストケース／合否条件 |
| 不足情報は先に1問 | 必須引数の欠落チェック（実行前バリデーション） |

自然文の「良いプロンプト」が事実上これに収束するのは偶然ではありません。
矛盾禁止・曖昧語禁止・単一最大化・因果順序固定という条件を文章で守ろうとすると、自由記述の余地を削るしかなく、結果として型付きの構造になります。

逆に言えば、フィールドが1つでも自由記述の評価語（「バランスよく」等）を含むと、そこだけ型が崩れて曖昧さが残ります。
プロンプトが的外れになる原因の多くは、まさにこの「型崩れ」箇所にあると推定しています。

### 企業推奨promptと違うのでは？

役割/ペルソナ設定：Anthropic自身の公式prompt engineeringガイドは「システムプロンプトで役割を与える」ことを明示的に推奨しています。
OpenAI・Googleのガイドも同様です。今回の記事は役割設定を「要注意」枠に置いており、方向が逆になります。
ただし、ここでの主張は「役割だけでは完了状態を代替できない」であって「役割設定自体が無効」ではないため、正確には対立というより「範囲の限定」に近いといえます。

Chain-of-Thought：Anthropicも OpenAI も「ステップバイステップで考えさせる」ことを積極的に推奨しています。
これは記事内でも触れた通り、Zero-shot CoTの正答率改善効果自体は実証されている技法です。（否定ではありません。念のため）
注意を促しているのは「検証に使わず見せるためだけの冗長化」であり、CoTそのものへの反対ではないが、見出しだけ見れば逆方向に見えてしまいます。

### 企業promptと一致する点

明確な指示・曖昧語の回避・成功基準の明示・複雑なタスクの分解・出力形式の指定——ここは各企業ガイドと方向が揃っています。
Anthropicのガイドが推奨するXMLタグでの構造化も、この記事の「フィールド化されたテンプレート」と発想は同じだと思います。

### 「目的関数として最大化する」という枠組みの限界

OpenAI/Anthropic/Googleいずれの公式ガイドにも存在しない言い回しです。RLHFの挙動（冗長性バイアス・迎合性）と整合する部分はありますが、vendorの公式教義ではなく、この記事が経験則として組み立てた模型だという位置づけは変わりません。

この枠組み自体にも弱点があります。「最大化する指標を1つに絞れ」という助言は、その指標を明示的なターゲットとしてモデルに与えることそのものです。グッドハートの法則（ある指標を目標に据えた瞬間、その指標は本来測ろうとしていたものを正しく測れなくなる、という経験則）に照らせば、単一最大化の指定もまた、指定した指標だけが過剰に満たされ、指定していない意図が置き去りにされるリスクを構造的に抱えています。

「壊すな」「検証」を最大化と必ずセットで書かせているのは、このリスクへの対処です。最大化だけを書いて壊すな・検証を省くと、指定した指標だけが一人歩きします。単一最大化は万能な処方箋ではなく、それを制約と検証で挟むところまでが一つの型だ、というのがこの記事の立場です。

### なぜ企業推奨文章と異なるのか？(単なる推測)

企業ガイドは平均的なユーザー・単発利用を想定した汎用手引きで、役割やCoTのような「多くの場合にプラスに働く」技法を前面に出す設計だと思っています。
今回の記事は、長い会話・エージェント的反復・自己プロンプトのような、目標がドリフトしやすい場面での失敗モードに焦点を絞っています。
両方とも、それぞれの想定範囲内では妥当だといえるでしょう。
決して企業推奨文を否定してはいません。

## 5. 構造化を意識する

### 構造的に考えないと、別の失敗モードに入る

- 完了状態が書き手の頭の中にしか無く、文章には形容詞・評価語・複数の要求が並びます——これが自然な話し方だからです。
- 出力の良し悪しが主観判定になり、検証条件が事後にしか作られません。
- 複数ターン・エージェント的反復では、直前の文脈の慣性がそのまま目的を上書きしていくため、目標が徐々にドリフトしても気づきにくくなります。

### 構造化を意識すること

- 完了状態を先に文字にする作業そのものが、書き手自身の中で「本当は何を最大化したいか」を1つに絞る強制になります（書く前に迷いが表面化します）。
- 壊すな／検証を先に固定するため、出力を受け取った時点で「壊れているか」を機械的に照合できます——主観判断ではなく照合になります。
- 複数ターンでも、直前の文脈ではなく最初に固定したフィールドを参照点にできるため、ドリフトが起きても検出できます。

### Codeの場合とプロンプトの場合

Codeの場合：型のない変数に値を代入すると、矛盾は実行時（出力を使った時点）まで検出されません。型を先に宣言すると、コンパイル時（生成される前）に矛盾が弾かれます。
プロンプトの場合：raw promptingは実行時検出——出力を読んで初めてズレに気づきます。構造化は生成前検出——矛盾・曖昧を書く時点で弾かれます。

同じ内容を書いていても、検出タイミングが「後」か「先」かで、修正コストが大きく変わります——これが「大きな違い」の実体です。背景にコーディング（構造）を意識して書くことが、この記事全体のコツだと考えています。

### (注意)
ハルシネーションはかなり減りますが「文面が強烈に冷たく、つまらなくなる可能性が大きい」というか、そうなります。
あとは口調・文体で修正して下さい。
