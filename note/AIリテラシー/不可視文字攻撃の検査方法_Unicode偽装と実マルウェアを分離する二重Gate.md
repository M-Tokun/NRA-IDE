# 不可視文字攻撃の検査方法

## Unicode偽装と実マルウェアを分離する二重Gate

## はじめに

画面では同じように見えるのに、コンピューターには違う内容として解釈される文字があります。

たとえば、次のような文字です。

- 幅を持たないゼロ幅文字
- 文字の表示方向を変える双方向制御文字
- 見た目が似ている別のUnicode文字
- 絵文字の表示形式を指定する異体字セレクタ
- ファイル先頭に置かれるBOM

これらは、すべてが危険なわけではありません。

絵文字を正しく表示するために必要な文字もあれば、CSVの文字コードを示すために意図的に置かれたBOMもあります。

一方で、見た目と実データの違いを利用し、人間の確認をすり抜ける攻撃にも使われます。ソースコードの表示順序と、コンパイラが解釈する順序を食い違わせるTrojan Sourceは、その代表例です。

この問題に対して、

> AIに読ませて、不審かどうか判断してもらう

だけでは安全性を確立できません。

AIも、人間と同じように表示された文字列や前後の文脈に影響されます。また、AIが「安全です」と答えても、全コードポイントを検査した証明にはなりません。

必要なのは、AIに判断させる前に、実データを決定論的に検査する境界です。

---

# 第1章　不可視文字攻撃はウイルスですか

日常的には「不可視型ウイルス」と表現したくなることがあります。

しかし、安全対策を設計するときは、少なくとも次の二つを分ける必要があります。

| 種類 | 何が起きるか | 主な検査方法 |
|---|---|---|
| Unicode偽装攻撃 | 表示と機械解釈が食い違う | コードポイント検査 |
| 実マルウェア | 不正なプログラムや命令が実行される | ウイルス対策製品、サンドボックス、署名検査 |

ゼロ幅文字が存在するだけでは、ファイルがウイルスに感染しているとは限りません。

反対に、Unicode上は正常でも、実行ファイルやスクリプトにマルウェアが含まれている可能性はあります。

したがって、Unicode検査だけで「ウイルスなし」と判断してはいけません。また、ウイルス対策製品が脅威を検出しなかったからといって、Trojan Sourceのような表示偽装がないとは限りません。

この二つは、別の検査層で扱います。

---

# 第2章　なぜ人間の目視だけでは確認できないのですか

通常の確認では、画面に表示された内容を見ます。

しかし不可視文字攻撃では、確認したい対象そのものが画面に正しく現れません。

たとえば、実データが次の並びだったとします。

    abc\u202Edef

U+202EはRIGHT-TO-LEFT OVERRIDEという双方向制御文字です。

検査画面がこの文字をそのまま解釈すると、周囲の表示方向まで変化する可能性があります。その結果、検査報告自体が攻撃対象になります。

そこで、検出結果には生文字を入れません。

    codepoint: U+202E
    name: RIGHT-TO-LEFT OVERRIDE
    category: Cf
    escaped_context: abc\u202Edef

このようにASCIIだけで表現すれば、報告を見るソフトウェアが制御文字を実行することを防げます。

重要なのは、

> 見えるように表示する

だけではなく、

> 表示機能に解釈させない形式へ変換する

ことです。

---

# 第3章　AIの前に置くUnicode Boundary Gate

基本構造は次のようになります。

    Raw Input
        ↓
    Unicode Boundary Gate
        ├─ PASS → AI、IDE、Compilerへ
        └─ FAIL → 遮断

Boundary Gateは、同じ入力と同じポリシーに対して、毎回同じ結果を返す必要があります。

主な検査対象は次です。

- UTF-8として正しく復号できるか
- CcまたはCfカテゴリの制御・書式文字
- 双方向制御文字
- ゼロ幅文字
- 非ASCII改行文字
- Unicode非文字
- BOM
- 異体字セレクタ
- NFCなどの正規化状態
- 識別子における危険な文字体系混在
- パス名に含まれる制御文字

ただし、似た字形の完全な検出は簡単ではありません。

たとえば、数式で使われるギリシャ文字とラテン文字を一律に危険とすると、正当な数式まで大量に警告されます。UTS #39などの固定データを導入していない段階では、検出範囲と限界を明記する必要があります。

検出器が分からないことを、分かったように扱ってはいけません。

---

# 第4章　無条件削除が危険な理由

不可視文字を見つけたとき、

> すべて削除すれば安全になる

と考えたくなります。

しかし、実際には意味を持つ文字があります。

## U+FE0F

U+FE0Fは異体字セレクタです。絵文字表示を指定するために使われることがあります。

これを全面削除すると、表示形式が変化する可能性があります。

## U+200D

U+200DはZERO WIDTH JOINERです。

複数の文字を一つの絵文字として結合する用途があります。たとえば、人とロケットを結合した絵文字では、U+200Dが意味を持ちます。

## U+FEFF

U+FEFFはファイル先頭ではBOMとして使われます。

CSVの試験データが意図的にBOM付きであり、読み込み側がUTF-8-SIGを使うことを検証している場合、BOMを削除すると試験の意味が変わります。

また、説明文の中で実際の不可視文字を例示していることもあります。この場合は削除ではなく、

    \uFEFF

という可視のASCII表現へ置換する方法があります。

したがって処理は、

> 検出、可視化、用途別判断、明示承認、限定修正

の順に行います。

# 第5章　LIST方式

検出結果は、AIの説明文だけにしません。

ASCII限定の機械可読LISTへ書き出します。

    {
      "id": "UG-...",
      "path": "example.py",
      "file_sha256": "...",
      "rule": "BIDI_CONTROL",
      "severity": "FAIL",
      "line": 18,
      "column": 27,
      "codepoint": "U+202E",
      "escaped_context": "abc\\u202Edef",
      "decision": "PENDING",
      "action": "NONE"
    }

すべての検出事項は、最初はPENDINGです。

AIが文脈を読んで、自動的にAPPROVEDへ変更してはいけません。

修正を許可する場合でも、少なくとも次を確認します。

- 走査時と現在のファイルSHA-256が一致する
- パスがリポジトリ内にある
- 行、列、コードポイントが一致する
- 承認された操作が削除か置換か明示されている
- 修正によって新しいUnicode検出が増えない

一致しない場合は、推測して修正せず停止します。

---

# 第6章　全面許可ではなくexact baseline

正当な文字が見つかったとき、コードポイント全体を許可すると、将来追加された同じ文字まで無条件で通過します。

たとえば、

> U+FE0Fは安全だから、今後すべて許可する

というポリシーは広すぎます。

代わりに、現在確認した出現だけをbaselineへ登録します。

baselineには次を含めます。

- ファイルパス
- ファイルSHA-256
- 規則
- コードポイント
- 行と列
- baseline entry ID
- 保持理由

ファイル内容が変わればハッシュが変わり、以前のbaselineは一致しなくなります。

これは不便に見えますが、過去の承認が将来の別内容へ自動継承されることを防ぎます。

baselineは異常を消すための箱ではありません。

> 確認済みの特定状態だけを、証拠付きで次状態へ継承する仕組み

です。

---

# 第7章　入口と出口の二つのGate

Unicode検査は、入口と出口の両方に置きます。

    外部入力・生成
        ↓
    第1防衛線：入力時Unicode Gate
        ↓
    IDE・AI・Compiler・テスト
        ↓
    第2防衛線：pre-push Gate
        ↓
    Remote Repository

## 第1防衛線

ファイルを取得、生成、貼り付けた直後に検査します。

目的は、危険な文字が編集環境やAIの文脈へ入る前に止めることです。

## 第2防衛線

Git push直前に、送信予定コミットに含まれるblobを検査します。

Gitはファイル単位ではなくコミット履歴を送信します。そのため、最終状態だけを見ると、途中のコミットに存在して後で削除されたblobを見逃す可能性があります。

pre-push Gateでは、送信範囲に新しく到達可能になるblobを列挙し、途中コミットだけに存在するblobも含めて検査します。

GitHub Actionsは第3防衛線として有効です。

しかしpush後の検査なので、問題のある内容がすでにリモート履歴やPull Requestへ入った後になります。ローカルでFail-Closedする最終関門の代わりにはなりません。

---

# 第8章　実マルウェア検査を別に置く

Unicode Gateは、マルウェア検査器ではありません。

そこでpre-push前には、別のMalware Gateを置きます。

検査時には次を確認します。

- ウイルス対策機能が有効か
- リアルタイム保護が有効か
- 定義ファイルが古すぎないか
- 走査対象を飛ばしていないか
- 走査器が正常終了したか
- LFSポインタだけを見て実体を未検査にしていないか
- 容量超過を理由に黙ってスキップしていないか

検査不能は安全ではありません。

    未検査 ≠ 脅威なし

そのため、署名が古い、走査器が利用できない、対象容量が上限を超えた、LFS実体を確認できない、といった場合はpushを止めます。

走査時に自動駆除を行うと、検査の途中でファイル内容が変わり、Gitのsnapshotと検査対象が一致しなくなる可能性があります。

検査工程では自動修復を無効にし、検出、隔離判断、修復を別工程に分ける方が追跡しやすくなります。

---

# 第9章　初回baselineと日常運用

検査対象を「直近30日だけ」にすると、31日前に混入した文字を永久に見逃す可能性があります。

運用は次の三段階に分けます。

## 初回

リポジトリ全体を走査し、既存の検出事項を確定します。

## 日常

新規・変更ファイルと、送信予定Git blobを必ず検査します。

## 定期

検査器、Unicodeデータ、ポリシーが更新されたときは、全体を再走査します。

状態は次のように継承されます。

$$
S_{t+1}
=
S_t
+ \{\text{新規・変更}\}
- \{\text{承認済み修正}\}
$$

新しいbaselineによって、過去の未解決事項を消してはいけません。

# 第10章　実施例から分かったこと

あるリポジトリでは、初回走査で次の結果が出ました。

- 走査対象：707ファイル
- FAIL：97件
- WARN：57件

内訳を調べると、すべてを削除してよいわけではありませんでした。

- U+200Bのノイズ：91件を削除
- 説明用のU+200BとU+FEFF：4件をASCIIエスケープへ置換
- U+FE0F：57件をexact baselineで保持
- CSV BOM：1件を試験データとして保持
- 絵文字のU+200D：1件を保持

最終結果は次です。

- FAIL：0件
- WARN：0件
- BASELINED：59件
- unittest：106件成功
- pytest：106件と32 subtests成功
- HAN統合検証：7項目成功

この結果が示すのは、

> 不可視文字を全部消すこと

ではありません。

> 意味を持つ文字とノイズを、証拠を保持したまま分離できたこと

です。

# 第11章　AIの役割

AIは、次の役割に限定すると有効です。

- コードポイントの意味を説明する
- 周辺文脈から用途候補を提示する
- 人間が確認するための論点を整理する
- 検査スクリプトやテストを作る

一方で、次をAIだけに任せてはいけません。

- 文字の存在確認
- 正確な位置の確定
- ファイルハッシュの確定
- すべての検出事項の自動承認
- push可否の最終権限

役割分担は次です。

| 層 | 役割 |
|---|---|
| 決定論的検出器 | 存在、位置、コードポイントを確定 |
| AI | 意味と攻撃可能性を説明 |
| Policy Gate | 事前規則に基づいて遮断 |
| 人間 | 意味判断と例外承認 |

AIが忘れても、検査手法が消えないようにする必要があります。

スクリプト、policy、baseline、LIST、テスト、hookへ外部化することで、会話の記憶から安全性を分離できます。

---

# 第12章　外部横軸としてのUnicode Gate

この方式は、ある瞬間のファイルだけを見る方法ではありません。

変更前のハッシュ、検出事項、承認、baseline、変更後のハッシュ、テスト結果を接続します。

$$
H_t=(C_t,F_t,D_t,B_t,V_t)
$$

- $C_t$：ファイル内容とハッシュ
- $F_t$：検出事項
- $D_t$：承認状態
- $B_t$：保持するbaseline
- $V_t$：検証証拠

遷移条件は次です。

$$
H_t \rightarrow H_{t+1}
\iff
\text{Preimage一致}
\land
\text{明示承認}
\land
\text{新規異常なし}
\land
\text{回帰検証成功}
$$

これはAI内部の記憶ではありません。

AIの外側で、証拠と権限を次状態へ継承する外部横軸です。

---

# まとめ

不可視文字攻撃への対策で重要なのは、AIや人間の注意力を上げることだけではありません。

確認できないものを、確認可能な形式へ変換する必要があります。

- Unicode偽装と実マルウェアを分離する
- 生文字ではなくASCIIエスケープで報告する
- AIの前に決定論的Gateを置く
- 全件をPENDINGから始める
- 無条件削除と全面許可を避ける
- exact baselineで正当な文字を限定保持する
- 入口とpre-pushの二重Gateを置く
- 変更前後のハッシュと検証証拠を継承する
- 検査不能を安全扱いしない

安全性は、

> 見つけられるか

だけではなく、

> 見つけた事実を、意味と証拠を失わずに次工程へ渡せるか

によって決まります。
