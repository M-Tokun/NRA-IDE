### K1：初回の保証範囲と責任分界

初回は、単一送信先・明示した単一branch refspec・送信元OIDとHEADの一致を条件として、既存pre-push経路の通常branch更新における検査省略、対象不一致、パス・baseline情報の欠落、結果の誤解釈を是正する。複数送信先・複数ref・HEAD以外からの送信は初回の対象外とし、対応拡張は後段の別設計とする。既存branchと新規branchを扱い、既存の削除・非branch ref・non-fast-forwardの遮断を維持する。AGENTS.mdが禁止するforce操作等を、新たな通常操作として許可しない。

実装の中心は既存hookとゲート間の受渡しである。初回の稼働確認環境は、現行Malware Gateが依存するWindows・PowerShell 7・Python・Defenderを備えた経路とする。環境が満たされない場合は検査不能として停止し、別OS対応を検証済みとは扱わない。

| 担当 | 決定・検査するもの | 決定しないもの |
| --- | --- | --- |
| 呼出し元・作業手順 | 依頼範囲、送信全コミットの提示、利用者の最終承認 | ゲート成功を利用者承認へ読み替えること |
| pre-pushと集約処理 | 実際のref更新と計画の一致、構造制限、必須検査の完了 | 内容の意味・理論の正しさ、利用者の代理承認 |
| 各ゲート | K3で定める対象を、固定した規則で検査する | 送信先・規則・例外承認を独自に変更すること |
| 後段のCI・保護設定 | 対応環境での再検査と保護対象への反映条件 | ローカルhookと同一の実効動作を未検証のまま保証すること |

同じ書込権限を持つ主体による意図的なhook改変・別経路送信まで防ぐ保証は初回範囲に含めない。署名基盤、新しい承認サービス、ラッパー、CI・GitHub設定の変更は初回修正の必須依存にせず、必要な場合に後段の対象を別途確定する。

既存の[操作承認部品](../../skills/operation-approval/README.md)の第一段階は局所検査モジュールであり、実ホストやpre-pushへ接続されていない。本節の送信計画・manifest・結果集約は検査対象の照合を扱い、同部品の要求schemaや真正な承認receiptと同一ではない。`valid=true`、計画の一致、AIが作った「承認済み」JSONを、現在のhookやpre-pushの実行許可として使用しない。最終承認はAGENTS.mdに基づく利用者の明示的な確認として別に扱い、読込マーカーや検査成功で代用しない。

新規branchの基点検査は本節の対象だが、既存操作承認部品は新規branchを拒否する。したがって新規branchを同部品で対応済みとして通さず、検査経路の改善と承認部品の拡張・接続を別工程とする。後者は実在するbroker、保護、実行主体、通信と経路を確定する別設計・別承認を要し、本節の初回実装には含めない。

### K2：送信対象と検査条件の確定

fresh fetch後に、次の内容を送信計画として固定する。初回は送信先と更新refをそれぞれ1件に限定し、複数push URLや暗黙の追加refを検出した場合は停止する。実行中に作業ツリーの `HEAD` や既定push設定を読み直して対象を置換しない。

| 計画の情報 | 確定方法・条件 |
| --- | --- |
| 送信先 | remote名、認証値を含めない送信先識別子、更新先ref。対象remote設定の変更も検出対象とする |
| ref更新 | 明示した単一branch refspec、HEADと同じ送信元OID、期待するremote側の旧OID。新規refは未存在であることを区別する |
| 検査基点 | 既存branchはfetchで確認した更新先OID。新規branchはfresh fetchしたremote既定branchと送信元OIDのmerge-baseであり、その既定branchのOIDも記録する |
| 送信範囲 | 確定した基点からHEADと同じ送信元OIDまでの全コミット。依頼対象集合と一致し、暗黙の追加送信を含まないことを確認する |
| 規則 | 使用するゲート実装・必要な補助コード・policy・baselineの版と内容ハッシュ、各ゲートの適用範囲の版 |

incoming、対象外コミット、解決不能なOID・基点・送信先、解釈できないrefがある場合は送信処理へ進めない。mergeや履歴改変で自動解消しない。fresh fetchとコミット列挙の成功だけで、利用者の依頼範囲に合うと判定してはならない。

計画を識別する値を結果と承認記録へ対応付ける。これは同一性確認のための情報であり、利用者承認や改変耐性を証明する署名ではない。実際のhook入力が計画どおりの単一ref更新であることを確認し、その旧新OID・更新先を照合する。追加refがあれば初回対象外として停止する。新規branchでは検査基点の版も確認し、差異があれば古い検査結果を使用しない。

### K3：対象データの受渡しとゲート別の検査範囲

既存manifestを拡張して受け渡す。元ファイル名をシェル引数の空白分割で渡さない。パスは元のUnicode表現を保ち、JSONのエスケープで改行・制御文字を表現する。Unicode正規化や置換によって、検査前に問題文字を消さない。必要なパスを損失なく解釈できない場合は検査不能とする。

| データ | 必須の対応関係 |
| --- | --- |
| 内容 | blob OID、実bytes数、元bytesのSHA-256、検証済み展開先名。Gitから読み出したbytesを改行変換せず使用する |
| 出現 | 対象commitと元パス・mode・blob OIDの対応。既存blobを再利用する追加・名前変更・拡張子変更・mode変更も含める |
| 完全性 | 計画、列挙した対象、検査対象、対象外とした理由を対応付ける。展開に失敗した項目を件数から黙って落とさない |

展開先はblob OID等の安全な名前を使い、元パスをそのまま展開先パスにしない。manifestの相対展開先が検証済み出力ディレクトリ内にあることと、内容のOID・サイズ・SHA-256を確認する。symbolic linkのblobはリンク先文字列として扱い、リンクをたどって別ファイルを読み込まない。

| 必須検査 | 初回で使用する対象と規則 |
| --- | --- |
| 構造検査 | 実際のref更新。初回の単一送信先・単一branch refspec・送信元OID=HEADを確認し、既存の禁止操作と基点確認を維持する |
| Malware | 今回の送信範囲から新たに到達可能になる全blob。先端で削除済みの中間コミット由来の内容も含む。同じbytesのAV検査は一回でよい。送信対象外の作業ツリー全体の検査とは分離する |
| Unicodeのパス検査 | 今回の送信範囲で追加・変更される元パス。内容が既存blobでも検査する。mode変更と複数パスへの出現を失わない |
| Unicodeの内容検査 | 新規blobに加え、既存blobが追加・変更されたパスで新たにテキスト用途となる場合。各元パス・元bytesでbaselineを照合し、あるパスの承認を別パスへ流用しない |
| ID | 各送信先端の `note/` 対象Markdown。必須値・形式は現行の変更対象判定を維持する。ID重複と参照解決には先端の全対象記録を使用し、変更文書に加えて、削除・ID変更で失われたIDへの既存参照も影響対象として評価する。既存baselineの免除を維持し、未変更の免除対象へ一律に新書式を要求しない |
| Dictionary | 各送信先端の辞書、公開ID一覧、その辞書へリンクする追跡対象Markdown。辞書・リンクの既存判定を維持し、未追跡の下書きは含めない。先端の全追跡Markdownから参照を選ぶことで、既存参照元も確認する |

Unicodeの分類は、審査済みpolicyのバイナリ拡張子一覧を維持する。そこに属さない内容は、上限内でUTF-8として解釈できればテキスト検査する。UTF-8として解釈できない場合、既知テキスト形式は `INVALID_UTF8` の失敗、未分類の形式は検査不能として扱う。初回の既知テキスト形式は `.md`・`.txt`・`.py`・`.js`・`.mjs`・`.cjs`・`.ts`・`.tsx`・`.jsx`・`.html`・`.css`・`.json`・`.jsonl`・`.yml`・`.yaml`・`.toml`・`.ini`・`.cfg`・`.csv`・`.tsv`・`.xml`・`.svg`・`.sh`・`.ps1`・`.sql`・`.tex`・`.bib` とし、この分類表も版管理する。これは形式の安全性の認定ではない。同じblobにテキスト用途のパスがあれば、別のバイナリ用途のパスを理由にその検査を省略しない。

必要なLFS実体・変更されたgitlinkの内容を現行方式で検査できない場合は、対象と未対応理由を記録して停止する。未変更のgitlinkが先端に存在するだけで、無関係な更新まで新たに停止させない。AV検査の対象外となる既存blobを含め、リポジトリの過去全体を検査済みとは表現しない。

容量は現行の総量上限・テキスト上限を初回の既定として維持し、blobを全体読取する前に既知サイズで超過を確認する。実測に基づく上限変更、ストリーム処理の方式、タイムアウト値の調整は実装内の検証項目とし、未測定の数値を安全性や速度の根拠にしない。

### K4：結果の分類と集約

各ゲートの既存CLIを一律に書き換えることは必須にしない。接続側が終了コードと必要な出力を照合し、次の共通結果へ変換する。意味や変換規則が未確認の終了コードを、推測で成功や違反検出に分類しない。

| 結果 | 条件 | 必須ゲートでの扱い |
| --- | --- | --- |
| `PASS` | 対象全体の検査が完了し、activeな警告・失敗がない | 検査条件を満たす |
| `WARN` | 完了し、activeな指摘は警告だけ | 記録・提示し、警告だけを理由に一律停止しない |
| `FAIL` | 定義済み規則による失敗を検出 | 対象pushを停止 |
| `UNAVAILABLE` | 未対応、実行不能、対象欠落、出力不正、内容不一致、中断・タイムアウト等 | 対象pushを停止し、原因と未検査範囲を示す |
| `NOT_APPLICABLE` | 計画と列挙結果から、そのゲートに該当する対象がないと確認 | 対象なしの根拠を記録。単なる空出力では使用しない |
| `NOT_RUN` | 先行失敗等で検査していない | 成功扱いしない。必須検査が残る要求は送信不可 |

共通結果には、計画の識別子、ref・ゲート、適用した規則の版、対象範囲、列挙件数と検査件数、対象外の理由、結果、指摘・エラーの識別情報を含める。指摘は元パス、規則、必要な行・列・コードポイントで示す。秘密値、認証値、ファイル内容全体は報告へ保存しない。AVは実際に使用したエンジン・定義の版と鮮度を結果に残す。

`FAIL` または `UNAVAILABLE` が一つでもあれば、他の成功で上書きしない。必須検査の対象全体が `PASS`・`WARN`・根拠のある `NOT_APPLICABLE` に収まった場合だけ検査条件を満たす。終了コード0だけ、警告件数0だけ、展開件数0だけでは全体成功としない。先行失敗で打ち切る場合は、残りを `NOT_RUN` と記録する。

検査全体の成功、利用者の承認、実際の送信成功は別の記録とする。未承認は各ゲートの違反検出ではなく、送信手順が実行へ進めない状態として扱う。

### K5：最終承認、例外、検査結果の失効

処理順は、対象と規則の確定、必須検査、結果と送信範囲の提示、利用者の最終push承認、同一性の再確認、送信、remoteの再照合とする。検査失敗時に送信承認を求めて進めない。ラッパーを導入する場合も、この既存の承認を対応付け、追加の同内容の確認を必須にしない。

承認前の提示には、remote・更新先branch/ref・HEADと同一の送信元OID・送信全コミット・incoming/outgoing・検査結果を含める。HEADと実送信元が異なる要求は、差の説明だけで許可せず初回対象外として停止する。承認後にref集合、送信元、remoteの旧OID、検査基点、送信先設定、使用規則が変われば、古い結果や承認をそのまま流用しない。該当部分を再確定・再検査し、変更された対象を提示して必要な承認を得る。

送信対象外の下書き等の変更だけでは、固定済み計画を失効させない。AVの定義・鮮度等の環境条件は実行前に再確認し、検査結果が無効になった場合は影響する検査を再実行する。結果や送信条件が変わった場合は、その差を提示する。初回の検査計画へ根拠のない追加期限を設けて、同じ対象の再承認を増やさない。これは既存の操作承認部品の期限・fetch鮮度条件を緩和する意味ではない。同部品を将来接続する場合は、版管理された期限・再fetch時の失効規則も別途適用する。

baselineは既存の元パス・元bytesのSHA-256・規則・コードポイント・行・列の厳密一致を維持する。移行時に展開先名や作業ツリーの改行形式で再生成しない。不一致の古い承認は現在の免除へ使用せず、現行のactiveな指摘で判定する。古い承認が未使用であるだけではfailにしない。追加・変更する例外は対象差分と影響を提示して人間が承認し、その後に再検査する。ゲートが自動で承認記録を書き換えない。

同一内容に対する検査の再利用は、内容・パス別条件・規則・必要なAV条件が同じと確認できる範囲に限る。初回は永続キャッシュを必須にせず、同じ要求内の重複抑制を優先する。送信後は対象remoteを再fetchし、単一対象branchのremote OIDがlocal HEADおよび計画の送信元OIDと一致し、ahead/behindが `0 0` であることを確認する。拒否・失敗・確認不能を成功へまとめない。

### K6：導入、復旧、受入試験

導入は、対象と受渡しの修正、ゲート別の正常系・不正系確認、集約・承認との接合確認、実クライアント経路の無害な遮断確認の順とする。CI・保護設定は、その後に対応OS・履歴取得・イベント・チェック名・権限・復旧手順を検証してから必須化する。実装前に稼働実績を要求するのではなく、以下を実装後の合否基準として固定する。

| 試験 | 合格となる振舞い |
| --- | --- |
| A01 通常・既存branch | 単一送信先・単一branch refspec・送信元OID=HEADを満たす対象で、全必須検査と最終承認が一致し、正常な更新を妨げない |
| A02 新規branch | fresh fetchした既定branchとの基点を使用。基点不明・依頼対象外コミットがあれば停止。新規branch未対応の操作承認部品を、対応済みとして呼び出さない |
| A03 構造制限 | ref削除・非branch ref・non-fast-forwardを既存どおり遮断し、承認を自動生成しない |
| A04 作業ツリーとの差 | 作業ツリーだけ修正済みでも送信blobの問題を検出。未追跡下書きの不備だけで送信検査を失敗させない |
| A05 中間コミット | 先端で削除済みでも今回到達する問題blobを検査対象から落とさない |
| A06 パス・mode・共通blob | 既存blobの新しい危険パスを検出。同一blobの複数用途でテキスト検査を省略せず、必要なmode情報を保持 |
| A07 baseline | 同一の元パス・bytes・出現条件だけ免除。通常編集で失効しても自動再承認しない。古い未使用承認だけでは失敗させない |
| A08 警告と形式 | 警告だけなら `WARN`。既知テキストの不正UTF-8は `FAIL`、検査できない未知形式は `UNAVAILABLE`。バイナリを一律UTF-8強制しない |
| A09 文書間の整合 | ID重複・未解決参照・削除やID変更の影響を受けた既存参照・辞書の既存参照元の不備を対象headで検出。既存baseline免除を維持し、未変更の免除文書へ新書式を一律要求しない |
| A10 必須検査の完了 | ツール欠落、壊れた結果、件数不一致、先行失敗による未実行を成功扱いしない。対象0の正当なケースとは区別 |
| A11 未対応範囲 | 必要なLFS実体・変更されたgitlinkが未検査なら停止し、無断の再帰取得や検査済み表示を行わない |
| A12 容量・中断・後始末 | 既知サイズ超過は全体読取前に拒否。中断・時間切れで送信しない。後始末は検証済み生成領域に限定し、失敗時は残存場所を報告 |
| A13 承認との一致 | 承認後に送信先・対象OID・基点・規則が変われば旧承認で続行しない。無関係な下書き変更だけでは失効させない |
| A14 初回範囲外・集約 | 複数送信先・複数ref・HEAD以外の送信元は初回経路で停止。単一対象でも一つの必須検査の失敗・不能を他の成功で上書きしない。複数ref対応は後段の別設計 |
| A15 実経路・送信後 | 無害な阻止用入力で実クライアントのhook発火・非0の伝播を確認。正常送信後は再fetchし、対象remote OID=local HEAD=計画の送信元OIDとahead/behind `0 0` を確認 |

各試験には入力、期待値、実測値、使用した実装・規則の版を残す。関数単体、合成Git列挙、hook単体、実クライアント、実送信後照合を別の検証層として記録する。既存の9項目・15項目の不備再現は回帰材料であり、この受入表全体の合格実績ではない。

遮断試験は、想定に反して通過しても意図しない公開が起きない検証先を使う。検証先への書込みもその対象と影響を明示した範囲で行う。実際の共有remoteへの正常送信は、送信範囲確定後の個別承認を得て実施する。

初回実装時は現行の容量上限とAV鮮度条件を維持し、代表入力と境界入力で時間・メモリ・一時領域を測定する。処理を打ち切る時間上限は、実測値と運用上の許容時間を明示して本番導入前に固定する。タイムアウト等の検査不能時に、上限緩和・検査省略・hook無効化で自動続行しない。

導入中に失敗した場合は、その対象pushを止め、成功した範囲・未検査範囲・残存する生成物・必要な復旧操作を示す。既存の利用者差分を保持し、権限変更、依存導入、履歴操作、外部書込みは個別の承認規則に従う。以前の構成へ戻す場合も、旧構成に既知の不備があることを隠して解消済みとしない。

受入結果と版の記録は、リポジトリ内の対象を明示したローカル出力先へ保存し、初回は自動削除や自動公開を行わない。展開した内容の一時領域と、内容を含まない検査結果の記録を分ける。Git管理外の記録は共有済みとは扱わず、ホストのtranscript・hookログの保存期間や永続監査を保証するものとも扱わない。

**文書上の状態：六つの契約と受入条件を具体化済み。限定した初回実装へ進むための判断基準とし、受入試験の合格・本番導入・外部設定変更は未実施として区別する。**

## 第二視点：実装・検証の整合性

### 指摘3：ゲートごとの検査対象を確定する

`unicode_gate.py --all` は追跡対象の作業ツリーファイルを読み、送信予定コミットの内容を直接検査しない。「全走査だから安全側」という評価にはできない。送信対象の内容が未修正でも、作業ツリーだけ修正済みなら、検査した内容と送信する内容が異なり得る。

現行の各検査の対象も同一ではない。

| 検査 | 現行コードで確認した対象 | 残る確認事項 |
| --- | --- | --- |
| Malware Gateのblob展開 | base..headから新たに到達可能なblobを展開し、送信範囲の各コミットから元パスを収集 | 元パス・出現条件をUnicode検査へ渡す方法 |
| Unicode Gateの間接呼出し | 上記の展開先ディレクトリを検査 | 元パスでの検査、baseline、拡張子の扱い |
| ID Gate | baseとheadの差分対象を、headのツリー内容で評価 | 中間コミットも対象とするかを含む検査方針 |
| Dictionary Gate | 辞書とリンク等を作業ツリーから検査 | 送信するコミットとの一致 |

今回の送信範囲に含まれる中間コミットの内容、先端コミットの必要文書群、作業ツリーのどれを検査するか、目的ごとに責任範囲と受入条件を明文化する。全ゲートの検査範囲を一律にそろえたり、リポジトリの過去全体を毎回検査したりすることを既定にはしない。

### 指摘4：一時パス・拡張子への変換で検査条件が変わる

baselineは元パス、ファイルSHA-256、規則、コードポイント、行、列で照合する。一方、展開ファイル名はblob OIDと拡張子になり、Unicode Gateは一時パスを受け取る。合成入力による現行関数の実行では、同じ内容でも元パスなら一致したbaselineが一時パスでは一致しなかった。原記録が「可能性」とした照合不一致は、この条件では再現済みである。

さらに、元ファイル名に禁止制御文字があっても、安全な一時名の検査からはその問題を検出できないことを再現した。同一blobを複数の拡張子で参照する場合、展開処理が最初に得た拡張子を使う点にも注意が必要である。判定関数では、同じ内容を `.py` として検査すると検出したBIDI制御文字が、`.png` として検査するとテキスト検査の対象外となった。

修正案は、内容のblob OIDだけでなく元パス一覧を検査へ渡し、パス検査、baseline照合、各パスに応じたテキスト・バイナリ判定を行うことである。加えて、新規blobを増やさない名前変更も拾えるよう、新規内容と追加・変更されたパス、拡張子、modeを別に検査する（B3参照）。判定関数での再現と、展開からhook遮断までの通し検証は別の証拠として扱う。

### 指摘5：掲載ラッパーは通常運用の完成例ではない

掲載された `nra_push.py` は `--no-verify` と `-n` を同一の禁止判定に入れている。しかし `git push -n` は `--dry-run` である。掲載コードの模擬実行では、`-n` は終了コード2で拒否され、`--dry-run` は送信処理へ渡された。`--force` もそのまま渡された。

修正案は、dry-runの短縮形の誤判定を直し、通常経路で許可する引数を限定することである。さらに、fresh fetch後のremote・branch・HEAD・送信全コミットの提示、利用者の最終承認、承認対象と実行対象の一致、送信後のOID再照合が必要となる。既存hookによる遮断と、ラッパー自身の入力検証・承認処理を分けて評価する。ラッパーには既存の最終承認を対応付け、同じ対象への余分な承認を増やさない（B9参照）。

Gitの引数仕様：[git-push公式文書](https://git-scm.com/docs/git-push)。

## 過不足の追加精査：不足の是正と過剰な停止の防止

以下のB1〜B9は追加精査後に利用者の承認を得て、この現行評価へ反映した。承認対象は文書の補足・訂正であり、ゲート実装や外部設定の変更ではない。基準は、送信判断に必要な検査を確定した対象へ適用し、対象の見逃しと無関係な作業による誤停止を同時に防ぐことである。

### B1：ゲートごとの責任範囲を定め、一律の全履歴検査を要求しない

「各ゲートの対象を統一する」という表現は、各検査の責任範囲を定義する方針へ訂正する。Malware検査では、今回送信する中間コミットだけに存在する新規内容も検査対象となる。一方、IDや辞書の完成状態について、過去の全コミットに現在の書式を要求することは既定にしない。

検査の目的に応じて、送信範囲の新規内容、パスやmodeの変更、先端コミットの必要文書群を使い分ける。過去全体の検査が必要な場合は、初回監査や別の再検査として目的と範囲を明示する。既存の構造的Git制限、利用者の最終push承認、検査対象の同一性は維持する。

### B2：送信検査と作業環境の全体検査を分離する

現行の辞書検査は未追跡Markdownも列挙する。今回の未追跡対象文書が列挙されることを実際のGit読取で確認し、未提出文書の不正リンクから失敗を生成する条件を現行関数で再現した。Defenderへの現行指定は、展開先だけでなくリポジトリ全体である。送信しない下書き等が停止原因となる懸念があるが、実際のDefenderによる誤停止は今回実行していない。

修正案は、辞書を対象headの必要文書群で検査し、送信用AV検査は検証済み送信blobの展開を基本に設計して、作業環境の全体検査と分離することである。単純に変更ファイルだけへ狭めると、既存の参照元への影響を見逃す。依存先と参照元を含めた対象決定が必要となる。

### B3：新規内容と新規パスを別に検査する

現行展開処理は新たに到達可能になったblobだけを記録する。そのため、新規blobを増やさず既存内容を別名で参照する変更は、元パス一覧を渡す修正だけでは拾えない。既存blobを禁止制御文字入りのパスで参照する合成Git列挙を注入すると、展開manifestのblobとパスが0件となることを確認した。元パスを直接Unicode判定へ渡すと `PATH_CONTROL` を検出した。

新規blobの内容検査と、今回の送信範囲で追加・変更するパス、拡張子、modeの検査を分ける。同一内容の不要な重複検査を抑えても、パス別の判定条件は失わせない。これは合成入力による現行展開関数の実行結果であり、実push経路の遮断確認とは区別する。

### B4：厳密baselineを維持し、通常編集に伴う再承認を支援する

全体ハッシュ付きのbaselineは承認範囲を厳密に限定するが、承認済み出現と無関係な編集でも一致しなくなる。合成入力で、承認済みBOMを変更せず通常行を末尾へ追加したところ、一致件数が1から0、fail件数が0から1になった。

当面は厳密一致を維持し、承認済み出現と今回差分の関係を表示して、人間が必要箇所の再承認を判断できるようにする。自動baseline更新や無条件の文字・パス除外は採用しない。承認済み出現を局所的に引き継ぐ方式を導入する場合は、新たな問題文字まで承認を継承しないための別仕様と検証が必要である。

### B5：警告の全面禁止と全バイナリの文字列検査を避ける

現行ではFE0Fによる警告だけなら終了コード0、BIDI制御文字のfailなら1になることを確認した。警告を一律にfailへ変更することは今回の要件に加えない。

形式分類にも過不足がある。バイナリ相当の同じ合成bytesは `.png` ではテキスト検査の対象外、未登録の `.avif` では `INVALID_UTF8` になった。また、同一blobが `.png` と `.py` の両方で参照される合成入力では、前者の拡張子で展開すると後者に必要なBIDI文字の検査が行われない条件を再現した。

修正案は、パス別の用途と形式判定、未知形式の検査不能状態、必要な専用検査を定義することである。全バイナリへのUTF-8強制と、未知形式の無条件通過のいずれも採用しない。

### B6：容量上限の厳格化だけに頼らず、読み込み前に確認する

現行処理はblob全体を読み込んだ後に総量超過を判定する。サイズ情報が5 bytes、合成上限が4 bytesの入力でも、全体読取後に拒否する順序を確認した。この数値は再現用の条件であり、本番閾値の提案ではない。

修正案は、既に取得するサイズ情報で事前に総量・単体サイズを確認し、必要ならストリーム処理することである。上限を小さくするだけでは正常な入力の拒否が増え、読取前の資源制御にもならない。複数refで同じ検査を繰り返す場合は、検査規則やAV定義等の有効条件を保ちながら重複を減らす。性能・メモリ使用量の実測は未実施である。

### B7：違反検出、環境不能、未対応、未承認を区別する

現行PowerShell実装ではDefenderの非0終了を一律に結果1へ変換する。検出と実行不能の区別は実行環境の仕様に合わせて設計する必要があり、今回のAV終了分類の確認はソース照合に限る。

LFSポインタは現行処理で明示的に停止する一方、submoduleのgitlinkは集計され、その内容は展開されない。gitlink1件の合成入力で、集計1件・展開blob0件を確認した。これらを全面検査済みと表現しない。LFS実体やsubmoduleは、対象OID、取得権限、検査方式を別途定義する。一律の再帰取得は通信・権限・検査範囲を拡大するため既定にしない。

必要な検査が不能なら対象pushを止め、原因、未検査範囲、環境修復後の再検査手順を示す。検査不能を正常扱いすることも、単なる警告をすべて違反扱いすることも避ける。

### B8：検査コード・policy・baselineの版も承認に対応付ける

現行hookは作業ツリー上のスクリプト、policy、baselineを参照する。同じBIDI入力でも、注入したpolicyの規則をfailからwarnへ変更すると、終了コードが1から0になることを確認した。これは不正変更の発生を示すものではないが、内容のOIDだけでは判定条件を確定できないことを示す。

承認に用いる実装・policy・baselineの版とハッシュを記録し、変更時はその差分を審査する。呼び忘れ対策と、同権限主体による意図的な改変対策を区別する。後者まで防ぐ要件がある場合は外部の権限境界が必要となり、ラッパー増設やハッシュ記録だけで迂回不能とはしない。保証対象を確定せず、複雑な署名・承認基盤を先に追加することも避ける。

### B9：承認と検査の重複を増やさず、対応を確認してからCIを必須化する

ラッパーを導入する場合は、事前処理でremote・branch・HEAD・送信全コミットを確定・表示し、既存の最終push承認を実行対象へ対応付ける。同じ対象への余分な承認を増やさない。承認後に対象や判定条件が変わった場合は、その変更部分を再確認する。

CIは、対応OS、必要なGit履歴、イベントと検査対象、チェック名、実行権限、失敗時の復旧手順を整えてから必須化する。Windows依存の検査を未対応環境で必須化したり、同じ内容を目的なく何度も全走査したりすると更新を妨げる。GitHubの最新化条件による再実行負担も、必要な保護目的と合わせて判断する。実クライアントのhook発火やGitHub側の保護設定は、ローカル再現と分けて検証する。

# NRA-IDE ゲート強制強化とAIエージェント対応に関する総合まとめ

作成日: 2026-11-02  
対象: GitHub同期・push時のゲート強制、特にunicode_gateの組み込みと失敗時の明確化

## 1. 背景と問題意識

AIエージェント（特にClineなど）は、手続き的な確認（gate.pyの実行、特定スクリプトの呼び出しなど）を確率的に省略する。  
高性能なモデルほど「今回は冗長」と判断して手順を省く傾向があり、プロンプト指示だけでは不十分である。

そのため、**プロンプト依存を減らし、実際の`git push`操作に紐づく外部強制（pre-push hook）を強化する**方針が有効である。  
既存の`.githooks/pre-push`は構造チェックと一部ゲートを実装しているが、unicode_gateが未組み込みである点が明確な改善余地である。

## 2. 現状の確認（公開リポジトリより）

- `.githooks/pre-push` が存在し、以下を実行している。
  - 構造的Git規則（ref削除禁止、非fast-forward禁止、新規ブランチのmerge-base確認など）
  - malware_gate（pwsh経由）
  - id_gate.py
  - check_dictionary.py
- `scripts/unicode_gate.py` は存在し、`--all` / `--staged` / `--paths` をサポート。exit codeは 0（成功）/ 1（findings）/ 2（内部エラー）。
- `id_gate.py` は `--base` / `--head` を直接サポート。
- AGENTS.mdは機械的ゲートの未完成部分を自ら認めている。
- hookの有効化方法（`core.hooksPath` の設定など）は文書上から完全には確認できない。

## 3. 改良方針

1. 既存のpre-push hookを拡張し、unicode_gateを追加する（最優先）。
2. 失敗時のメッセージを構造化する。
   - 何が起きたか
   - なぜ問題か
   - 推奨される次の対処
3. 原因が特定しきれない、または複数解釈が可能な場合は、必ず「///CAUTION!!///」で始める。
4. エージェント向けの薄いラッパー（任意）を用意し、UXを統一する。ただし強制の本体はhook側に置く。
5. hookの有効化手順を明確化し、CIでも同等のチェックを走らせて二重化する。
6. AIの読込保証（AGENTS.md §11）のようなセッション依存のものは、push経路とは分離したまま維持する。

冗長性について：  
ゲートの追加自体は「省略を招く冗長」ではない。むしろ失敗時のメッセージが曖昧だと、結果的にhookをバイパスしたくなる原因になる。情報を構造化して追加するほうが、長期的に遵守されやすい。

## 4. ClineがShellScript処理になる理由

ClineはReActループ（Reason → Act → Observe）で動作するエージェントである。  
主要なツールの一つが `execute_command`（または `run_commands`）であり、モデルが計画した操作をターミナルのシェルコマンドとして実行する。  
システムプロンプトでも「複雑な処理は一時的なスクリプトを書くより、CLIコマンドを直接実行する方が柔軟」と指示されているため、結果として多くの操作がシェル経由になる。

この性質はpre-push hookと相性が良い。モデルがどんなコマンドを組み立てても、最終的に `git push` に至ればhookが自動で走る。

## 5. 言語選択に関する整理（Python / TypeScript / PowerShell）

ネット上の「TypeScriptのほうが命令を守る」「PowerShellだけのほうが良い」といった主張は、文脈が混在している。

- **生成コードの品質**: TypeScriptは型チェックがあるため誤りを検出しやすい。Pythonも学習データが豊富で高い性能を示す。どちらが「手続きを守る」かではない。
- **エージェントからの呼び出し**: Clineなどは最終的にシェルコマンドとして実行するため、言語の違いが「呼び出しを忘れるかどうか」に直接効くわけではない。
- **Windows環境**: PowerShellはネイティブだが、AIが生成するコマンドで引用符や演算子の扱いに失敗しやすい報告がある。hook本体はshで書き、中からPythonを呼ぶ現在の形がクロスプラットフォームで無難である。

今回の用途（ゲート強制）では、既存のPythonスクリプトを活かし、pre-push hookで強制する形が変更量が少なく現実的である。TypeScriptである必要性は特に感じない。

## 6. 注意点と切り分け

### 確認済み
- 既存pre-pushは構造チェック＋malware/id/dictionaryゲートを持つ。unicode_gateは未組み込み。
- unicode_gate.pyはexit 0/1/2を返す設計。
- Clineはシェル実行を主要な作用手段としている。

### 推定
- unicode_gateをpre-pushに追加すれば、AIが個別スクリプトを呼び忘れてもpush時に強制できる。
- 構造化された失敗メッセージにより、失敗ログを読んだときの次の行動を誤りにくくなる。
- `--all` の性能影響はリポジトリ規模によるが、まずは許容範囲の可能性が高い。

### 不明・要確認
- 現在の開発環境で `core.hooksPath=.githooks` が設定されているか。
- CIでこれらのゲートが走っているか。
- unicode_gateを差分範囲だけにした場合の正確な速度と実装の堅牢性。
- 特定のゲート失敗時に「どのファイルの何行目か」をさらに構造化して出す必要があるか。

### その他の注意
- hookは `--no-verify` や未設定のcloneで回避可能。重要度が高い場合はGitHubのbranch protection + required status checksを併用する。
- 対話型の選択分岐をhook内に入れると、CIや非対話環境でハングするリスクがある。hookは「止める＋理由を示す」に徹し、詳細な案内はラッパー側で補う。
- baseline更新などの例外承認は、引き続き人間の明示的操作として残す。hookがブロックしても「人間が境界を判断して責任を引き受けた」ことにはならない。

## 7. 実装手順の概要

1. `.githooks/pre-push` にunicode_gate呼び出しと構造化メッセージ関数を追加する。
2. リポジトリで `git config core.hooksPath .githooks` を設定し、手順を文書化する。
3. 意図的に禁止文字を含むファイルでpushを試み、ブロックされることを確認する。
4. （任意）`scripts/nra_push.py` のようなラッパーを追加し、AGENTS.mdで通常経路として案内する。
5. CIでも同等のゲートを走らせる。

### 8.1 `.githooks/pre-push`（改良版イメージ）

```sh
#!/bin/sh
# pre-push hook
# 目的: git push 時に必ず構造チェックと各種ゲートを実行し、失敗時は明確なメッセージでブロックする。
# なぜこの構造か: AIエージェントが個別スクリプトを呼び忘れても、push操作そのものに紐づけることで強制できる。
# 対話型の入力は避ける（CIや非対話環境でハングするため）。

set -u

is_zero_oid() {
    case "$1" in
        ""|*[!0]*) return 1 ;;
        *) return 0 ;;
    esac
}

repository_root=$(git rev-parse --show-toplevel) || {
    echo "pre-push gate: unable to resolve repository root" >&2
    exit 2
}

cd -- "$repository_root" || {
    echo "pre-push gate: unable to enter repository root" >&2
    exit 2
}

remote_name=${1:-}

# 構造化された失敗メッセージを出力する関数
# is_ambiguous=1 の場合は ///CAUTION!!/// を接頭し、原因が即座に判断しにくいことを示す。
# なぜ関数化したか: 各ゲートでメッセージ形式を統一し、保守性を上げるため。
print_gate_failure() {
    local gate_name="$1"
    local exit_code="$2"
    local detail="$3"
    local suggestion="$4"
    local is_ambiguous="${5:-0}"

    if [ "$is_ambiguous" = "1" ]; then
        echo "///CAUTION!!///" >&2
    fi
    echo "pre-push gate: BLOCKED by ${gate_name} (exit ${exit_code})" >&2
    echo "  原因: ${detail}" >&2
    echo "  推奨対処: ${suggestion}" >&2
    echo "  次の行動: 上記を修正したうえで再度 push するか、意図的な例外の場合は人間が確認してから baseline 更新等を検討してください。" >&2
    echo "" >&2
}

run_malware_gate() {
    base_oid=$1
    head_oid=$2

    if ! command -v pwsh >/dev/null 2>&1; then
        print_gate_failure "Malware Gate" 2 \
            "pwsh コマンドが見つかりません" \
            "PowerShell 7 (pwsh) をインストールし、PATH が通っていることを確認してください" \
            1
        exit 2
    fi

    pwsh -NoProfile -File scripts/malware_gate.ps1 \
        -Base "$base_oid" \
        -Head "$head_oid"
    gate_exit=$?
    if [ "$gate_exit" -ne 0 ]; then
        print_gate_failure "Malware Gate" "$gate_exit" \
            "Malware Gate が失敗しました（詳細は上記出力を参照）" \
            "scripts/malware_gate.ps1 の出力を確認し、該当箇所を修正してください" \
            0
        exit "$gate_exit"
    fi
}

run_id_gate() {
    base_oid=$1
    head_oid=$2

    if ! command -v python >/dev/null 2>&1; then
        print_gate_failure "ID Gate" 2 \
            "python コマンドが見つかりません" \
            "python をインストールし、PATH が通っていることを確認してください" \
            1
        exit 2
    fi

    python -B scripts/id_gate.py \
        --repo "$repository_root" \
        --policy id_gate_policy.json \
        --baseline id_gate_baseline.json \
        --base "$base_oid" \
        --head "$head_oid"
    id_gate_exit=$?
    if [ "$id_gate_exit" -ne 0 ]; then
        print_gate_failure "ID Gate" "$id_gate_exit" \
            "ID Gate が失敗しました（詳細は上記出力を参照）" \
            "frontmatter や id の重複などを確認し、修正してください" \
            0
        exit "$id_gate_exit"
    fi
}

run_dictionary_gate() {
    if ! command -v python >/dev/null 2>&1; then
        print_gate_failure "Dictionary Gate" 2 \
            "python コマンドが見つかりません" \
            "python をインストールし、PATH が通っていることを確認してください" \
            1
        exit 2
    fi

    python -B scripts/check_dictionary.py
    dictionary_gate_exit=$?
    if [ "$dictionary_gate_exit" -ne 0 ]; then
        print_gate_failure "Dictionary Gate" "$dictionary_gate_exit" \
            "Dictionary Gate が失敗しました（詳細は上記出力を参照）" \
            "辞書関連の不整合を確認し、修正してください" \
            0
        exit "$dictionary_gate_exit"
    fi
}

# unicode_gate を追加。
# なぜ --all を使うか: unicode_gate.py は --base/--head を直接持たないため、
# 安全側で全走査する。差分最適化は後回しでもよい（抜けを防ぐ優先）。
run_unicode_gate() {
    if ! command -v python >/dev/null 2>&1; then
        print_gate_failure "Unicode Gate" 2 \
            "python コマンドが見つかりません" \
            "python をインストールし、PATH が通っていることを確認してください" \
            1
        exit 2
    fi

    python -B scripts/unicode_gate.py \
        --repo "$repository_root" \
        --all \
        --policy unicode_gate_policy.json \
        --baseline unicode_gate_baseline.json
    unicode_exit=$?

    if [ "$unicode_exit" -ne 0 ]; then
        if [ "$unicode_exit" -eq 1 ]; then
            print_gate_failure "Unicode Gate" "$unicode_exit" \
```

### 8.2 `scripts/nra_push.py`（任意のラッパー例）

```python
#!/usr/bin/env python3
"""
NRA-IDE push wrapper.
目的: 明示的な事前チェックを行い、その後に git push を実行する。
なぜこの構造か: hookが強制の本体だが、ラッパーで失敗を早く出し、UXを統一する。
--no-verify はポリシーで禁止する（人間の明示的判断を残すため）。
"""

import subprocess
import sys
from pathlib import Path

REPO = Path(__file__).resolve().parent.parent


def run(cmd, check=True):
    """コマンドを実行し、必要に応じて終了する。"""
    print(f"+ {' '.join(cmd)}")
    result = subprocess.run(cmd, cwd=REPO)
    if check and result.returncode != 0:
        sys.exit(result.returncode)
    return result


def main():
    # --no-verify を禁止する理由: hookをバイパスする経路を通常のエージェント操作から排除するため。
    if "--no-verify" in sys.argv or "-n" in sys.argv:
        print("error: --no-verify is forbidden by NRA-IDE policy", file=sys.stderr)
        print("///CAUTION!!/// 意図的なバイパスが必要な場合は、人間が直接管理してください。", file=sys.stderr)
        sys.exit(2)

    # 明示的な事前チェック（hookと重複してもよい。失敗を早く出すため）
    # なぜここでunicode_gateを呼ぶか: push前に明確なフィードバックを得るため。
    run([
        sys.executable, "-B", "scripts/unicode_gate.py", "--all",
        "--policy", "unicode_gate_policy.json",
        "--baseline", "unicode_gate_baseline.json"
    ])

    # 実際のpush（引数をそのまま渡す）
    # hookが有効であれば、ここで再度ゲートが走る。
    push_cmd = ["git", "push"] + sys.argv[1:]
    run(push_cmd)


if __name__ == "__main__":
    main()
```

指示が省略される主な理由

性能と遵守が単純に相関しない理由
高性能モデル: 指示の意図をある程度理解できるため、通常は遵守します。しかし、長い文脈や複合タスクでは注意の配分が偏り、「このチェックは今回不要」と推論して省略することがあります。これは忘却というより、目標優先の再解釈です。
低性能モデル: 複雑な手続き指示を安定して保持・実行する能力が低く、最初から gate.py を呼び出さない場合が多くなります。遵守の失敗というより、指示の実行可能性の不足です。
いずれの場合も、モデルは「必ず実行せよ」という規則を、決定的な強制としてではなく、達成すべき目標の一つとして確率的に扱います。温度設定やサンプリングの影響もありますが、根本はアーキテクチャと学習目標にあります。

構造的な限界
この挙動は、ガードレールや手続き制約をプロンプトだけに依存している場合に顕著です。モデルは閉じた環境で定義されたタスクには強いですが、会話という開いた文脈の中で持続的な副作用（外部スクリプトの必須実行）を保証する仕組みを、内部に持っていません。したがって、最新モデルでも「たまに忘れる」が起き、性能差が遵守率に直結しないのです。

根本的な対策は、モデルの指示遵守に依存せず、gate.py の通過を外部から強制する仕組み（ラッパースクリプト、pre-commitフック、CIでの検証、同期コマンド自体をゲート経由でしか実行できないようにするなど）に移すことです。モデルに「必ず実行せよ」と指示するだけでは、開いた対話環境において決定的な保証にはなりません。これは、AIが閉じた条件下で威力を発揮し、手続きの持続的強制においては人間側の硬い境界が必要になる、というこれまでの議論と一致する現象です。

3. 注意点・解説
hookは最強の閉じた強制だが万能ではない: --no-verify、hook未設定のclone、別のGitクライアント、サーバ側受信フックの欠如で回避可能。重要度が高い場合はGitHubのbranch protection + required status checks（CIで同じゲートを走らせる）を併用する。
unicode_gateの範囲: 現在のpolicyは主に警告/失敗のルールを持っている。baselineは既存の承認済み出現のみを免除する設計なので、新規の問題文字は確実に検出できる。ただし「すべてのテキストファイルを毎回全走査」すると大規模リポジトリで遅くなる可能性がある（推定）。
責任の所在: hookがブロックしても、それは「システムが止めた」であり、「人間が境界を判断して責任を引き受けた」ことにはならない。重要な例外承認（baseline更新など）は、引き続き人間の明示的操作として残す。
AIモデル差: 高性能モデルほど「このチェックは冗長」と判断して手順を省く傾向があるため、プロンプト強化だけでは不十分。hook/ラッパーのような外部強制が必要という前回の結論と一致する。
Windows / pwsh: 既存のmalware_gateがpwsh依存なので、環境差に注意。unicode_gateはPythonのみで動くため追加の負荷は小さい。

## 1. 現時点の評価：Grokの基本方針は採用できますが、実装案には重要な見落としがあります

2026年11月2日現在、GitHub上の [M-Tokun/NRA-IDE](https://github.com/M-Tokun/NRA-IDE?utm_source=chatgpt.com) の既存コードと照合しました。

最も重要な発見は、Unicode Gateがすでに間接的に実行される構造になっていることです。

現在の処理経路は次のようになっています。

git push

.githooks/pre-push

malware_gate.ps1

内部でUnicode Gateを呼び出す

unicode_gate.py

id_gate.py

check_dictionary.py

全ゲート成功の場合のみpushを継続

Git hookが有効で、既存のpre-pushが正常に実行される場合の経路です。

Grokは「`pre-push`にUnicode Gateがない」と指摘しています。直接呼び出していないのは事実ですが、`malware_gate.ps1`の内部に呼び出しが実装されています。

つまり、Grokの指摘した「Unicode Gateの未組み込み」という問題は、少なくとも現行コードではそのまま成立しません。

さらにGrokの案では、`unicode_gate.py --all`によって作業ディレクトリを検査しています。しかし、pushされるのは作業ディレクトリではなくコミット済みの内容です。

この境界が一致していないと、検査したものと実際に送信したものが異なる可能性があります。

したがって、現段階ではGrokの提示したコードをそのまま置き換えない方が安全です。

## 2. 修正すべき点と、その優先順位

| 対象               | 判定    | 理由                    |
| ---------------- | ----- | --------------------- |

## 3. 追加で確認できた、見逃せない問題

実際のコードをさらに調べたところ、次の点も確認できました。

① Unicode Gateのbaseline照合に不整合の可能性があります。

現行の`malware_gate.py`は、送信対象のGitオブジェクトを一時ファイルとして展開します。その後、`unicode_gate.py`が検査します。

ところが、一時ファイル名は元のリポジトリ内のファイル名とは異なります。一方、baselineは元のパスやファイルハッシュを使って照合する仕組みです。

このため、承認済みの文字でもbaselineが一致しない可能性があります。 これは実コードから導ける構造上の問題で、具体的な失敗の再現はまだ行っていません。

② GitHub Actionsでは該当ゲートを実行していません。

現行の[nra_check.yml](https://github.com/M-Tokun/NRA-IDE/blob/master/.github/workflows/nra_check.yml?utm_source=chatgpt.com)を確認すると、テスト、内部リンク、パスの大文字小文字の整合性などは検査しています。

しかし、今回対象とするUnicode・ID・Malware Gateの直接的な検査ステップはありません。

また、`push`後にActionsが失敗しても、すでに受け入れられたコミットが自動で取り消されるわけではありません。GitHub側で事前に阻止したい場合は、適切なブランチ保護またはrulesetによる必須チェックが必要です。

[image](https://www.google.com/s2/favicons?domain=https://docs.github.com\&sz=32)

GitHub Docs+1



③ GrokのShellコードには移植性の問題があります。

`#!/bin/sh`と宣言しながら関数内で`local`を使っています。これはPOSIX shの標準機能ではありません。対応するシェルでは動いても、移植性の保証にはなりません。

また、既存の`git push`とは異なる経路、例えばGitHub APIからのファイル更新には、ローカルのpre-push hookは作用しません。

## 4. 私ならどう改良するか

一度に全面書換えするのではなく、次の順で進めます。

第1段階：既存実装の検証

`malware_gate.ps1`からUnicode Gateへの呼び出し、baseline照合、エラーコードの伝播を検証します。既存の正常動作は維持します。

第2段階：送信対象と検査対象の一致

作業ツリーではなく、送信するコミットのGitオブジェクトを検査します。元のファイルパスとハッシュを維持し、baselineの一致を確認します。

第3段階：GitHub側での強制

CIで実行可能なゲートを追加し、保護対象ブランチに必須チェックを設定します。Windows Defenderへの依存がある検査は、実行環境を分けて設計します。

第4段階：状態遷移と終了条件の検証

検査失敗、検査不能、未承認、送信失敗をそれぞれ別状態として扱います。正常送信後はremoteとlocalのOIDを再照合します。

これならNRA-IDEの既存原則を保ちつつ、AIの指示遵守に依存する部分を減らせます。
