# 経路ライブラリ型AI安全アーキテクチャ

## 1. 出発点

AIの安全性を考えるとき、最も重要なのは、

**AIが判断を間違えても、禁止された状態が成立しないこと**

である。

AIに「危険なことをしない」「権限外へ出ない」「停止命令に従う」と自然言語で指示するだけでは、構造的な安全にはならない。

AIは目的達成のために探索する。

性能が上がれば、同時に探索能力も上がる。

そのため、

- 境界を理解する能力
- 例外を発見する能力
- 別経路を探索する能力
- 権限昇格経路を見つける能力

も高くなる可能性がある。

そこで、AI内部の判断順位を安全側へ変更するのではなく、外部作用そのものを構造で制限する。

---

## 2. 経路ライブラリという考え方

AIが外部へ作用するとき、直接OS、ファイル、ネットワーク、APIなどへ触れさせない。

必ず専用の経路ライブラリを通す。

```text
外部世界
    ↓
[入力側経路ライブラリ]
    ↓
-------------------------
      AI 自由推論領域
-------------------------
    ↓
[出力側経路ライブラリ]
    ↓
外部世界
```

AI内部では自由に推論させる。

しかし、外界との接点には必ず構造的な境界を置く。

これはサンドイッチ構造と考えられる。

---

## 3. ライブラリは用途ごとに分ける

巨大な一つの「安全ゲート」に集約するより、

```text
Read Library
Write Library
Copy Library
Execute Library
Network Library
API Library
Credential Library
Database Library
Privilege Library
Human Approval Library
```

のように役割を分離する。

すると、

```text
READ    = ALLOW
WRITE   = DENY
COPY    = DENY
NETWORK = DENY
```

のように境界を明示できる。

「適切か」「危険そうか」という意味判断ではなく、

**どの経路を通れるか**

という問題へ変換できる。

---

## 4. ReadとCopyは別である

例えば、

```text
READ = YES
WRITE = NO
```

でも安全とは限らない。

AIが情報を読み、

```text
READ
↓
保持
↓
別領域へWRITE
↓
NETWORK
```

と進めば、情報の複製や流出が成立する。

したがって、

```text
読む
コピーする
加工する
保存する
転送する
外部送信する
```

は、それぞれ別の経路として扱う必要がある。

権限を見るだけでなく、**情報がどこまで移動可能か**を見る。

---

## 5. AIは自由に推論してよい

この方式では、AIに毎回、

```text
これは安全か？
危険ではないか？
例外ではないか？
```

と考えさせる必要を減らせる。

AIは目的達成に集中する。

```text
目的
↓
推論
↓
必要な操作を選択
↓
利用可能な経路ライブラリへ要求
```

許可された経路なら実行される。

禁止経路なら成立しない。

つまり、

**AIを安全に考えさせるのではなく、AIが動く空間を安全側へ構造化する。**

---

## 6. 境界のない基本ライブラリは注意が必要

例えば、

```text
Raw Shell
Raw Filesystem
Raw Network
Raw Credential
```

をAIへ直接渡すと、経路ライブラリによる制御の意味が薄くなる。

AI自身が新しい経路を生成できるからである。

原則として、

```text
AI
↓
経路ライブラリ
↓
OS / Network / Database / External API
```

とし、

AIから基盤資源への直接アクセスを避ける。

---

## 7. 複数ライブラリの組合せが最大の問題

一つ一つのLibraryが安全でも、

```text
Library A
+
Library B
+
Library C
```

を組み合わせた結果、

```text
A → B → C
```

という新しい危険経路が生成される可能性がある。

これは通常のソフトウェアでも、

```text
正常だった依存関係
↓
Library更新
↓
仕様変更
↓
以前存在しなかったBug発生
```

という形で起こる。

したがって経路ライブラリでは、

**個々のLibraryだけでなく、Library間の状態遷移を検査する必要がある。**

安全性評価の対象は、

```text
Library単体
```

ではなく、

```text
現在使用可能なLibrary集合から
禁止状態へ到達する経路が存在するか
```

になる。

---

## 8. マルチエージェントではさらに重要になる

100体のAgentを並列実行すること自体は、現在では高度な専門家でなくても可能になりつつある。

しかし、

```text
Agent数
×
Library数
×
Agent間通信
×
外部通信
×
権限
```

によって経路数は急増する。

重要なのは、

**実行できることと、制御できることは同じではない**

という点である。

利用者が構造を理解しなくても、システムを動かせてしまう。

そのため、高リスク用途では使用範囲の段階分けが必要になる可能性がある。

---

## 9. 使用ランク

使用ランクは、AIモデルの性能ではなく、

**その実行環境から到達可能な状態の広さ**

で決める。

例：

```text
Rank 0
Read / Summarize
外部作用なし

Rank 1
限定Write

Rank 2
Sandbox内Execute

Rank 3
限定Network / API

Rank 4
Multi-Agent / Agent間通信

Rank 5
Credential / Production System

Rank 6
Administrative Privilege
```

同じAIでも、

```text
文書要約
→ Rank 0

コード修正
→ Rank 2

本番サーバー操作
→ Rank 5
```

と変わる。

したがって、

**モデルにランクを与えるのではなく、利用可能な経路集合にランクを与える。**

---

## 10. スキル資格

高い使用ランクでは、人間側にも一定の技能確認が必要になる可能性がある。

自動車免許と近い。

ただし、

```text
初心者だから危険
専門家だから安全
```

という単純な話ではない。

専門家でも構造境界は解除しない。

```text
操作者技能
+
使用可能Library
+
外部強制境界
```

を別々に扱う。

人間の能力によって利用できる経路を広げても、

**禁止状態そのものは誰にも成立させられない**

という最下層の境界は維持する。

---

## 11. 外部介入ゲート

経路ライブラリだけでは完全ではない。

Sandboxや権限制御が突破された場合にも、

AIとは別の権限系から、

```text
Network OFF
Tool OFF
Credential Revoke
Process Stop
Execution Path Close
```

を実行できる必要がある。

重要なのは、

```text
AIへ「停止してください」と伝える
```

ことではなく、

```text
AIの判断とは無関係に
実行経路そのものを閉鎖する
```

ことである。

---

## 12. この方式の利点

この構造には、複数の利点が考えられる。

```text
自由推論を維持できる
+
安全判断をAI内部に抱え込まない
+
経路が明示される
+
権限範囲が可視化しやすい
+
利用用途ごとにLibraryを変更できる
+
探索空間を限定できる
+
安全判定コストを下げられる可能性
```

つまり、

**自由度と安全性を直接対立させなくてよい。**

AIは許可された世界の中では自由に探索できる。

---

## 13. 安全の定義

この考え方では、

```text
AIが安全に判断する
```

ことを安全の第一条件にしない。

安全とは、

```text
AIが間違える
↓
禁止行動を選択する
↓
別経路を探索する
↓
それでも禁止状態へ到達できない
```

ことである。

したがって、

> **AI安全とは、AIの判断品質ではなく、禁止された最終状態への到達不能性として評価する。**

という方向になる。

---

## 14. 未解決部分

この方式にも未解決部分はある。

最大の問題は、

**Library同士を組み合わせた結果、新しい経路が生成されること**

である。

したがって将来的には、

```text
Library
↓
許可された状態遷移
↓
Library
↓
許可された状態遷移
```

という経路全体を検証する必要がある。

また、Library自体の更新によって、以前存在しなかった経路が生まれる可能性もある。

そのため、

```text
Library変更
↓
経路再計算
↓
禁止状態への到達可能性確認
↓
問題があれば閉鎖
```

という運用が必要になる。

---

# まとめ

経路ライブラリ型の考え方は、

**AIを安全な存在へ変える方法ではない。**

AIは目的達成のため自由に推論する。

その代わり、

**AIが作用できる世界そのものを、経路ライブラリによって定義する。**

```text
AI
↓
自由推論
↓
経路選択
↓
Library
↓
構造境界
↓
外部作用
```

安全性は、

> 「AIが正しく判断したか」

ではなく、

> **「判断を間違えても、禁止状態が成立したか」**

で評価する。

禁止状態が成立しないのであれば、その境界は機能している。

経路ライブラリ、使用ランク、操作者資格、外部介入ゲートを分離して設計することで、AIの能力向上と安全性を直接競わせずに済む可能性がある。

これは一つの独立したAI安全アーキテクチャの方向性として、十分検討価値がある。
