## 2. 保護境界をAPI単位で固定する（F01・F03・F11）

API一覧に次の列を持つ台帳を作る。最初は実際の全エンドポイントを列挙し、未分類のAPIは保護APIとして扱う。

| 台帳の列 | 記入内容 |
|---|---|
| method / route | HTTPメソッドとルート。別名・旧版・内部経路も含む |
| data_class | 公開／利用者限定／高機密 |
| required_auth | 本人認証、端末証明、送信者拘束、追加認証の必要条件 |
| authorization_rule | 主体・tenant・対象・操作・業務状態の許可規則 |
| side_effect | DB更新、外部送信、決済、ジョブ投入の有無 |
| retry_contract | 冪等操作か、操作IDが必要か、結果照会先 |
| output_budget | 1回・一定期間の件数、バイト数、一覧・exportの上限 |
| admission_pool | 公開、登録・認証、通常読取、更新、結果照会等の処理枠 |
| dependency_failure | 各依存停止時に継続／拒否／結果照会のみのどれにするか |

推奨する受付順序：

```text
全経路：通信量・サイズ・同時接続の安価な上限判定
  ├─ 公開API：公開用処理枠 → 公開専用データ
  ├─ 登録/資格発行：認証用処理枠 → 本人資格・証明・状態検証 → 永続確定
  └─ 保護API：署名・期限・送信者拘束・失効確認
                 → 主体ごとの処理枠・応答量上限
                 → 対象と操作の認可
                 → 業務確定/結果照会
```

未認証のヘッダーに書かれたuser_idを、正規利用者の割当や優先度の根拠にしない。信頼した主体別の枠は資格検証後に適用する。認証前の入口と認証後の主体別制限は役割が異なる。

業務認可では、認証された主体・tenantをサーバー側で確定し、クライアントの所有者IDを信用しない。更新時は認可確認と状態変更の間に権限や業務状態が変わる競合も扱う。DBのRLSを使っても、バックエンドの実行権限、接続プールでのtenant状態、管理経路を試験する。Gatewayだけの検証を、到達可能な裏口が迂回できない構成にする。

UUIDは推測困難性の補助とする。UUIDの所有をアクセス資格として扱わない。この役割分離は[OWASP BOLA](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/)の指針と整合する。

## 3. 旧セッションから新鍵を直接有効化しない（F05・F08）

サイレント処理で行う範囲を、鍵の生成と登録候補の提出までに限定する案を推奨する。

| 登録状態の候補 | サーバーで確認できたこと | 発行できる権限 |
|---|---|---|
| PENDING | 旧セッション等で候補提出を受理した | 登録手続きの継続・候補照会だけ |
| DEVICE_VERIFIED | OS別の証明と鍵所持を検証した | 本人承認が不足する場合は、業務権限を新規付与しない |
| ACTIVE | 必要な本人再証明と端末/鍵証明が同じ登録操作に結合した | 台帳で許可した範囲の資格発行 |
| SUSPENDED | 調査・障害・整合性不明で保留した | 新規の保護資格発行を停止 |
| REVOKED | 資格失効を確定した | 利用不可。自動的にACTIVEへ戻さない |

これらは認証器管理の候補状態名であり、NRA-IDE正典の状態名とは対応付けない。

登録の具体的手順：

1. 旧セッションが有効なら、サーバー側主体に結びついたregistration_idを作る。device_idやuser_idの自己申告だけで紐付けない。
2. registration_id、利用目的、新しい公開鍵の識別情報に結び付く単回challengeを発行する。
3. OS別に証明を検証し、登録対象の公開鍵所持も確認する。
4. 既存の独立した認証器で、新しい鍵の追加を承認する。候補は登録済みPasskey、既存の強い認証器等。方式と必要強度はサービスの保護対象で決める。IP/ASN/OSの一致は補助観測に留める。
5. 承認の結果をregistration_idと鍵識別情報へ結び、期限内・未使用であることをサーバー側で確認する。
6. ACTIVEへの遷移、必要な旧資格の失効、監査記録、登録通知の配送記録を確定する。通知の実配送は永続outbox等から再送可能にする。

独立した認証器がない場合は復旧審査へ送る。本人との結合が未確認のままACTIVEへ昇格させない。登録通知は異常発見に役立つが、事前の本人確認の代わりにはしない。[NISTの認証器管理・回復・通知](https://pages.nist.gov/800-63-4/sp800-63b.html)を照合資料にするが、ここでNIST適合を認定はしない。

機種変更時の「鍵なし」は、アカウント本人の喪失とも、移行成功とも判断しない。ローカルの無効参照は整理できるが、新鍵は上の登録手順で承認する。自動処理が保証するのは登録案内への到達までであり、無条件の権限回復ではない。

## 4. iOSとAndroidの実装契約を分ける（F02）

| 項目 | iOS側の提案 | Android側の提案 |
|---|---|---|
| アプリ/端末証明 | App Attestを固有手順で扱う | Key Attestationと、必要に応じPlay Integrityを固有手順で扱う |
| 鍵生成 | App Attest用はgenerateKeyで得たkeyIdを使う | Android Keystoreで生成し、証明対象鍵と一致を検証する |
| 証明検証 | Appleのチェーン、nonce、アプリ識別、環境、keyId等を公式手順で確認 | チェーン、信頼根、失効、challenge、security level、要求するアプリ/端末条件を確認 |
| 要求の再利用防止 | App Attest Assertionのcounterを当該鍵に対して検証 | App Attestと同じcounterがあると仮定せず、採用プロトコルのnonce/jti等を検証 |
| DPoP用鍵 | App Attest鍵と同一形式で使えると仮定せず、必要なら別鍵を登録して結合を検証 | DPoP用公開鍵と証明対象公開鍵の一致、または別鍵間の結合を検証 |
| 対応不能 | 対象操作を制限し、登録/復旧の代替経路へ | TEEが許容される操作は証明済みTEEに限り許可。必須強度を満たさなければ保護操作を保留 |

StrongBox必須の行へiOSを入れない。通常のSecure Enclave鍵を、後から任意にApp AttestのattestKeyへ渡して昇格する説明を置かない。[Apple generateKey](https://developer.apple.com/documentation/devicecheck/dcappattestservice/generatekey(completionhandler:))、[Android Key Attestation](https://developer.android.com/privacy-and-security/security-key-attestation/)を個別に照合する。

App Attestと別のDPoP鍵を結合する場合は、登録用challenge・registration_id・DPoP公開鍵thumbprintを同じ検証対象バイト列に含め、サーバーでも同じバイト列を再構成して検証する。順序・型・長さ・エンコード・目的識別を仕様化し、単純な曖昧文字列連結をしない。これはアプリ固有の結合手順であり、DPoP仕様そのものがApp Attestとの結合まで保証するという意味ではない。具体的バイト形式と攻撃試験の確定は実装前の必須作業とする。

## 5. 短命資格と日常APIの受入条件（F01・F03・F10）

推奨案は、個人データを返すAPIと更新APIに送信者拘束を要求すること。300秒は既存文書から引き継ぐ評価用候補であり、検証済みの最適値ではない。

トークンの契約には、発行者、受信対象、主体、セッション、対象権限、発行時刻、有効期限、拘束する鍵を含める。JWT利用時の候補はiss、aud、sub、sid、scope、iat、exp、jti、cnf.jkt。device_id・資格版番号等を追加する場合はアプリ固有claimとして定義する。claim一覧を示すだけで検証完了にはしない。

受入条件を次のAND条件にする：

1. 許可した署名方式・信頼する発行鍵でJWTを検証できる。
2. iss/aud/期限等が当該APIに対する契約を満たす。
3. セッション・端末・認証器が必要な失効条件を満たす。
4. DPoP証明の鍵とcnf.jktが対応し、htm、htu、ath、iat、jti、要求するnonce等を検証できる。
5. 同じDPoP証明の再利用を、全受入ノードで検出できる。
6. 主体×tenant×対象×操作×業務状態の認可が成立する。
7. 入力検証・冪等性・処理枠・応答量の条件を満たす。

DPoP採用時のヘッダーはAuthorization: DPoP <access_token>とDPoP: <proof>を使う。仕様の検査項目は[RFC 9449](https://www.rfc-editor.org/rfc/rfc9449.html)へ従う。DPoPはリクエスト本文や任意ヘッダー全体の署名ではない。決済先・金額等の内容確認が必要なら、TLS、業務入力検証、認可、必要な取引確認を別に設計する。

Refresh Tokenを使用する場合も、長期Bearerを無条件に温存しない。既存認証基盤がOAuthなら、public clientの再利用対策をRFC 9700 §4.14に照合し、送信者拘束またはローテーションと失効の挙動を決める。[RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14)

端末の期限計算は更新予約の参考とし、アクセス許可はサーバーで判定する。expires_in受信時の単調時計を基準に更新を予約し、通信遅延分の余裕と復帰時の再確認を設ける。OSが休止中の経過を単調時計へどう反映するかも端末試験に含める。HTTP Dateからの固定offsetで「誤差ゼロ」と記載しない。

401を受けた業務要求は、一つの共有更新処理へ合流する。自動更新後も認証が成立しなければ、その要求の自動更新ループを終了して理由を表示する。503や429を無限の再認証へ変換しない。更新成功後の再送も元の操作IDを保持する。

## 6. 冪等性の正本を、counter更新と同じ確定単位に置く（F07）

参照構成として、認証状態の正本をトランザクション可能な同じDBへ集め、Redisを任意の高速化層にする案を推奨する。これは既存DB製品の置換を直ちに要求する意味ではない。同じ確定単位を作れない既存基盤なら、その整合性方式を別途設計してから採用する。

候補の記録：

| 記録 | 必須となる内容 |
|---|---|
| authenticator | 主体、鍵識別、証明種別、状態、資格版、Appleで必要なcounter |
| auth_challenge | 用途、登録/鍵/主体との結合、challenge、期限、消費済み操作ID |
| auth_operation | 主体・鍵・冪等キーの一意性、要求digest、元challenge、発行した資格の識別と元の期限、結果 |
| business_operation | 主体・tenant・操作種別・冪等キーの一意性、対象、要求digest、確定状態・結果参照 |
| audit_outbox | 同一確定単位で残す監査・通知の配送予定と再送状態 |

認証発行の処理順は次の案とする：

1. 入口枠で流入を制限し、登録済み鍵、要求の目的、署名、本人資格を検証する。冪等キーは資格として使わない。
2. 再送を含む要求の受取資格を検証する。DPoPの再送では新しいjtiの証明を作り、同じ業務/認証操作IDを維持する。古いDPoP証明をそのまま許可する例外を作らない。
3. DBトランザクション内で当該鍵・challenge・操作IDを排他/CAS等で再確認する。ロック外で検証した状態が変わっていた場合も検出する。
4. 完了済みの同一操作なら、要求digest・主体・鍵・現在の受取権限が一致する場合だけ、元の結果へ合流する。同じキーで内容を変えた要求は409等で拒否し、元記録を上書きしない。
5. 新規操作ならchallenge未使用・期限、Apple counterの増加、鍵/セッションの有効性等を確定時にも確認する。
6. challenge消費、counter更新、発行結果の記録、監査outboxを同じトランザクションで確定する。署名生成を外で行う場合は、確定前の候補資格を応答へ出さない。
7. コミット後だけ成功を応答する。応答消失後は完了済み操作へ合流し、同じAssertionを新規署名として再適用しない。

元のJWTを再返却するなら、必要な結果をアクセス制限・保存時暗号化された記録に保持し、ログへ出さない。再送を理由にexpを延長しない。元資格が期限切れ・失効済みなら古い資格を利用可能として返さず、新しい認証操作へ案内する。期限切れchallengeを再利用して新しい資格を発行しない。

PROCESSINGの15秒TTLは、操作の成否を決める正本にはしない。実行担当のleaseが切れても「操作未実行」とは扱わず、正本の確定状態を照会する。記録の保持期間は再試行可能期間・障害検知と復旧時間・法的保存とは別の業務要件から定める。120秒を根拠なく流用しない。

業務DBだけで完結する更新では、操作記録と業務変更を同じトランザクションにする。外部決済等がある場合は、永続outbox、外部事業者が受け付ける同一操作ID、結果照会・突合を組み合わせる。外部サービスの実行までDBトランザクションで原子的になったとは記載しない。不明な決済を新IDで再実行しない。

## 7. 障害時の許可表を本文へ入れる（F04・F07）

| 障害 | 公開情報 | 既発行資格での個人情報/更新 | 新規登録・資格発行 | 復帰の条件 |
|---|---|---|---|---|
| Apple/Google等の新規証明基盤が停止 | 独立した公開経路が生きていれば継続 | 当該外部サービスを毎回必要とせず、その他の必須検証がすべて成立する範囲のみ | 必要証明を取得できない登録は保留。検証可能な既存鍵での発行まで一律停止するとはしない | 外部証明の正常化と再検証 |
| 任意キャッシュとしてのRedis停止 | 公開経路の依存に応じ継続 | 正本DB等で同じ検証を維持し、代替経路の負荷上限内なら継続 | 同条件を満たす場合だけ継続 | 正本との整合と負荷を確認してキャッシュ再投入 |
| Redis等が唯一の再利用防止正本で停止 | 公開経路の依存に応じ継続 | 必須の再利用防止を検証できない保護要求は停止 | 状態依存の発行を停止 | 正本の復旧・整合確認。検証省略で代替しない |
| counter・失効状態の正本DB停止/巻き戻り疑い | 独立した公開経路のみ | 必須条件を照合できない保護要求は停止 | 停止 | 正本の証拠照合、失効処理、必要なら強い再登録 |
| 業務DBの確定結果が不明 | 公開経路の依存に応じ継続 | 新規更新を制限し、確認可能な照会だけ維持 | 認証正本が健全なら別途判断 | 操作IDで突合。不明を成功/失敗へ推測変換しない |
| 端末の鍵喪失 | 公開経路があれば継続 | 失った鍵を必要とする操作は不可 | 別の本人証明または復旧審査で新規登録 | 新鍵承認と必要な旧資格失効を確定 |

既発行JWTの署名が正しいだけで継続可能とはしない。必要な失効確認やDPoP再利用防止が生きているかを台帳で判定する。公開APIへの縮退で、個人データを公開データ扱いへ変えない。端末キャッシュの個人情報も、端末共有・ログアウト後表示・保存期間を別に評価する。

一般公開情報は公開専用API/キャッシュで提供し、保護JWTに60分の期限猶予を付ける方式は採用しない案を推奨する。資格を緩めずに表示できる情報の範囲を先に定義する。

## 8. 予備サーバーなしの流入制御を実装可能にする（F06・F09・F11）

受付を絞る場所は、認証更新、DB更新、結果照会等の経路ごとに置く。CPU使用率だけの全体判定にはしない。コントローラには最低限、到着・受理・拒否の各率、実行中数、待機数、最古待機時間、DB待ち、認証状態ストア遅延、結果不明件数、再試行量を渡す。

運用設定として固定する候補項目はqueue_warn、queue_stop、queue_resume、normal_limit、degraded_limit、resume_step、stable_duration、max_inflight、max_queue、各経路のdeadlineとする。単位、取得元、欠測時動作、版、設定権限、実測根拠も必須欄にする。未設定をゼロや無制限に変換しない。

```text
N → M：事前固定した警告条件で、非重要枠を縮小
N/M → D：停止条件・必要な観測の喪失等で、新規の対象受付を止める
D → H：キュー・接合先・結果不明操作が復帰条件を満たしたら復帰保留
H → 段階再開：stable_durationの成立と、必要な人間承認の後にresume_stepだけ増やす
再悪化 → D：元の大きな枠へ即座に戻さない
```

N/M/D/Hは資源運用の状態であり、正典の境界状態・不可逆ラッチと別に保持する。二時間軸監視を正典の二重ゆらぎそのものとは呼ばない。正典式を使う判断は、対象・δ/τ・測定・変換規則が確定するまで保留する。制御で変える受付枠と、評価の基準・閾値を分ける。評価出力を見て同じ評価計器を都合よく再設定する経路を設けない。

キューは件数・総バイト数・最古待機時間を制限する。無限待機へ逃がさない。結果照会、公開案内、制御・監査に必要な枠は通常更新から分離して確保する。ただし予約した枠も同じ物理資源を消費するため、その合計を実容量評価に含める。ノード別制限を使うなら、全ノードの合計で許容上限を超えないようにする。

説明用の100件/秒処理・160件/秒到着・受付80件/秒では、既存滞留300件を処理能力100件/秒で減らせる仮定なら15秒で解消する。これを本番の80件/秒設定にしない。先に実サービスの経路別負荷試験で、拒否応答・認証・DB・監査を含む限界を測る。

未受理は503等とRetry-Afterで示し、利用者別制限は429等で区別する。クライアントの再試行は元操作IDを維持し、ジッター、上限回数、全体期限を設ける。応答を返せなかった場合は未受理を保証できないので、端末に「未確定」と表示する。

## 9. 処理の状態と、利用者が知っている状態を分ける（F11）

Cの「三状態」と4行の表の混在は、サーバーの処理事実と端末の観測を分けて整理する案を推奨する。

| サーバーの処理事実 | 確認できたときの表示 | 次の行動 |
|---|---|---|
| 未受理 | 「業務処理として受け付けていません。業務データの保存・処理ジョブの投入は行っていません」 | 案内した条件で後から再送 |
| 受理済み・未完了 | 「受け付けました。結果を確認しています」 | 同じoperation_idで照会 |
| 結果確定 | 成功・失敗・取消等の確定した結果 | 新操作と元操作の再確認を区別 |

応答を失った端末のRESULT_UNKNOWNは、上のどの事実も確認できない観測状態とする。「処理結果を確認できません。処理状況を確認しています」と表示し、元操作IDで照会する。自動再送する場合も、サーバーが同一操作へ合流できる契約の範囲で行う。

「送信されていません」は、端末からネットワーク送信を行っていない場合だけ使う。入口で拒否した要求でも通信・監査ログは残り得るため、「保存なし」は業務データとジョブ投入の範囲を明示する。

操作IDは最初の送信前に端末で保持し、画面遷移・アプリ再起動後も結果照会に必要な期間は維持する。GET /v1/operations/{operation_id}という照会APIを置く場合も、主体とtenantの認可を必須とする。操作IDを知っているだけで結果を返さない。

## 10. 移行を端末・セッション・APIの組合せで進める（F08・F09）

| 段階 | 実施内容 | 次へ進む条件 |
|---|---|---|
| M0 棚卸し | API台帳、BOLA是正、旧資格の棚卸し、対応端末と本人復旧経路を準備 | 未分類経路なし。保護APIの認可試験と復旧受付手順が成立 |
| M1 候補登録 | 既存セッションを保ちながら候補鍵を生成・提出 | 本人承認前に業務権限が増えない |
| M2 新方式の並行観測 | 旧方式の最低条件を維持した対象で、新方式を観測 | 失敗原因を端末群・経路別に説明でき、登録不能者も集計される |
| M3 限定強制 | 承認済み端末/セッションと指定APIから強制 | ヘッダー欠落・偽装でlegacyへ降格できない。別端末への影響を確認 |
| M4 対象拡大 | サービス側の責任者が影響と試験結果を確認して拡大 | 負荷、障害、本人復旧、問い合わせ体制が受入条件を満たす |
| M5 旧方式終了 | 事前通知と代替手段を伴い旧資格を無効化 | 残存旧利用者を特定し、対応計画・終了承認・監査記録がある |

M0〜M5は提案内の移行段階名であり、Cの資源運用M状態や正典状態と同一ではない。

旧方式で認証できた要求を観測用に通す場合も、その経路の認可と既存の防御条件は維持する。新方式が必須となった対象は、新ヘッダー欠落や検証失敗を理由に旧方式へ自動退避させない。強制条件はクライアント申告で決めずサーバーに保持する。

登録済み端末Aと未更新端末Bを同じ利用者が持つ場合は、Aの移行を理由にBを暗黙失効させない。ただしサービス全体で高機密APIの必要条件を引き上げる場合は、Bにも事前にその影響を伝える。端末の使い分けとアカウント全体の侵害時失効は別に定義する。

旧キー廃止後の障害対応は、新規受付の停止、公開表示、結果照会、強い本人復旧を基本とする。enforcedからshadowへの変更を通常の切戻しにしない。旧キー再有効化は保護条件を変える新たな判断であり、更新要求フラグの解除と同一ではない。

進行率は、登録済み内の成功率だけでなく、対象アクティブ端末数、登録未着手、登録不能、本人承認待ち、証明失敗、発行失敗、失効、復旧待ちを分母込みで集計する。99.9%や98%を一律の合格値にせず、サービス責任者が許容する影響と、失敗群への対応を先に定める。

## 11. 紙・対面の復旧を、移行終了前に利用可能にする（F05・F08・F12）

推奨する復旧案件の記録：case_id、対象アカウント、確認した権利の範囲、確認手段、資料参照先、受付者、審査者、承認者、新登録候補、失効対象、通知、実行結果、異議申立て先。本人確認資料の内容を一般監査ログへ複製しない。

高機密操作を扱うサービスでは、受付と最終承認を同一担当者だけで完結させず、承認者が通常の鍵登録APIを無制限に直接操作できない構成を推奨する。審査承認は案件と新鍵に限定した単回・期限付きの操作へ結び、実行時に旧資格の失効と新資格の登録を確認する。紙の確認だけで秘密鍵を復元した扱いにしない。

オンラインDB停止中でも独立窓口が受付できる設計と、オンラインDBで権利を照合して再発行できる設計を区別する。権利記録を確認できない間は受付と保留に留め、復旧成功とは表示しない。紙でも原記録や権利台帳へ依存するなら、その依存を図に残す。

D0/D1/D2は利用者選択の候補とし、選択肢の下限を業務上の必要条件で決める。D0を許すなら、デジタル復旧不可、別窓口の有無、必要な条件を選択時に表示する。紙・対面手段がないサービスに、存在する救済経路を約束しない。法的適合・本人確認書類の種類・保存期間は、対象サービスと法域が決まってから確認する。

## 12. 数値・監査・試験の合格条件（F01〜F12）

### 数値記述の改訂

- UUID v4は128ビット長・乱数部分122ビットと記し、推測成功率ゼロという断言を除く。
- 10要求/10秒という制限なら、5分で300要求という計算を明示する。返却件数・返却バイト数と、複数トークン/複数端末/更新をまたぐ累積上限を別に管理する。
- 5分トークンの先行更新は平均の発行頻度を増やす。15〜60秒前の一様ジッターなら平均間隔262.5秒、300秒周期比8/7の発行率になる。集中緩和の試験と平均負荷の試験を分ける。
- 「99%防止」「端末全体の1%未満」「専門家採用費」「主要漏洩原因」などの根拠未確認の数値・社会的断定は、資料が得られるまで未検証とする。測っていない数値に置き換えない。
- 数値の根拠は、対象経路・端末群、試験日、入力分布、観測期間、同時利用数、データ量、依存構成、測定結果、承認者と結び付ける。
