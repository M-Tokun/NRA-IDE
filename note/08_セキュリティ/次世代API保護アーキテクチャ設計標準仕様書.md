## 1. エグゼクティブ・サマリー（経営層向け背景と目的）

### 1.1 背景：AIエージェントによる「攻撃コストのゼロ化」と従来型防御の破綻

現在、国内外で数百万〜数千万件規模の個人情報漏洩（メガリーク）が相次いでいる。これらの主要因は、スマートフォンアプリ等を逆コンパイルして内部の通信仕様（API）を解析し、バックエンドサーバーから直接データを引き抜く**「A2B（App-to-Backend）攻撃」**である。
従来、この種の解析は高度な知識を持つ人間が時間をかけて行うものだったが、現在は**AIエージェントの自動化により、24時間365日・ほぼ無コストで数千本のアプリに対する総当たり攻撃（絨毯爆撃）**が可能となった。

この脅威に対し、従来の「ユーザーにパスワード変更や二段階認証を求める対策」は**完全に無意味**である。なぜなら、攻撃者は正規のログイン画面をバイパスし、裏側のAPIを直接叩いているからである。

### 1.2 課題：超高額スペシャリストの枯渇と「静的APIキー」の限界

すべての業務ロジックの認可不備（BOLA/IDOR）を人間の目で塞ぎ続けるには、年収数千万〜億単位のトップセキュリティスペシャリストが必要となるが、市場に絶対数が存在せず採用は不可能に近い。
また、開発の簡易さを優先して長年使われてきた「静的なAPIキー（固定の文字列）」や「端末を単なる画面表示器（フロント）としてしか使わない設計」は、鍵を抜かれた瞬間に全データが流出する致命的な構造欠陥を抱えている。

### 1.3 本仕様書の目的（ROIと到達点）

本仕様書は、「獲得不可能な超高額スペシャリストの属人的スキルに依存せず、かつモバイル特有の通信障害やサーバー負荷でユーザー体験を損なわない、現実的かつ機械的な境界防御基盤」を4つのフェーズで段階的に構築するための標準仕様を定義する。

| 評価軸 | 従来設計（静的APIキー・人間依存） | 本仕様書の新標準（物理署名・自動境界） |
| :--- | :--- | :--- |
| **漏洩時の被害規模** | 数千万件の全件流出（会社存続の危機） | 仮に穴があっても単発で遮断（メガリークの物理的阻止） |
| **人材・運用コスト** | 全APIのロジック監視に膨大な人件費が永続発生 | ゲートウェイと端末チップによる機械的遮断で運用費を平準化 |
| **AI自動攻撃への耐性** | スクリプトによる高速スキャンで容易に突破 | 物理スマホチップを通さない通信を1発目で100%破棄 |

## 2. アーキテクチャ基本原則（3大設計思想）

開発チームは以下の3原則をすべての設計の前提（Fail-Closed）とすること。

1. **原則1：静的APIキーの完全廃止と「端末のハードウェア・アンカー化」**
   * クライアント（アプリ）内に「秘密の文字列」を埋め込むことを全面禁止する。
   * 端末を単なるUI表示器ではなく「暗号処理ノード」と定義し、iOSの **Secure Enclave**、Androidの **StrongBox / TEE** 内部で生成した「抽出不可能な秘密鍵」による物理署名を通信の絶対条件とする。
2. **原則2：「トークン交換」と「業務API」の分離による並行性・低負荷の担保**
   * すべての業務APIで毎回ハードウェア署名とカウンター検証を行うと、非同期通信の順序逆転によるエラーやサーバーのCPUスパイクを招く。
   * 重いハードウェア検証は「5分間有効な短命トークンの発行時のみ」に集約し、日常の業務APIはその短命トークンを用いて完全並列・高速に処理する。
3. **原則3：「通信は必ず切れる」前提の冪等性（Idempotency）と段階的縮退**
   * モバイル通信の瞬断・タイムアウトによる再送が「リプレイ攻撃」と誤判定されてユーザーがロックアウトされないよう、Redis等を用いた `Idempotency-Key` によるトランザクション保護を必須とする。

## 4. 段階的実装ロードマップ（4フェーズ構成）

既存サービスを止めずにリスクを低減するため、以下の4フェーズで順次実装を行う。

### 【Phase 1】最小コストで行う「即時止血」（サーバー・ゲートウェイ層）

**目的:** クライアント改修を待たず、AIによる自動スキャン（連番探索）と大量データ抜き取りを物理的に遮断する。

#### 1.1 公開識別子の非線形化（UUID v4化）
* **要件:** APIのURLパスやリクエストボディにおいて、DBのオートインクリメント値（連番: `user_id=10001` 等）を露出することを禁止する。
* **実装:** 外部公開用の識別子はすべて最低128bitのエントロピーを持つ **UUID v4**（または暗号論的トークン）に変換し、推測による水平探索（BOLA/IDOR）のヒット確率を数学的にゼロにする。

#### 1.2 ゲートウェイでの機械的レートリミットとエラー監視
* **要件:** WAF / API Gateway（Cloudflare, AWS WAF, Kong等）において、異常な探索挙動を機械的にドロップする。
* **基準値:**
  * 同一セッション/IPから1分間に `403 Forbidden` または `404 Not Found` が **5回以上** 発生した場合、該当接続元を **60分間即時遮断** する。
  * 個別データ取得APIに対し、1ユーザーあたり **10 req / 10秒** を超えるバースト通信を遮断する。

#### 1.3 レスポンスの最小化（DTOホワイトリスト方式）
* **要件:** DBのテーブル構造（エンティティ）をそのままJSONシリアライズして返却する実装を禁止する。
* **実装:** 画面描画に必須のフィールドのみを定義した専用の DTO（Data Transfer Object）を必ず経由させ、不要な個人情報やハッシュ化パスワードがAPIレスポンスに混入する経路を断つ。

---

### 【Phase 2】端末の「脱フロント化」とハードウェア鍵封印（初期登録フロー）

**目的:** アプリ内の静的APIキーを廃止し、正規の実機端末のみを通信主体として登録する。

#### 2.1 ハードウェア隔離領域での鍵ペア生成
* **iOS実装要件:**
  * `Security` フレームワークにて `kSecAttrTokenIDSecureEnclave` および `kSecAttrKeyTypeECSECPrimeRandom`（256bit）を指定し、Secure Enclave内で鍵ペアを生成する。
* **Android実装要件:**
  * `AndroidKeyStore` にて `ECGenParameterSpec("secp256r1")` を指定。`hasSystemFeature(FEATURE_STRONGBOX_KEYSTORE)` を判定し、利用可能な場合は `setIsStrongBoxBacked(true)`、非対応機は TEE（TrustZone）へフォールバックさせる。

#### 2.2 初回ハードウェア証明（Attestation）の検証
アプリの初回起動・ログイン時に以下のフローで公開鍵をサーバーへ登録する。
1. サーバーが32バイトの乱数 `challenge` を発行。
2. 端末が **Apple App Attest** / **Android Key Attestation** を実行し、証明書チェーンを取得してサーバーへ送信。
3. サーバーは以下の項目を検証（1つでも不一致なら `403 Forbidden` で破棄）:
   * ルート証明書が Apple / Google 公式のハードウェアルートCAに連鎖していること。
   * App ID（`rpIdHash`）またはパッケージ名・APK署名ハッシュが自社の正規リリースビルドと完全一致すること。
   * 証明書拡張領域内のチャレンジ値が、直前に発行した `challenge` と一致すること。
   * （Android）SecurityLevel が `Software(0)` ではなく `TEE(1)` または `StrongBox(2)` であること。
4. 検証通過後、リーフ証明書から公開鍵（Public Key）を抽出し、端末IDおよび初期カウンター `signCount = 0` と共にDBへ永続化する。

---

### 【Phase 3】短命トークン交換による「負荷と競合の回避」（日常の認証フロー）

**目的:** 非同期APIの並行通信による `signCount` の順序逆転を防ぎつつ、トークン抜き取りを無力化する。

#### 3.1 短命トークン発行APIの仕様
業務APIとは独立した2つの認証エンドポイントを設ける。

* **`POST /v1/auth/challenge`**
  * 入力: `key_id`
  * 処理: ワンタイムの `challenge` と `session_id` を生成し、Redisに **TTL 60秒** で保存して返却。
* **`POST /v1/auth/token`**
  * 入力: `session_id`, `assertion`（ハードウェア署名データ）
  * 検証処理:
    1. Redisから `session_id` を引き当てて即時削除（ワンタイム保証）。
    2. 登録済み公開鍵を用いて `SHA256(authData || SHA256(challenge))` のECDSA署名を検証。
    3. 抽出した `currentSignCount` が、DB/Redis上の `storedSignCount` より **真に大きい（$\text{current} > \text{stored}$）** ことをアトミックに検証・更新。
  * 出力: **有効期限300秒（5分）の短命JWT（ES256署名）** を発行。

#### 3.2 クライアント側の直列更新と並行通信
* **直列更新制御:** クライアント側はトークン更新処理を `Swift Actor` や `Kotlin Mutex` で1本に直列化し、複数画面から同時にトークン更新が走らないよう排他制御する。
* **メモリ内保持:** 取得した短命JWTはディスク（Keychain/SharedPreferences）には書き込まず、**オンメモリのみ**で保持する。
* **業務APIの並列化:** 日常の業務API通信は、オンメモリの短命JWTをヘッダーに付与して通信する。ここでは `signCount` を消費しないため、何十本でも非同期・並列に通信可能とする。

### 【Phase 4】通信障害・スパイク負荷を乗り切る耐障害設計（インフラ・運用層）

**目的:** モバイルの電波悪化やアクセス集中時でも、セッション破綻やサーバーダウンを起こさせない。

#### 4.1 冪等性キー（Idempotency-Key）による通信断リトライ保護
モバイル環境で「サーバー側で `signCount` が更新された直後に電波が切れ、クライアントが同じAssertionを再送してリプレイ攻撃と誤認される事故」を防ぐ。

* **クライアント要件:** `/v1/auth/token` 呼び出し時にUUID `X-Idempotency-Key` を付与する。タイムアウト再送時は**必ず同一のキー**を維持して再送する。
* **サーバー要件（Redis制御）:**
  * キー構成: `idempotency:<device_id>:<idempotency_key>`
  * 初回受信時: `SET NX`（TTL 15秒）でステータス `"PROCESSING"` を記録し、署名検証と `signCount` 更新を実行。
  * 正常完了時: 生成した短命JWTを含めてステータス `"COMPLETED"` で上書き保存（**TTL 120秒**）。
  * 再送受信時: ステータスが `"COMPLETED"` であれば、`signCount` の検証をスキップし、**キャッシュされた短命JWTをそのまま `200 OK` で再返却**する。
  * 検証失敗時: 署名不正等でエラーとなった場合は、即座にRedisキーを `DEL` してロックを解放する。

#### 4.2 ジッター（Jitter：ランダムな時間揺らぎ）によるスパイク平滑化
* **要件:** 全端末が一斉に5分周期でトークン更新を行いサーバーが飽和（Thundering Herd）するのを防ぐ。
* **実装:** クライアントが先行更新（Pre-emptive Refresh）を行うタイミングを固定値にせず、「有効期限切れの $60\text{秒前} \sim 15\text{秒前}$ の間で一様乱数により決定した時刻」に分散させる。

#### 4.3 重要度に応じた段階的縮退（Graceful Degradation）
通信環境が極度に悪化した際、すべての画面がエラーで停止することを防ぐため、APIを2階層に分類する。

| API階層 | 対象となる処理の例 | 認証・境界の挙動 |
| :--- | :--- | :--- |
| **Tier 1（高機密・決済・更新）** | 送金・決済、個人情報閲覧・変更、パスワード変更、予約確定 | **厳格な Fail-Closed**: 有効期限内（5分）のハードウェア由来短命JWTが必須。欠落・期限切れは即時遮断。 |
| **Tier 2（一般参照・公開情報）** | 商品カタログ閲覧、お知らせ取得、店舗一覧検索 | **段階的縮退を許容**: 通信不安定でトークン更新が遅延している場合、最大60分までの期限猶予（Grace Period）またはローカルキャッシュ表示を許可。 |

## 5. セキュリティ監査・CI/CD品質ゲート基準

本仕様の実装漏れを防ぐため、CI/CDパイプラインに以下の自動検査を組み込む。

1. **静的解析（SAST）によるハードコード検知:**
   * クライアントのリポジトリ内に固定文字列のAPIキーやシークレットが含まれていた場合、ビルドを自動的に失敗させる。
2. **DTO未適用エンドポイントの検出:**
   * DBモデル（Entity）を直接レスポンスとして返しているコントローラーが存在した場合、プルリクエストをブロックする。
3. **BOLA自動テスト:**
   * ステージング環境にて、テストユーザーAの短命トークンを用いてテストユーザーBのUUIDリソースへアクセスし、`403/404` 以外（`200 OK` 等）が返った場合は本番デプロイを即時停止する。
