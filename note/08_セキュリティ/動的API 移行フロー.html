根拠は 08 の 3 原文（A 標準仕様書・B 移行計画書・C 統合設計案）と、同日の精査記録（F01〜F12）・具体的提言です。骨格には提言が推奨する C の「防御・縮退・復旧の分離」を使い、精査で問題とされた A/B の近道は採用していません。

前提と状態区分

位置付け
08 の 3 原文と提言はどれも非正典・未承認・未実装です。この図は設計検討用で、本番仕様ではありません。精査の判定は「精査完了／解消未完了（未解消 12 項目）」です。
事実
08 の「現況」は、モバイルアプリが静的APIキーと長期セッショントークンでバックエンドを呼ぶ構成です（B:7、A:23）。NRA-IDE の src/nra_llm_pipeline_*.py にある LLM プロバイダ用キーは、これとは別の境界です。前回版の図1はこの 2 つを混同していたため、差し替えました。
事実
移行段階 M0〜M5、登録状態 PENDING〜REVOKED、受付順序、障害時の許可表は、提言 §2・§3・§5・§7・§10 にある候補案です。名前はすべて候補名で、導入済みの機能ではありません。
推定
図の分岐の書き方と、段階の間を矢印でつないだ部分は、提言の文章を図にしたものです。差戻しの矢印は、提言の「次へ進む条件」を満たさない場合を表した解釈です。
未確定
対象サービス、端末 OS の分布、処理容量、認証製品、法的な本人確認要件はまだ示されていません（C:58）。そのため図には数値の閾値を入れていません。

障害時に許可すること（提言 §7 の要約）

障害保護API（既発行資格）新規登録・資格発行復帰の条件
Apple/Google 等の証明基盤が停止その外部サービスを毎回必要とせず、他の必須検証がすべて成立する範囲だけ継続必要な証明を取れない登録は保留外部証明の正常化と再検証
Redis（任意キャッシュ）が停止正本DBで同じ検証を続けられ、負荷上限内なら継続同じ条件を満たす場合だけ継続正本との整合と負荷を確認
Redis が唯一の再利用防止正本で停止再利用防止を検証できない保護要求は停止停止正本の復旧と整合確認。検証の省略で代替しない
counter・失効の正本DBが停止、または巻き戻りの疑い照合できない保護要求は停止。独立した公開経路だけ継続停止証拠照合、失効処理、必要なら強い再登録
端末の鍵を喪失失った鍵が必要な操作は不可別の本人証明または復旧審査で新規登録新しい鍵の承認と旧資格の失効

A/B 原文から採用しなかった近道

原文の案採用しない理由（精査）この図での扱い
旧セッションだけで新端末を自動登録（B:83, 164）漏えいした旧セッションが新しい鍵の信頼に昇格する（F05）図3：独立した認証器の承認か復旧審査を必須にする
障害時に署名や signCount の検証を省略（B:266, 329）同じ署名の再利用や counter の巻き戻しが通る（F04）障害表：省略せず、保留または停止
短命 Bearer ＋ IP/TLS 指紋で盗用を防ぐ（B:346）秘密鍵を持っていることの証明にならない（F03）図4：DPoP などの送信者拘束を受入条件にする
UUID 化・端末署名で BOLA を解消（A:99）正規の端末でも他人の ID を要求して署名できる（F01）図4：業務認可を独立した判定として残す
Redis の TTL だけで冪等性を確保（A:171–173）停止のタイミングによっては、正当な再送が拒否される（F07）図4：操作記録を同じトランザクションで確定する
enforced から shadow への切戻し（B:183）強制済みの境界が緩む（F08）図2：通常の切戻し手段にしない

大事な部分のまとめ

  • 防御（不正を止める）、縮退（処理しきれないものを受け付けない）、復旧（デジタル資格を失った後の権利回復）は、それぞれ別の系統として持ちます。縮退を理由に認証・認可を緩めることはしません。
  • 新しい鍵は、旧セッションだけでは ACTIVE になりません。独立した本人承認か、復旧審査を通します。
  • BOLA の是正と復旧経路の準備は、移行の後ではなく前に済ませます（M0、M5 の前提）。
  • 検証できない状態では、新しい資格を発行せず、保護された操作も通しません。

要点（要約）

棚卸し・BOLA 是正（M0）→ 候補鍵の登録（M1）→ 並行観測（M2）→ 限定強制（M3）→ 対象拡大（M4）→ 旧方式終了（M5）の順に進め、各段階のゲートを満たさなければ次に進みません。図の数値や段階名はすべて未承認の候補で、受入試験 AT01〜AT20 も未実行です。
