動的鍵によるAPI保護の設計思想と仕様

本書は、既存APIへ追加する認証・認可・操作受付の設計を説明します。端末が保持する鍵、サーバーが発行する短命トークン、要求ごとの鍵所持証明を分け、登録から失効までの条件を定めます。移行手順は、その条件を既存サービスへ段階的に適用する手順として後半に置きます。

〈推論〉本設計の位置付け

通常処理検証・判定完了・許可待機・再試行／推論・未決拒否・停止・異常

以下は、確認できた資料を根拠に、既存APIへ追加する改良部分を組み立てた設計案です。実サービスの構成・運用条件との適合は未確認です。根拠資料に記載された現況を、実環境で確認済みの事実として扱いません。

  • 推論：資料から導いた処理順序・分岐・改良ロジックです。設計上の提案であり、実装済み・安全性検証済みという意味ではありません。
  • 未決：実装前に責任者が決める条件です。保存先、保持期間、処理容量、障害時の扱い、外部処理との整合方法などは、対象サービスごとに決定します。
  • 未検証：実ブラウザでの描画・印刷、本番APIへの組込み、受入試験、負荷・障害試験は確認が残っています。

1. 設計思想：要求を受理する根拠を分ける

この設計で守る対象は、利用者のデータ、更新処理、決済等の外部副作用です。アプリに埋め込んだ共有秘密だけに依存せず、「現在有効な本人資格」「承認済みの鍵の所持」「対象と操作への権限」「今回の操作を実行してよい状態」をサーバー側で確認します。鍵の所持を証明できても、他人のデータや未許可の操作への権限は増えません。

防御・縮退・復旧には、それぞれ別の責任を持たせます。防御は不正な要求を拒否し、縮退は処理容量を超える要求を入口で制限します。復旧は鍵を失った本人が別の確認手段で権利を回復する手続きです。混雑や利便性を理由に、必須の検証を省略しません。

想定する問題本設計で追加する条件残る限界
アプリから共通APIキーを抽出される端末ごとの承認済み公開鍵と、その鍵に拘束した短命資格を使うアプリの識別情報自体は秘密として扱えない
アクセストークンだけを盗まれる同じ登録鍵で作った要求証明を要求する端末上で鍵を不正利用できる攻撃は別途対処が必要
漏えいした旧セッションで攻撃者の鍵を追加される独立した本人承認を、新しい鍵と登録操作に結合する本人確認・復旧審査の強度は対象サービスで決める
正規利用者が他人の対象IDを指定する主体・tenant・対象・操作をサーバー側で認可する鍵署名、UUID、端末証明だけではBOLAを解消できない
同じ証明や更新操作を再送される証明の重複検出と業務操作の一意受付を別に実施する外部先が冪等性や照会を提供しない場合、自動で一回実行を保証できない
障害後に更新要求が集中する入口制限、専用枠、更新の合流、段階再開を使う必要容量と効果は負荷・障害試験で確かめる

2. 「動的鍵」が指すものと更新の単位

本書でいう動的鍵は、端末鍵に結び付いた短命資格と、要求ごとに作る所持証明を組み合わせる認証方式の呼称です。秘密鍵をAPI要求のたびに作り直す仕様にはしません。秘密鍵の更新、アクセストークンの更新、要求証明の生成は、それぞれ別の周期・理由で行います。

要素作る主体・保存先更新する契機用途
端末のDPoP鍵ペア端末で生成。秘密鍵は利用可能なOSの保護領域へ保存し、持出しを制限初回登録、承認された鍵更新、喪失・侵害後の再登録API要求に対する鍵所持証明
公開鍵と登録記録サーバーの登録正本本人承認、停止、失効、鍵更新どの主体にどの鍵を許可したかを管理
短命アクセストークン認証サーバーが発行。端末では原則メモリ保持有効期限前の更新、許可範囲変更等API・権限・期限・登録鍵の結合
DPoP proof端末がDPoPを使うHTTP送信の直前に生成再送・状態照会を含む送信ごと今回のメソッド・宛先・資格に対する所持証明
Refresh Token採用する認証基盤が発行。端末はOSの保護された保存先を使用更新契約に従う。失効・再利用検出も管理新しいアクセストークンを取得する資格
登録challengeと本人承認サーバーが登録操作に結合して管理登録操作ごと。期限切れ後は所定の手順で再取得古い証明や別の鍵への承認の流用を防止
トークン発行署名鍵認証サーバー側の鍵管理基盤発行側の鍵更新・侵害対応の計画によるアクセストークンへ発行者の署名を付ける

端末の署名鍵と、トークン発行者の署名鍵は役割も保管場所も異なります。端末の公開鍵を受信しただけでは、その所有者がアカウント本人であることは確定しません。登録承認と本人認証で結合を作り、以後の要求でその結合を確認します。

4. 登録と有効化の仕様

旧セッションで行える自動処理は、登録候補の提出までです。登録サービスは、サーバーで確定した主体にregistration_idを結合し、目的、新しい公開鍵のthumbprint、単回challenge、期限、状態版を保存します。本人承認も同じ登録操作と鍵へ結合します。

状態確認した内容許可する処理
PENDING登録候補を受け付けた登録手続きと候補照会。業務権限は増やさない
DEVICE_VERIFIED必要なOS別証明と登録鍵の所持を検証した本人承認の確認へ進む。承認不足なら業務資格は発行しない
ACTIVE本人承認・鍵・候補の有効条件を確定時にも満たした台帳で許可された資格発行
SUSPENDED調査・障害・整合性不明で停止している新規発行と、その状態が必須の保護要求を停止
REVOKED失効が確定した当該資格の利用不可。自動でACTIVEへ戻さない

候補全体が期限切れなら、その登録操作を終了します。本人承認だけが期限切れなら、候補の有効性を再確認したうえで承認を取り直します。承認を更新しても候補やchallengeの期限は無制限に延びません。

有効化では、候補の状態版、鍵、主体、期限、承認の対象・未使用を再照合します。ACTIVEへの遷移、承認の消費、必要な旧資格の失効、監査・通知outboxの作成を同じ確定単位にします。他端末の資格は、失効対象として明示した場合だけ変更します。資格発行の直前にも有効性を確認します。

5. OS別証明とDPoP鍵の結合

App Attest、Android Key Attestation、DPoPは別の仕組みです。OS別証明が成功しただけで、任意の別鍵まで信用したことにはしません。

項目iOSでの契約Androidでの契約
証明処理App Attest固有の鍵・検証手順を扱うKeystoreの証明対象鍵とチェーン・失効・要求条件を確認
DPoP鍵App Attest鍵をそのままDPoP用に利用できるとは仮定しないDPoP公開鍵と証明対象鍵の一致、または別鍵との結合を検証
別鍵の結合registration_id・目的・challenge・DPoP公開鍵thumbprintを同じ検証対象へ含める同じ項目を証明の契約と照合し、単なる自己申告にしない
再利用防止App AttestのcounterとDPoPのjtiを別に管理App Attestと同じcounterがあるとは仮定しない
未対応端末必須の証明強度を満たさない操作を制限し、代替経路を案内証明済みの強度で許可できる範囲を台帳に定める

結合するデータは、型・順序・長さ・文字コード・版・目的識別を固定したバイト表現にします。曖昧な文字列連結で署名対象を組み立てません。バイト表現と検証器の実装は未決であり、異なる鍵・主体・登録操作へ証明を流用する試験を通すまで採用しません。

照合先は Appleの検証手順 と Android Key Attestation です。Appleページ本文は今回の取得経路では確認できていないため、iOS固有実装の適合確認は残っています。

6. アクセストークンと要求証明の契約

JWTアクセストークンを使う場合、発行者が署名し、APIは許可した発行者・鍵・アルゴリズムで検証します。ID TokenやDPoP proofを、アクセストークンとして受け入れません。検証するアルゴリズムと鍵の用途は設定で固定し、未検証のヘッダーから任意の鍵取得先を選ばせません。JWT検証の指針 RFC 8725

項目本設計で確認する内容
iss・aud設定した発行者と、当該APIを対象とするaudience
sub・scope主体と許可範囲。発行元のgrantや現在の権限を超えない
iat・exp・必要ならnbf発行時刻・期限・有効開始。サーバー時計と設定済みの許容差で判定
cnf.jkt今回のDPoP公開鍵のthumbprintと一致する拘束

トークンのjti資格を識別する値。要求証明のjtiとは別

DPoPの要求形式は次です。山括弧内は説明用の置換箇所であり、実際の資格や署名ではありません。TLSを必須にします。

GET /v1/records/record-001 HTTP/1.1
Host: api.example.invalid
Authorization: DPoP <access_token>
DPoP: <signed_proof_jwt>

proofの検証項目は RFC 9449 §4 に従います。本案の初期候補はES256・P-256とし、端末と認証基盤の対応確認を採用条件にします。署名方式の変更は設定変更として管理します。

proofの項目確認内容

htm・htu今回のHTTPメソッドと宛先。htuの照合ではquery・fragmentを除外
ath保護APIで提示した資格について、base64url(SHA-256(ASCII(access_token)))と一致
iat・jti設定した受理時間内で、今回の送信を識別するproof
nonceサーバーが要求した場合、その発行元・用途・有効条件に対応する値

JWKのthumbprint計算には RFC 7638 の表現を使います。DPoPは本文や任意ヘッダー全体への署名ではありません。本文、queryの条件、金額、送金先等はTLS、入力検査、業務認可、必要な取引確認で扱います。

htuの照合先は、設定した公開URLと信頼するproxyの構成から再構成し、規格に従うURI正規化を固定します。未検証のHostや転送ヘッダーだけで照合先を決めません。内部URLへの書換えと公開URLの差もGatewayとAPIで共通の契約にします。

7. proofの再利用防止と鍵の更新

本案では全保護APIでproofの単回受入を要求します。署名・拘束・用途・時刻を確認してから、検証領域・鍵thumbprint・jtiをスコープに正本へ原子的に記録します。同じproofが別ノードへ同時到着しても、一方しか受理しない構成にします。これは本設計の配備方針であり、すべてのDPoP配備に共有ストアを義務付ける規格上の主張ではありません。

記録はproofを受理できる最終時刻まで保持します。nonceがあっても本案ではiatの受理窓を維持し、nonceだけで重複検出を置き換えません。最大長、保存時間、障害時の停止、全ノードの整合を契約にします。RFC 9449 §11.1

端末鍵を更新する場合、新しい鍵も登録・本人承認を通します。既存のトークンの拘束先だけをクライアントの申告で書き換えません。旧鍵に拘束したRefresh Tokenを、新鍵のproofだけで更新することも許可しません。旧鍵が使えない場合は独立した本人確認・復旧へ進みます。

過去の操作結果を新鍵で受け取る必要がある場合は、通常の同鍵再送と分けた回復契約を設けます。新鍵の承認だけで過去操作の受取権限を自動移管せず、主体・操作・回復承認の対応を監査可能にします。

8. 資格発行・更新APIと保存する正本

次の経路名・項目名は既存APIへ接続する候補です。既存のOAuth基盤がある場合はそのtoken endpointとgrantを使い、公開鍵提出だけで資格を発行する独自の近道を作りません。DPoPは鍵所持の追加証明であり、それ単独で本人認証やアクセス許可を成立させません。RFC 9449 §3

10. 既存APIへの接続例と実装責任

次は接続順序を示すPythonの疑似コードです。暗号検証、正本、一意制約、業務トランザクションを実装したコードではありません。各メソッドは不成立・状態不明で例外または明示した拒否結果を返す契約とし、暗黙の許可へ落としません。

def protected_request(request, service):
    service.admit_before_authentication(request)
    principal, proof = service.verify_access_and_sender(request)
    service.require_live_registration_and_session(principal)
    service.record_verified_proof_once(proof)
    service.admit_authenticated_principal(principal, request)
    service.authorize_target_or_receipt(principal, request)
    outcome = service.dispatch_by_request_kind(principal, request)
    dto = service.build_authorized_response(principal, outcome)
    return service.finalize_and_send(principal, dto, outcome)
接続箇所実装で担保する責任
verify_access_and_sender発行鍵検証と端末proof検証を分離し、別用途JWTを受理しない
record_verified_proof_once署名等の確認後に原子的な重複検出。mTLSへDPoPのjti検査を機械的に流用しない
dispatch_by_request_kind照会は照会のみ。再送はdigestと状態を確認。新規は一意受付後、確定時の認可・業務条件も検証して副作用を確定
finalize_and_send実件数・実バイト数・現在の受取権限・返却枠を確定してから送信
すべての経路旧版・一覧・export・キャッシュにも同じ保護境界を適用

11. 失効・障害・本人復旧

事象保護APIの動作登録・資格発行の動作
端末鍵・セッションが停止または失効必須状態を満たさない要求を拒否新規資格を発行しない
任意キャッシュが停止正本で同じ検証ができ、負荷上限内なら継続同じ条件が成立する範囲だけ継続
再利用防止・失効の唯一の正本が停止必須検証ができない保護要求を停止必要状態が不明なら停止
証明基盤が停止外部照会が不要で、他の必須検証が成立する既発行資格だけ継続証明を取得できない新規登録は保留
端末鍵を喪失旧鍵が必要な操作を停止独立した本人確認・復旧審査で新候補を登録
正本の巻き戻り・分断を疑う影響する資格を保留し、証拠と整合を確認counter・失効・世代の検査を省略して発行しない

失効情報にキャッシュを使う場合は、許容する鮮度と停止条件を明示します。「即時失効」を約束するなら、その時点の正本照合または同等の機構が必要です。短命であることだけでは即時失効を成立させません。

13. 採用前に決める値と受入試験

未決事項確定する仕様未設定・確認不能時の扱い
端末・認証基盤対応OS、必要な証明強度、独立認証器、OAuth連携対応を推測して有効化しない
鍵・資格・時刻許可署名方式、発行鍵、issuer、audience、access TTL、時刻許容差、鍵更新契機設定不足のプロファイルは有効にしない
登録と承認challenge・候補・承認の各期限、結合バイト表現、競合処理自動延長・対象の読み替えをしない
正本と保持再利用記録、失効、操作結果の保持・整合・復旧方法必須状態が不明な要求を拒否・保留
外部副作用同一IDの意味、照会、outbox、結果不明時の手順不明を未実行と推定しない
資源と応答経路枠、共有総量、deadline、DTO、件数・バイトの上限無制限へ変換しない

受入試験では、別鍵、別主体、別tenant、別宛先、期限境界、重複proof、失効、正本停止、登録確定時の競合、同一操作の並行実行、外部応答消失、旧経路迂回、実返却量超過を確認します。登録・更新・業務・結果照会の各経路で実施し、利用者の権限と結果表示が正しいことまで確認します。詳細な既存試験候補は提言のAT01〜AT20を参照します。これらは本番で未実行です。
