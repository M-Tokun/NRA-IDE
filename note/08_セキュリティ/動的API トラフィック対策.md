# 動的APIで増える負荷と、その回避方法

静的キーを短命トークンに置き換えると、新しい負荷が生まれます。このページでは、負荷がどこに生まれ、何で抑えられるかをまとめています。どの対策も、負荷を理由に認証・認可を緩めないことを前提にしています。

## 考え方の前提

- **推定**：増える負荷は「全体が均等に重くなる」形ではありません。**トークンの発行窓口**と**状態ストア**（失効情報・再利用防止）に集中し、さらに**一斉に更新が走る瞬間**に跳ね上がります。業務APIの検証は、設計次第でほとんど増やさずに済みます。
- **推定**：静的キーを廃止すると、盗んだキーで無制限に呼んでいた不正なトラフィックが減ります。差し引きで全体が増えるか減るかは、実測するまで分かりません。
- **根拠**：08 の A 原則2（トークン交換と業務APIの分離）・Phase 4、C §5（入口制御・N/M/D/H）、具体的提言 §5・§8、精査 F09（先行更新による発行率の増加 8/7）。DPoP の nonce と再利用防止は RFC 9449、mTLS の送信者拘束は RFC 8705 の仕組みです。
- **境界**：**高リスク／一般の区分は API 台帳の data_class で決めます。**個人データを扱う API と更新を行う API は高リスク側に置き、提言 §5 の条件（送信者拘束と、全受入ノードでの再利用検出）を満たします。jti の保存を省く「一般」は、台帳で明示的に指定した API に限ります。指定のない保護API は、「静的APIキーから動的API認証への移行フロー」図4 のとおり、全条件を確認します。
- **未確定**：台帳の data_class の値は、提言 §2 で公開／利用者限定／高機密と定められています。そのうち、どの値を jti の保存を省く「一般」にしてよいかの対応はまだ決まっていません。

## 図1　負荷はどこで生まれるか

```mermaid
flowchart LR
  CL["端末・呼び出し元"] -->|"① 発行要求<br/>台数 ÷ 有効期限 の頻度"| TK["トークン発行窓口<br/>署名検証・証明検証"]
  TK -->|"② 状態の読み書き<br/>challenge・counter・発行記録"| ST[("状態ストア")]
  CL -. "③ 端末登録時だけ<br/>iOS：端末が Apple に証明を要求" .-> EXT["Apple / Google<br/>外部の証明基盤"]
  TK -. "③ Android：失効リストを取得<br/>（キャッシュ可）" .-> EXT
  CL -->|"業務要求"| GW["業務APIゲートウェイ"]
  GW -->|"④ 要求ごとの検証<br/>失効確認・DPoP の jti 記録"| ST
  GW --> BIZ["業務処理・DB"]
  OUT["障害の復旧・アプリ一斉起動<br/>有効期限の同期"] -. "⑤ 一斉更新<br/>（サンダリングハード）" .-> TK
  ERR["401 の連鎖・再試行"] -. "⑥ 再試行の増幅" .-> TK
```

①⑤⑥は発行窓口に、②④は状態ストアに集中します。③で外部の証明基盤に問い合わせるのは、iOS（App Attest）では端末です。発行窓口は受け取った証明をローカルで検証します。Android（Key Attestation）では、発行窓口が取得するのはキャッシュできる失効リストです。業務処理そのもの（BIZ）の負荷は、認証方式を変えても基本的には変わりません。

## 規模の目安（例示の計算）

同時にアクティブな端末を **100 万台**と仮定した計算です。実際の台数ではありません。先行更新は、期限の 15〜60 秒前に一様にずらす前提です（平均 37.5 秒前）。

| 有効期限 | 発行頻度（期限ちょうど） | 発行頻度（先行更新あり） | 増加率 |
|---|---|---|---|
| 5 分（300 秒） | 3,333 件/秒 | 3,810 件/秒 | 8/7 ≒ 1.143 |
| 15 分（900 秒） | 1,111 件/秒 | 1,159 件/秒 | ≒ 1.043 |
| 60 分（3,600 秒） | 278 件/秒 | 281 件/秒 | ≒ 1.011 |

- **一斉更新**：障害の復旧後に 100 万台が 60 秒間に均等に更新すると、平均で約 16,667 件/秒です。これは 5 分期限の平常時（3,333 件/秒）の 5 倍にあたります。更新が偏れば、瞬間の値はこれより高くなります。
- **DPoP の再利用防止**：保護APIへの要求が 20,000 件/秒で、証明の受付窓を 60 秒とすると、状態ストアへの書き込みは 20,000 件/秒、保持する件数は約 120 万件になります。

発行頻度は有効期限に反比例します。期限を短くするほど安全側に寄りますが、その分の発行負荷は発行窓口に集まります。

```mermaid
  V2 -- "明示指定あり（一般）" --> V4["一般：失効は配布済みの小さな失効リストで確認<br/>短い期限が失効の上限になる"]

```

要点は 3 つです。重い検証を発行時に集めること、業務APIはローカルで検証できるトークン（JWT と公開鍵キャッシュ）を使い、要求ごとに認証サーバーへ問い合わせないこと、状態を伴う検証を省くのは台帳で明示した一般APIだけにすることです。高リスク／一般の境界は「考え方の前提」の「境界」の行によります（再精査 P1）。

## 図3　一斉更新が起きたときの段階的な再開

```mermaid
flowchart TD
  O0(["障害が復旧"]) --> O1["H（復帰保留）<br/>発行窓口の受付枠を小さい値から開始"]
  O1 --> O2["期限内のトークンを持つ端末はそのまま業務を継続<br/>（有効期限そのものが猶予になる）"]
  O1 --> O3["新規発行は枠の範囲で受け付け<br/>超えた分には 503 ＋ ずらした Retry-After"]
  O3 --> O4{"待ち行列・最古の待機時間・<br/>状態ストアの遅延が収束し<br/>その状態が継続期間（stable_duration）続いたか"}
  O4 -- "否" --> O3
  O4 -- "可" --> O4B{"結果不明の操作の整合が済んだか"}
  O4B -- "否" --> O3
  O4B -- "済" --> O4C{"H の解除を人が承認したか"}
  O4C -- "未承認" --> O3
  O4C -- "承認" --> O5["受付枠を一段だけ上げる"]
  O5 --> O6{"継続期間の間に<br/>再び悪化したか"}
  O6 -- "悪化" --> OD["D（縮退）に戻す<br/>元の大きな枠へ即座に戻さない"]
  OD -. "復帰条件を満たしたら" .-> O1
  O6 -- "安定" --> O7{"通常の枠に達したか"}
  O7 -- "否" --> O5
  O7 -- "達した" --> DONE(["通常運用"])
```

C の資源状態 D（縮退）→ H（復帰保留）→ 段階的な再開にあたります。H の解除には、人間の承認（C:223）、結果不明の操作の整合と回復の継続期間（C §6.1）、提言 §8 の stable_duration を条件にします（再精査 P2）。再び悪化したときは H ではなく D に戻します（提言 §8「再悪化 → D」）。継続期間などの数値は未確定です。悪化の検知は速く、復帰はゆっくり行います。Retry-After を全端末で同じ値にすると、次の一斉更新を作ってしまいます。

## 問題ごとの回避方法

| 問題 | 有効な回避方法 | 代償・注意 |
|---|---|---|
| ① 平常時の発行負荷 | リスクに応じて有効期限を分ける（高リスクは短く、一般は長く）。トークンを期限まで再利用する | 期限が長いほど、盗まれたときに使われる時間が延びる |
| ② 発行時の状態の読み書き | 重い検証を発行時だけに集める。challenge・counter・発行記録を一つのトランザクションで確定する | 状態の正本をどこに置くかを先に決める必要がある（提言 §6） |
| ③ 外部の証明基盤 | 証明は端末登録のときだけ行う。日常の更新には使わない。Android の失効リストはキャッシュする | 外部基盤が止まると、新規の登録は保留になる |
| ④ 要求ごとの検証 | JWT をローカルで検証し、公開鍵はキャッシュする。要求ごとの問い合わせ（introspection）は避ける。jti の保存を省くのは、台帳で明示した一般APIだけにする（個人データ・更新APIは省かない）。DPoP の jti ストアは鍵ごとに分割し、受付窓を短くする（サーバー nonce も使える） | 一般APIの失効は即時ではなく、最大で有効期限分だけ遅れる。省略の範囲は台帳で明示的に決める |
| ⑤ 一斉更新 | 端末側のジッターと Single-Flight。発行窓口の専用枠。段階的な再開。Retry-After をずらす | 再開に時間がかかる |
| ⑥ 再試行の増幅 | 上限つきの指数バックオフ。401 での自動更新は 1 回で打ち切る。503 と 429 を再認証に変えない | 利用者には「しばらく待つ」と表示する必要がある |
| 社内サービス同士 | mTLS の接続を使い回し、TLS の握手（クライアント証明書の検証）は接続ごとに済ませる。トークンとクライアント証明書の照合（RFC 8705 の cnf の x5t#S256）は要求ごとに行うが、ハッシュの比較だけなので安い | 接続を集約する経路の設計が必要 |

## 負荷対策として、やってはいけないこと

- 混雑を理由に有効期限を延ばしたり、期限切れのトークンを通したりする（A の 60 分猶予案。精査 F09 で 65 分の利用窓になると指摘）。
- 状態ストアが重いからといって、再利用防止や counter の検証を省く（B の案。精査 F04）。
- 未受理の要求に 200 を返す。拒否は 503 や 429 で正直に返す（C §5.5）。
- CPU 使用率だけを見て、一気に通常運用へ戻す（C §5.2、C:212）。

## 大事な部分のまとめ

- 動的APIで増える負荷は、発行窓口と状態ストア、そして一斉更新の瞬間に集中します。業務APIの検証はローカル検証で抑えられます。
- 最も効く対策は、重い検証を発行時に集め、業務APIをローカル検証にする「分離」と、端末側のジッター・合流・バックオフで「同期を崩す」ことの 2 つです。
- 発行窓口と業務APIの処理枠を分けると、一方の混雑がもう一方を止めなくなります。
- jti の保存を省けるのは、API 台帳で明示的に指定した一般APIだけです。個人データ・更新APIは送信者拘束と全受入ノードでの再利用検出を省きません。
- 負荷対策は入口の枠と時間の使い方だけで行います。認証・認可の条件は変えません。復帰保留（H）の解除には人の承認が要ります。

## 要点（要約）

負荷の発生点は 6 か所です。分離（発行と業務）、同期を崩す（ジッター・合流・バックオフ）、処理枠の分割、状態を伴う検証の省略を台帳で明示した一般APIに限る、条件つきで段階的に再開する、の 5 つで回避します。有効期限は安全性と発行負荷の釣り合いで決め、数値は実測で確定させます。
