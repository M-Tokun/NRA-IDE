# 既存アプリの無停止マイグレーション計画書

**〜ユーザーを強制ログアウトさせずに「静的APIキー」から「App Attest / StrongBox」へ完全移行する手順〜**

* **文書種別:** マイグレーション実行計画書（運用・移行設計）

* **前提条件:** 稼働中の本番アプリ（静的APIキー＋長期セッショントークン方式）が存在し、数万〜数百万人のアクティブユーザーが利用していること。

* **絶対条件:** 移行期間中、正規ユーザーに対して「強制ログアウト（再ログイン要求）」や「アプリ更新前の突然の通信遮断」を一切発生させないこと。

## 1. マイグレーションの最大のリスクと解決アプローチ

### 1.1 なぜ「一斉切り替え」は失敗するのか

1. **アプリストアのアップデート浸透ラグ:**
   新バージョンのアプリをリリースしても、全ユーザーがアップデートするまでには数週間〜数ヶ月かかる。サーバー側でいきなり静的APIキーを無効化すると、旧バージョンのユーザー全員が通信不能になる。

2. **OS・端末の非対応・一時的エラー:**
   古いAndroid端末や、Apple/GoogleのAttestationサーバーの一時的な障害により、初回証明（Attestation）が失敗するケースが必ず一定割合（0.1%〜数%）発生する。

3. **既存ログイン状態の維持:**
   すでにログインして長期トークン（CookieやRefreshToken）を持っているユーザーに対し、「鍵登録のために一度ログアウトしてID/PWを入れ直してください」と要求すると、パスワード忘れによる大量の離脱とサポート窓口のパンクを招く。

### 1.2 解決の基本戦略：「サイレント・バインディング」と「デュアル・ゲートウェイ」

* **サイレント・バインディング（裏側での鍵紐づけ）:**
  ユーザーがアプリをアップデートして起動した際、**現在のログインセッション（長期トークン）を維持したまま、バックグラウンドでSecure Enclave / StrongBoxの鍵生成と公開鍵登録を完了**させる。

* **デュアル・ゲートウェイ運用（段階的エンフォースメント）:**
  APIゲートウェイに「監視モード（Shadow Mode）」を設け、旧方式（静的APIキー）と新方式（ハードウェア短命トークン）の両方を並行受け入れしながら、段階的に旧方式の門を狭めていく。

## 2. 移行の全体タイムライン（5ステップ構成）

```
[Step 1: サーバー先行準備] ──> デュアル認証基盤の構築 & UUIDルーティング対応
       │
[Step 2: アプリ配布 & 裏登録] ──> 既存セッション維持のままバックグラウンドでハードウェア鍵を登録
       │
[Step 3: シャドー検証 (監視)] ──> 新トークンを付与して通信。失敗しても旧キーで通し、エラー率を計測
       │
[Step 4: 段階的強制 (Tier別)] ──> 高機密API (Tier 1) から順に静的APIキーを遮断・新方式を必須化
       │
[Step 5: 完全撤廃 (Decommission)] ──> 旧バージョンの強制アップデート発令 & 静的APIキーの完全削除

```

## 3. 各ステップの詳細実装・運用手順

### Step 1：サーバー側の先行準備（クライアント影響ゼロ）

アプリを改修する前に、バックエンド側で新旧両方のリクエストを受け入れられる「ハイブリッド境界」を構築する。

1. **DBスキーマの拡張:**

   * 既存の `users` または `user_sessions` テーブルに紐づく形で、新規テーブル `device_hardware_keys` を作成する。

   * カラム構成: `device_id (PK)`, `user_id (FK)`, `platform (ios/android)`, `public_key_pem`, `sign_count (uint32)`, `attestation_level (strongbox/tee/secure_enclave)`, `trust_state (shadow/enforced)`。

2. **認証エンドポイントの新設:**

   * `/v1/auth/attest`（初回公開鍵バインド用）

   * `/v1/auth/challenge` および `/v1/auth/token`（5分短命トークン発行用）

3. **APIゲートウェイの「デュアル検証ミドルウェア」実装:**
   リクエストヘッダーを検査し、以下の優先順位でルーティングするモードを実装する。

   * **パターンA:** `Authorization: Bearer <短命JWT>` が存在する場合 ➔ 新方式で検証。

   * **パターンB:** 従来の `X-API-Key: <静的キー>` ＋ 既存セッショントークンのみの場合 ➔ **現時点ではそのまま通過させつつ、監査ログに `"auth_mode": "legacy"` を記録**する。

### Step 2：アプリのリリースと「サイレント・バインディング（無痛移行）」

ユーザーに再ログインを一切意識させず、アプリのアップデート後の初回起動時（またはフォアグラウンド復帰時）に裏側でハードウェア鍵への移行を行う。

```
【アップデート後の既存アプリ】                           【サーバー】
  │ (既存のログインTokenは保持したまま)                     │
  ├─ 1. バックグラウンドで Secure Enclave / StrongBox 鍵生成│
  ├─ 2. OSから Attestation 証明書チェーン取得               │
  ├─ 3. POST /v1/auth/attest                              │
  │     Header: [既存の有効なログインSessionToken]          │
  │     Body:   [PublicKey + Attestation証明書] ──────────>│ ① 既存Tokenで本人確認
  │                                                       │ ② Attestation検証
  │<─────────── 200 OK (device_id 発行・紐づけ完了) ───────┤ ③ ユーザーと物理鍵を結合

```

#### 実装のポイント（強制ログアウト回避の急所）

* **既存セッションを「身元保証人」として使う:**
  `/v1/auth/attest` を叩く際、ユーザーにID/パスワードを再入力させるのではなく、現在端末に保存されている既存のログインセッショントークン（またはリフレッシュトークン）をヘッダーに載せて送信する。サーバー側は「現在ログイン中の正当なユーザーからの端末登録要求である」と判定し、シームレスに公開鍵をそのユーザーIDへバインドする。

* **ノンブロッキング実行:**
  この鍵生成・登録処理はアプリのUIスレッドを止めず、バックグラウンドタスクとして非同期実行する。通信エラー等で失敗した場合は、次回のアプリ起動時に指数バックオフで自動リトライする。

### Step 3：シャドーモード（Shadow / Monitoring Mode）運用

新アプリが市場に浸透し始める期間（リリース後2〜4週間）は、新方式のハードウェア署名トークンを送信しつつも、万が一検証に失敗してもユーザーを弾かない「シャドーモード」で稼働させる。

1. **クライアントの挙動（二重ヘッダー送信）:**
   ハードウェア鍵登録が完了した端末は、5分寿命の短命JWTを取得し、業務APIを叩く際に「新ヘッダー（`X-Hardware-Token`）」と「従来のヘッダー（`X-API-Key` + 旧Session）」の両方を付与して送信する。

2. **サーバーの挙動（検証のみ・遮断なし）:**

   * ゲートウェイは `X-Hardware-Token` を検証し、`signCount` の不整合や有効期限切れがないかをチェックする。

   * **もし新トークンの検証に失敗した場合でも、直ちにエラー（401/403）にはせず、同時に送られてきた「従来のヘッダー」が正しければリクエストを通過させる。**

   * 同時に、メトリクス基盤（Datadog / CloudWatch等）へ「シャドー検証失敗ログ（端末機種、OSバージョン、エラー理由）」を出力する。

3. **移行判定基準（KPI）:**

   * 特定メーカーの安価なAndroid端末でKeyStoreのバグがないか、地下鉄移動中の通信断で `Idempotency-Key` が正しく機能しているかを分析・修正する。

   * **「ハードウェア鍵登録済みユーザーのシャドー検証成功率** $\ge 99.9\%$**」** を達成した時点でStep 4へ進む。

### Step 4：リスク階層（Tier）別の段階的強制（Progressive Enforcement）

シャドー検証で安定性が確認できたら、リモートコンフィグ（Feature Flag）を切り替え、サーバー側で段階的に「従来の静的APIキーのみのリクエスト」を遮断していく。

#### 第4.1段階：登録済み端末のダウングレード禁止（Pinning）

* **対象:** すでに一度でも Step 2 でハードウェア公開鍵をサーバーに登録したユーザー（`trust_state = enforced`）。

* **制御:** そのユーザーIDからの通信において、ハードウェア由来の短命JWTが含まれていない（従来の静的APIキーしか付いていない）リクエストが届いた場合、**「トークンを抜いて外部スクリプトから叩いている（ダウングレード攻撃）」とみなし、即時 `403 Forbidden` で遮断**する。

* **効果:** すでに新アプリへアップデートしたユーザーのアカウントは、この瞬間からAIスクリプト等による乗っ取り・API直接攻撃が100%不可能になる。

#### 第4.2段階：高機密API（Tier 1）での新方式必須化

* **対象:** 個人情報閲覧（マイページ）、決済、送金、パスワード・メールアドレス変更などの重要エンドポイント。

* **制御:** 未アップデートの旧アプリ（静的APIキーのみ）から Tier 1 API が叩かれた場合、HTTPステータス `426 Upgrade Required`（またはカスタムエラーコード）を返し、アプリ側で「セキュリティ強化のため、アプリを最新バージョンにアップデートしてください」というモーダルを表示する（ログアウトはさせない）。

### Step 5：レガシーAPIキーの完全撤廃（Decommission）

新バージョンのアプリ浸透率が **95%〜98%以上** に達した段階（リリースから約2〜3ヶ月後）で、最終的な「門の閉鎖」を行う。

1. **旧バージョンへの強制アップデート発令:**

   * アプリ起動時のバージョンチェックAPIにて、静的APIキーを使用している旧バージョンに対してストアへの誘導ダイアログを表示する。

2. **ゲートウェイでの静的APIキー受け入れ停止:**

   * APIゲートウェイの設定を変更し、すべての業務API（Tier 1 / Tier 2）において、ハードウェア検証を経た短命JWTを持たないリクエストを **無条件で `401/403` 破棄** する。

3. **コードからの静的キー抹消:**

   * サーバー側の環境変数・設定ファイルから旧静的APIキーの定義を完全削除し、マイグレーションを完了する。

## 4. 例外ケース・フォールバック設計（現場で必ず起きる問題への対処）

移行時、以下のエッジケースで正規ユーザーが締め出されないための救済措置を組み込む。

### ケースA：機種変更（データ移行・バックアップ復元）時の鍵消失

* **現象:** ユーザーがiPhoneやAndroidを新端末へ機種変更し、OSのバックアップ復元機能を使った場合、アプリのローカルデータ（設定や旧トークン）は引き継がれるが、**Secure Enclave / StrongBox 内の秘密鍵は物理チップ固有のため絶対に新端末へ引き継がれない**。

* **対処法:**

  1. クライアントは起動時、ローカルに保存している `key_id` でチップ内の秘密鍵が引けるか（`SecItemCopyMatching` 等）を確認する。

  2. 鍵が存在しない（＝機種変更された）と検知した場合、保持している既存の長期リフレッシュトークンを用いて再度 Step 2 の `/v1/auth/attest` を呼び出し、新端末のハードウェア鍵を「追加登録（または差し替え）」する。これにより機種変更時も再ログイン不要で移行できる。

### ケースB：ハードウェア非搭載の古いAndroid端末（TEEすら不安定な端末）

* **現象:** Android 7〜8世代の極めて古い端末や一部の特殊端末では、Key Attestation自体がサポートされていない、または証明書チェーンが破損している場合がある。

* **対処法:**

  * `/v1/auth/attest` でハードウェア非対応エラーが返った端末（全体の1%未満）については、即座に切り捨てるのではなく、`attestation_level = "software_fallback"` として登録する。

  * これらの端末には、厳格なレートリミット（通常の1/5の通信頻度制限）と行動監視をかけた「制限付き短命トークン」を発行し、正規ユーザーの最低限の利用を継続させつつ大量データ抜き取り（メガリーク）を防ぐ。

## 6

先ほど挙げた7つの欠陥・副作用を放置して本番投入すれば、攻撃者を防ぐ前に「正規ユーザーの締め出し（セルフDoS）」と「サポート窓口の炎上」でシステムが自괴します。

このアーキテクチャを現場で生き残らせるための核は、「異常検知時には権限（爆発半径）を最小化した上で、通信自体は止めずに縮退運転させる境界制御」**と、**「端末・サーバー間の状態不整合を自動で初期化する自己修復（Self-Healing）回路」の2つを最初から組み込むことです。

---

## 1. 大事な部分のまとめ（フェイルセーフ設計の3大原則）

1. **「全か無か（All-or-Nothing）」の排除と権限の段階的縮退**
* ハードウェア検証やRedisが落ちた際、「全員遮断（サービス全停止）」か「全員素通し（丸腰）」の二択にしてはいけません。「検証できない間は、閲覧・通常操作のみ許可し、重要操作（決済・個人情報変更・一括取得）のゲートだけを閉じる」というトークンスコープの動的縮小（Step-down）で逃がします。


2. **「鍵と状態の不一致」はクライアント主導で自己修復（Self-Healing）させる**
* 機種変更やOSバグによる鍵の消失は「エラー」ではなく「日常的に起きる状態遷移」として扱います。鍵が見つからない場合はアプリ側で自動的に古いメタデータを破棄し、裏側で新規鍵生成フローへフォールバックさせます。


3. **「端末の時計」と「単一メーカーの実装」を信用しない**
* クライアント側の時刻判定はすべてサーバー時刻からの相対オフセット（ズレ補正値）で計算させ、Androidの機種固有バグに対してはサーバー側からリアルタイムに検証レベルを降格できる「キルスイッチ（動的プロファイル）」を必ず用意します。

## 2. 7つの欠陥に対する具体的な「逃げ道（フェイルセーフ）」設計

### ① 【機種変更・OS復元時の鍵喪失】自己修復（Self-Healing）ステートマシン

クイックスタートやバックアップ復元で「ストレージ上の `key_id` は残っているが、Secure Enclave / StrongBox 内に秘密鍵が存在しない」状態を自動救済します。

```text
[アプリ起動 / トークン更新要求]
  │
  ├─ 1. ローカルの key_id でハードウェア秘密鍵の参照を試行
  │      ├─ 存在する ──> 通常の Assertion 署名へ
  │      └─ 存在しない (errSecItemNotFound / KeyStoreException)
  │            │
  │            ▼ ★自己修復フロー発動
  ├─ 2. ローカルの古い key_id キャッシュを即座に破棄（初期化）
  ├─ 3. ハードウェア内で「新しい鍵ペア」を生成 & 新規 Attestation 実行
  └─ 4. サーバーの「鍵ローテーションAPI (/v1/auth/key-rotate)」へ送信
         ├─ 既存セッショントークンが有効 ──> デバイス信頼度に応じて再バインド
         └─ セッション失効 / 高リスク判定 ──> 生体認証 / Passkey / SMS認証を1回だけ要求して再バインド

```

* **設計の急所**:
ハードウェアから「鍵がない」という例外が返った際、絶対にリトライ（再試行）させてはいけません。物理的に消えているため何度やっても失敗します。即座に「未登録状態」へステートを巻き戻す分岐を入れることで、機種変更ユーザーの詰みを100%防げます。

---

### ② 【無停止移行時の乗っ取り防止】リスクベース・バインディング制御

移行期間中（サイレント・バインディング時）に、漏洩済みの古いセッショントークンを使って攻撃者が自分の実機を登録してしまう「椅子取りゲーム」を防ぎます。

* **バインド時のコンテキスト照合**:
無条件で公開鍵を登録するのではなく、サーバー側で「既存のセッショントークンが過去30日間に通信していた特徴（IP帯・国・ASN・OS種別）」と、今回バインド要求してきた通信元を照合します。
* **段階的トラスト（仮登録と昇格）**:
* **一致する場合**: そのままサイレント・バインディングを完了（ユーザー操作ゼロ）。
* **不一致の場合（例：今までiOSだったのに突然Androidからバインド要求が来た、海外IPに変わった）**: サイレント登録を拒否し、画面上に「新しい端末の確認」として登録済みメール/SMSへのワンタイムコード確認、または再ログインを要求します。


* **1アカウントあたりの登録端末数上限と通知**:
1ユーザーに紐づけられるハードウェア公開鍵の上限（例：最大3台）を設定し、新規にハードウェア鍵がバインドされた際は必ずプッシュ通知やメールで「新しい端末が登録されました」と通知を出します（万が一先行されてもユーザーが気づいて解除できるようにする）。

---

### ③ 【Androidの破片化・機種固有バグ】リモート・デバイスポリシー（動的降格マトリクス）

「特定のAndroid機種（例: メーカーXのモデルY、OSバージョンZ）でStrongBoxがフリーズする・TEE証明書が壊れている」という現場の地雷を、アプリのアップデート審査なしで即日回避する仕組みです。

* **サーバー主導の「セキュリティプロファイル配布」**:
初回通信時（`/v1/auth/challenge`）に、端末の `Build.MODEL`、`Build.MANUFACTURER`、`OS Version` をヘッダーで送らせ、サーバー側が**その機種に要求するセキュリティレベル**を動的に返します。

| レベル | 適用対象 | クライアントの挙動 | サーバー側の検証 |
| --- | --- | --- | --- |
| **Level 3 (最高)** | iOS全般、Pixel/Galaxy等の検証済み機 | StrongBox必須 + Attestation | 完全検証 + `signCount` 厳格チェック |
| **Level 2 (標準)** | StrongBox非搭載の一般Android機 | TEE (ハードウェアKeystore) | TEE証明書検証 + `signCount` |
| **Level 1 (縮退)** | Keystoreバグが確認された特定問題機種 | ソフトウェア鍵ペア (アプリ内生成) | 公開鍵署名のみ検証（Attestation免除） |
| **Level 0 (緊急)** | OSアップデート直後の大規模不具合発生時 | 署名スキップ（一時バイパス） | 短命トークン + 厳格レートリミットのみ |

* **設計の急所**:
問題が起きた機種だけをサーバー側の設定ファイル（JSON/DB）1行で **Level 3 ➔ Level 1** へ即時降格（ダウングレード）できるようにします。これにより「特定のスマホを使っているユーザーだけがログインできない」というクレームを数分で鎮火できます。

### ④ 【Apple / Google サーバー障害・レートリミット】「仮設トークン（Provisional Token）」への逃がし

AppleのApp AttestサーバーやGoogleの認証基盤が落ちている、あるいはCM放送時などでレートリミットに達した際、新規登録や機種変更が全滅するのを防ぎます。

* **サーキットブレーカーと仮登録モード**:
1. クライアント側で `DCAppAttestService` がサーバーエラー（`serverUnavailable`）を返した場合、端末内の Secure Enclave で「Attestation（Appleの裏書き）なしの通常のECDSA鍵ペア」だけを生成します。
2. サーバーへ「Apple側の障害により裏書き取得失敗」というフラグと共に公開鍵を送信します。
3. サーバーはそれを **「未検証（Unverified）公開鍵」** として仮登録し、スコープを制限した **「仮設トークン（Provisional Token）」** を発行します。


* **仮設トークンの制限と遅延検証（Lazy Attestation）**:
* 仮設トークンでは、アプリの通常利用（閲覧、カート追加、ゲームプレイ等）はすべて許可し、換金性の高い操作や大量データ取得のみを制限（またはレートリミットを通常の1/5に絞る）します。
* 数時間後、Appleサーバーが復旧したタイミングで、アプリの裏側で再度 `attestKey` を実行し、正式な「検証済み（Verified）公開鍵」へ昇格させます。

### ⑤ 【端末の時計ズレ・バックグラウンド復帰】サーバー相対時刻とリクエスト・ゲート

ユーザーが端末の時計を手動でずらしているケースや、スリープ復帰直後の401エラー多発をクライアント側の通信層で吸収します。

#### A. 端末時計に依存しない「サーバー時刻オフセット」計算

端末の `Date()`（システム時刻）をそのまま使うのを禁止します。

```swift
// HTTPレスポンスの "Date" ヘッダーからサーバー時刻を取得し、端末時計との差分を記録
let serverTime = parseHTTPDate(response.allHeaderFields["Date"])
let localTime = Date()
self.clockOffset = serverTime.timeIntervalSince(localTime)

// 以降の署名タイムスタンプやトークン期限判定はすべて補正後の時刻を使う
func currentCorrectedTime() -> Date {
    return Date().addingTimeInterval(self.clockOffset)
}

```

これでユーザーのスマホの時計が1年ズレていようが、5分進んでいようが、サーバーと1秒の狂いもなく同期します。

#### B. バックグラウンド復帰時の「Single-Flight（合流）キュー」

スリープから復帰した瞬間に5本のAPIが同時に走り、全員が「トークン期限切れ！」と判定して5回更新を叩くのを防ぎます。

* 通信層のインターセプターで「トークン期限切れ」を検知したら、最初の1本だけが更新タスクを起動し、残りの4本はその非同期タスク（Promise / Task）の完了をメモリ上で待機（Await）させます。
* 更新が完了した瞬間に、待っていた5本全員に新しいトークンを配って一斉に発射します。

### ⑥ 【Redis障害・カウント巻き戻り】縮退検証モードと「自己同期（Auto-Resync）」

状態管理（`signCount` や `Idempotency-Key`）を担うRedisが落ちた際、全通信が死ぬのを防ぎます。

* **Redis障害時のフェイルソフト（署名のみ検証）**:
APIゲートウェイがRedisへの接続タイムアウト（例: 50ms以上応答なし）を検知した場合、自動的に **「ステートレス検証モード」** に切り替えます。
* **挙動**: `signCount` の比較と `Idempotency-Key` のチェックを一時的にスキップし、**「RDBまたはローカルメモリにキャッシュされた公開鍵によるECDSA署名検証」と「タイムスタンプ（±60秒以内）」だけ**でトークンを発行します。
* これにより、万が一Redisが全滅しても、物理チップの署名確認は維持したままサービスを無停止で継続できます。


* **カウント不整合（巻き戻り等）発生時の「再チャレンジ要求」**:
もし `currentSignCount <= storedSignCount` となった場合、即座にアカウントを永久BANするのではなく、特殊なエラーコード（`401 Counter_Out_Of_Sync`）を返します。
* 正規端末であれば、もう一度新しいチャレンジを取得して再署名すればカウンターがさらに進むか、あるいはサーバー側で「直近の有効な生体認証/セッション」を確認の上でサーバー側の `storedSignCount` を現在の値にリセット（再同期）します。

### ⑦ 【5分トークンの横取り（寄生攻撃）】軽量バインディングと行動異常スコアリング

マルウェアや不正プロキシに「正規端末が発行した5分間の短命トークン」を横取りされ、別環境のAIボットから高速連打される攻撃への対策です。

* **ネットワーク・フィンガープリントのトークン埋め込み**:
短命トークン（JWT）を発行する際、要求してきた端末の **「接続元IPアドレスのサブネット（またはASN番号）」と「TLSフィンガープリント（JA3/JA4ハッシュ）」** をJWTのクレーム（`cnf`）に焼き込みます。
* もし端末からトークン文字列だけを抜き取って、外部のクラウドサーバー（AWSやVPS上のPythonスクリプト）からAPIを叩こうとしても、「トークン発行時とASN（通信キャリア）やTLSの癖が違う」ため、APIゲートウェイで即座に弾かれます（DPoPのような毎回署名をせずとも、これだけで外部サーバーへの持ち出しは99%無力化できます）。


* **スライディング・レートリミットの絶対維持**:
仮に同一Wi-Fi内のPCからプロキシ経由で寄生されたとしても、Phase 1で敷いた「1トークン（1ユーザー）あたり1分間に最大Nリクエストまで」というゲートウェイの機械的上限を絶対に外さないことで、5分間に抜けるデータ量を数件〜数十件（メガリークには程遠い微細な範囲）に物理的に封じ込めます。

## 3. 要点（要約）まとめ：フェイルセーフ実装の全体マトリクス

| 欠陥シナリオ | 組み込むべき「逃げ道（フェイルセーフ）」 | 縮退時の防御ライン（爆発半径の制御） |
| --- | --- | --- |
| **1. 機種変更で鍵が消えた** | `KeyNotFound` 検知でローカルを初期化し、自動で新鍵生成＆再バインドへ遷移 | 既存セッション有効＋同一環境なら無停止、環境変化時はSMS/生体認証を1回要求 |
| **2. 移行期の乗っ取り** | バインド時に過去30日のIP/OS傾向を照合。不一致ならサイレント登録を拒否 | 不審な端末からのバインドは2要素認証（OTP等）を通さない限り拒絶 |
| **3. Androidの機種バグ** | サーバーから機種別プロファイル（Level 0〜3）を動的配布し、問題機種のみ検証降格 | ハードウェア検証を外した機種は、レートリミット上限を厳しくして監視 |
| **4. Apple/Googleの障害** | 裏書きなしの「仮設トークン（Provisional）」を発行し、復旧後に裏で遅延証明 | 仮設トークン中は決済・退会・個人情報変更などの重要APIのみロック |
| **5. 端末の時計ズレ** | HTTPレスポンスの `Date` ヘッダーと端末時計の差分（Offset）を常時補正 | 端末時計が何年ズレていてもサーバー時刻基準で正確に動作 |
| **6. Redisのダウン** | Redisタイムアウト時は `signCount` 確認をスキップし、公開鍵署名のみで通す | 数十秒間のリプレイ耐性のみ一時低下するが、外部からの偽造攻撃は引き続き遮断 |
| **7. 5分トークンの横取り** | トークン内に「発行時のASN/IP帯・TLSハッシュ」を焼き込み、別環境での使用を遮断 | 万が一同一ネットワーク内から悪用されても、レートリミットで大量取得を阻止 |

この「7つの逃げ道」を最初から仕様に組み込んでおくことで、「普段はハードウェア署名でAIボットを完全に締め出しつつ、障害時や機種変更時には柔軟に縮退してユーザーを絶対に締め出さない」
