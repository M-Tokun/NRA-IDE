動的鍵の更新・負荷制御・障害時運用の仕様

本書は、動的鍵の設計思想と仕様に従うシステムの運用契約を説明します。更新する対象と頻度、必要な状態保存、更新競合、再試行、処理枠、障害時の停止・再開を具体化します。認証・認可の必須条件は主文書と共通です。

〈推論〉本設計の位置付け

通常処理検証・判定完了・許可待機・再試行／推論・未決拒否・停止・異常

以下は、確認できた資料を根拠に、既存APIへ追加する改良部分を組み立てた設計案です。実サービスの構成・運用条件との適合は未確認です。根拠資料に記載された現況を、実環境で確認済みの事実として扱いません。

  • 推論：資料から導いた処理順序・分岐・改良ロジックです。設計上の提案であり、実装済み・安全性検証済みという意味ではありません。
  • 未決：実装前に責任者が決める条件です。保存先、保持期間、処理容量、障害時の扱い、外部処理との整合方法などは、対象サービスごとに決定します。
  • 未検証：実ブラウザでの描画・印刷、本番APIへの組込み、受入試験、負荷・障害試験は確認が残っています。

1. 運用上の設計思想

動的鍵の導入では、登録時の端末・本人確認、期限ごとの資格発行、各要求のproof検証に、それぞれ負荷が生じます。これらの発生頻度を分けて設計します。端末の秘密鍵は要求ごとに作り直さず、アクセストークンは期限まで利用し、DPoP proofだけを各HTTP送信で新しくします。

処理枠と時間の使い方で集中を抑えます。混雑を理由に署名、鍵拘束、失効、proofの再利用防止、対象認可を省略しません。静的キー廃止で減る不正通信も含めた総負荷の増減は、実測で判定します。

処理起きるタイミング主に使う資源本案での制御
端末鍵の生成と証明初回登録・承認された鍵更新端末の保護領域、OS別証明、登録正本登録専用枠。日常の業務呼出しと分離
アクセストークン発行初回認証・有効期限前の更新grant検証、発行署名、失効・更新・操作正本発行枠、ジッター、Single-Flight
業務APIの要求検証要求・再送・状態照会ごとJWT・DPoPの署名、鍵拘束、再利用・失効状態入口制限、公開鍵キャッシュ、署名確認後の状態記録
業務確定と結果返却新規操作・既存操作の照会業務DB、操作一意性、DTO、返却枠新規実行と照会を区別。実件数・実バイトを送信前に確定

2. 資格の有効期限と更新予約

access TTLはリスク、失効確認の仕組み、実容量、利用者の操作継続時間を根拠に決めます。短命化は盗用可能な時間を制限しますが、期限内の不正をすべて防ぐものではありません。Refresh Tokenを無期限・無拘束のBearerとして残せば、更新側に長期の危険が残ります。

端末はexpires_inを受信した時点の単調時計を基準に、通信時間の余裕とジッターを含む更新予定を作ります。休止・復帰で予定がずれた場合は資格状態を確認し直します。利用許可はサーバー時計と資格・失効の検証で決め、端末の時計変更で期限を延ばせないようにします。

制御項目本案の仕様
期限前更新設定した範囲で端末ごとに時刻をずらす。平常時から同時刻へ集中させない
Single-Flight同じセッション・更新資格に対する端末内の同時更新を1本へ合流
多端末端末間の同時更新はサーバーの一意受付・世代検証で扱う
自動更新の回数元の業務要求で401を受けた場合の自動更新は1回まで。新要求として制御状態を初期化しない
proofの生成更新、業務再送、結果照会の各送信で、新しいjtiとproofを作る
必須のtoken_typeDPoPを要求するプロファイルでBearerへ暗黙に降格しない

DPoPにおけるpublic clientのRefresh Token鍵拘束は RFC 9449 §5、再利用対策とローテーションの方針は RFC 9700 §4.14 を照合します。ローテーションを使う場合の旧値消費・新値確定・応答消失は、認証基盤と合わせた実装契約が必要です。

3. 発行量と状態保存量の計算例

以下は実測値でも推奨TTLでもありません。アクティブ端末を100万台、各端末が資格を継続使用し、更新周期が独立していると仮定します。平均発行率は台数を平均更新周期で割った値です。先行更新を期限の15〜60秒前へ一様に分散すると、平均の先行時間は37.5秒になります。

access TTL期限ちょうどの平均発行率先行更新ありの平均発行率先行更新による倍率
300秒1,000,000 ÷ 300 ≒ 3,333件/秒1,000,000 ÷ 262.5 ≒ 3,810件/秒8/7 ≒ 1.143
900秒1,000,000 ÷ 900 ≒ 1,111件/秒1,000,000 ÷ 862.5 ≒ 1,159件/秒24/23 ≒ 1.043
3,600秒1,000,000 ÷ 3,600 ≒ 278件/秒1,000,000 ÷ 3,562.5 ≒ 281件/秒96/95 ≒ 1.011

100万台が復旧後60秒で均等に更新すると平均約16,667件/秒となり、300秒TTL・先行更新なしの平均の5倍です。偏りがあればピークはさらに高くなります。平均値をそのまま受付枠にしません。

DPoPの再利用記録数は、記録対象の要求率と保持時間に依存します。例として、契約から算出した保持時間が60秒、保護API要求が20,000件/秒なら、約120万件を保持します。1件あたりのバイト数、インデックス、複製、削除負荷はこの件数に含めておらず、別途測定します。

4. 再利用防止・操作記録の保持と整合

保存対象スコープ消してよい条件障害時の動作
proofのjti検証領域・登録鍵・jti当該proofが全受入ノードで受理不能になり、安全余裕も過ぎた後一意受入を確認できない保護要求は停止
登録challenge・本人承認主体・登録操作・目的・鍵期限・単回使用と監査保持の契約による不明な承認や古い候補を有効化しない
操作記録とdigesttenant・主体・操作種別・operation_id再送・照会・外部突合の契約と監査保持を満たした後記録喪失を「未実行」とみなさない
失効と更新世代セッション・鍵・資格・更新family等残る資格への影響と保持契約を満たした後失効不明を有効とみなさない

本案はnonceの有無にかかわらずiatの受理窓を維持します。過去側の許容時間をW_past、未来側をW_future、ノード間時刻差・反映遅延等の保守余裕をMとすると、初回受入からの固定保持を使う場合の下限候補は W_past + W_future + M です。値と計算条件を設定契約に残します。受理窓だけを60秒と呼び、未来側許容を無視して60秒後に消す実装は採用しません。DPoP再利用防止 RFC 9449 §11.1

ストアを鍵等で分割しても、同じスコープのproofは必ず同じ一意判定へ到達させます。分断時に各ノードが独立して成功を返す方式では、単回受入を成立させません。正本と任意キャッシュを区別し、復旧時には巻き戻り・未反映・失効世代も照合します。

operation_idの保持はproofの短い保持時間とは別です。契約終了後の古い操作ID再提示も、新規実行として無条件に受理しないよう、利用可能な期間と終了後の応答を定めます。

5. 入口制御・処理枠・共有資源

入口ではサイズ、接続、同時実行、待ち行列、deadlineを安価に確認し、許容量を超えた要求を高コストの検証へ進めません。未認証ヘッダーの主体を、正規利用者の優先枠の根拠にしません。資格検証後に、主体・tenantごとの制限を適用します。

制御・監査失効、観測、縮退、監査の永続化混雑中も停止判断と記録を続ける

CPU、DB接続、状態ストア、回線ごとに、枠の合計と予約分が実容量を超えないようにします。同じ単位で能力100に対して発行80・業務40を許可すると合計120です。専用枠という名称だけでは共有資源の枯渇を防げません。

公開鍵は設定済みの発行者から取得してキャッシュします。未知kidや鍵更新失敗で検証鍵を確認できない要求は拒否・保留し、取得の連打を合流・制限します。署名を確かめる前にjtiストアへ書き込ませず、入力長も制限します。任意URLの鍵取得や未知鍵の許可へ切り替えません。RFC 8725

6. 再試行と応答の分類

端末は応答を受けてから、成功、認証失敗、nonce要求、混雑、処理中、結果不明を分類します。503・429を受けなかったことだけで成功とは判定しません。元業務のoperation_id、更新操作ID、要求種別、回数、全体期限、更新済みフラグを保持します。

応答・状態端末が行う処理サーバー側の契約
発行成功token_type・必要な項目・有効条件を確認して保存未確定の候補資格を応答しない
401・期限切れ元業務で未実施なら更新を1回だけ行う期限切れと別の認証失敗を区別できるエラー契約
DPoP nonce要求対応する発行元・用途のnonceで新proofを作る資格再発行とは別に扱い、回数・期限を制限
403・認可拒否自動更新で権限を得ようとせず停止データや操作の存在を不用意に漏らさない
429・入口での503Retry-After、ジッター、指数バックオフ。上限超過で停止未受理と表示できるのは業務副作用を起こす前に拒否した場合
202等・PENDING同じ操作IDで有限の照会照会可能な主体へ、許可した状態情報だけ返す
通信断・UNKNOWN同じ操作IDで照会・突合成功・未実行を推定せず、新IDの重複実行を防止
409・内容不一致元記録を確認し、自動再実行を止める同IDのdigest不一致で元記録を上書きしない
その他・未分類安全側に停止し、利用者へ状態を案内未分類の応答を成功にしない

Retry-Afterが全体期限を超える場合は、期限を延ばして待ち続けません。混雑応答と通信断では、業務が確定済みかどうかの知識が異なります。HTTPステータスだけに依存せず、契約した操作状態で判断します。資格発行の応答消失も、同一発行操作の照会・再受取契約へ従います。

7. 障害からの段階再開

再開条件は、待ち行列長、最古の待機時間、状態ストア遅延、欠測、結果不明操作の整合、設定した継続時間を合わせて判断します。CPUの瞬間値だけでは再開しません。

8. 返却量と観測・設定の仕様

DTOを構築した後、実件数とUTF-8本文バイト数を送信前に確認します。バイト数を確定する表現、圧縮前後のどちらを数えるか、HTTPヘッダーの扱い、一覧・export・streamingの上限は経路台帳で固定します。streamingは、総量の上限を保証する専用契約を確定するまで通常の返却経路へ混在させません。

受付時の見積りや予約だけで最終検査を代替しません。返却枠の不足や正本不明で送信を止めても、確定済みの更新・決済は保持し、操作IDで結果照会できる状態を残します。

proof過去・未来の受理窓、nonce用途・期限、保持余裕、最大長、正本の一意性
再試行最大回数、全体deadline、バックオフ、Retry-Afterの扱い、更新済みフラグ

設定には単位、取得元、欠測時動作、版、変更権限、根拠を持たせます。未設定値をゼロや無制限へ変換しません。ログには操作IDと理由コードを残し、アクセストークン、Refresh Token、秘密鍵、proof全文は出力しません。監査不能時の保護操作の扱いも、台帳で事前に決めます。
