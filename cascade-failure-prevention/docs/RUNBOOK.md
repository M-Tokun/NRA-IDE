## 1. 運用者がやること・やらないこと

### やること

- ゲートがデプロイされ、入口（Envoy/Nginx）に統合されているか確認する

- **SILENCE 発生率**と**連鎖反応シグナル**を監視する

- 対象サービス・経路・クラスタの実測を確認したうえで、必要なら CHAIN_SCORE_LIMIT や GAIN_BASE の変更を設計レビューする

- インシデント後にイベントログをレビューする

### やってはいけないこと

- 「レイテンシを改善しよう」としてリトライを増やす

- ゲートのロジックに ML・自動調整フィードバックを追加する

- 連鎖が始まっているときにゲートを無効化する

- 平均レイテンシだけを主要トリガーとして使う

## 2. 日次確認項目

- `/healthz` が OK を返しているか

- 判定エンドポイントがプロキシから呼び出せるか

- ConfigMap の CHAIN_SCORE_LIMIT / GAIN_BASE / GAIN_EMA_ALPHA / GAIN_AMPLIFY_LIMIT が意図した値か、稼働中 Pod に反映済みか

---

## 3. よくある障害パターンと期待される動作

**パターン A: 依存先タイムアウトが増え始め、リトライが続く**  

→ 非正典スコアがローカル閾値に達するか、HOLD 中なら SILENCE します。現行ゲートに WATCH 状態はありません。

　これだけでアップストリームの安定や連鎖停止は保証できません。

**パターン B: キューが急増しリトライストームが発生**  

→ スコア閾値到達時、または入力不備による Fail-Closed 時に SILENCE になります。

　再開には HOLD_MS 経過と、以後の判定でスコアが閾値未満であることが必要です。

## 5. SILENCE が多すぎる場合

### SILENCE 発生率の旧版目安（現行の普遍的な安全基準ではない）

下表は旧版文書の運用例として残します。対象ごとの観測期間、母数、被害・誤検知コストが未定義のため、これだけで「正常」「安全」を判定しません。

| 発生率 | 状態 | 対応 |
|---|---|---|
| 0〜1% | 旧版では「正常」と表現 | 現行では単独判定に使わない |
| 1〜5% | 注意 | 監視を強化する |
| 5%超 | 設計レビュー要 | 週次レビューで調整を検討 |

### 調整パターン（週次設計レビューで実施。インシデント中は変更しないこと）

以下は同じ入力・EMA状態を固定した場合の方向です。設定のロールアウトではプロセス内の EMA と HOLD が初期化されるため、変更前後を実測で比較します。

**より緩くする（SILENCE を減らす）：**

- CHAIN_SCORE_LIMIT を上げる: 1.0 → 1.5（スコア閾値を高くする）

- GAIN_BASE を下げる: 1.5 → 1.0（スコア補助倍率を下げる。正典の吸収厚みτではない）

- GAIN_EMA_ALPHA の変更方向だけでは判定の厳しさは決まらない（現在値と直前 EMA の関係を確認）

**より厳しくする（SILENCE を増やす・早くする）：**

- CHAIN_SCORE_LIMIT を下げる: 1.0 → 0.7

- GAIN_BASE を上げる: 1.5 → 2.0

- GAIN_AMPLIFY_LIMIT を上げると、上限にかかっていた場合だけスコアが増え得る

### 非正典スコアの EMA 補助倍率について

**GAIN_EMA_ALPHA（0 < α ≤ 1）**

「最近の状況をどれくらい重視するか」の感度です。  

大きいほど現在の共起値に近づきます。現在値が直前 EMA より高いと上昇が速く、低いと低下が速くなります。

旧版にあった「安定環境には 0.1〜0.2、変動環境には 0.3〜0.5」という目安は領域根拠・実測の確認前には推奨値としません。

**GAIN_AMPLIFY_LIMIT（1 以上）**

EMA によるスコア補助倍率が GAIN_BASE の何倍まで大きくなれるかの上限です。正典のτではありません。

2.0 はコードの既定値であり、ほとんどの環境に適合することは未検証です。

上限に達している場合、値を上げるとスコアは大きくなり得ます。遅い反応を意味しません。

### ConfigMap 変更の反映

この配置は `envFrom` で設定を渡すため、ConfigMap を変更しても稼働中 Pod の環境変数は自動更新されません。管理された Deployment のロールアウト後に、新しい Pod の設定と判定を確認します。Kubernetes の[公式説明](https://kubernetes.io/docs/tutorials/configuration/updating-configuration-via-a-configmap/)も環境変数は次のロールアウト後に反映されるとしています。

EMA と HOLD は各 Pod のプロセス内メモリにあり、Pod 間では共有されず、再起動時には失われます。複数レプリカ全体の共通 HOLD としては扱えません。

### 未解決の可用性リスク

外部入力から任意の `scope` 値が `/v1/decision` に到達し得る配置では、スコープ別 EMA 状態が件数制限なく増加し、メモリ枯渇によって正規の判定も提供できなくなる可能性があります。

### 調整前のチェックリスト

- テレメトリが欠損していないか（欠損 → 保守的になる）

- SILENCE が実際の連鎖を防いでいたか（ログを確認）

- アップストリームサービスは正常か（問題を隠していないか）

## 6. SILENCE が一度も発生しない場合（点検）

発生ゼロだけでは安全・危険のどちらも確定しません。観測期間、入力値、プロキシ経路、閾値設定を確認します。

- 実測と対象範囲を確認し、必要なら CHAIN_SCORE_LIMIT を下げる

- GAIN_BASE と GAIN_AMPLIFY_LIMIT の設定が意図どおりか確認する

- プロキシ統合（ext_authz / auth_request）が実際にゲートを呼んでいるか確認

---

## 7. ロールバック手順

- プロキシ側の ext_authz / auth_request の呼び出しを無効化する

- ゲート自体は削除しないこと（ロールバックを元に戻せるようにしておく）
