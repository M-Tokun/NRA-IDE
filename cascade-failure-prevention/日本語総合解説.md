## 📌 エグゼクティブサマリー（3行で）

1. **カスケード障害（連鎖的システムダウン）を、人間判断なしで自動防止**するシステムです

2. 従来の「頑張って復旧」ではなく、**連鎖が始まったら入口を自動で沈黙**させます

3. これにより**判断遅延事故（人が決断する前に全体崩壊）がゼロ**になります

## 🔧 何の運用のためのシステムか

### 目的：カスケード障害の構造的防止

**カスケード障害とは**：

- 一部の遅延・エラーが **連鎖的に増幅** してシステム全体が崩壊する現象

- 例：API遅延 → クライアント再送 → さらに詰まる → 全体ダウン

**従来の運用**：

```

障害発生 → アラート → 人が状況把握 → 判断 → 操作 → 復旧

       ↑____________ この間に連鎖拡大 ____________↑

```

**HAN Gate運用**：

```

連鎖開始 → 自動検知（0.1秒以内） → 入口沈黙 → 連鎖停止

       ↑________ 人は呼ばれない ________↑

```

### 適用対象システム

1. **Webサービス / API基盤**

   - マイクロサービスアーキテクチャ

   - 依存関係が複雑な分散システム

   - トラフィック急増時の安全弁

2. **クラウドインフラ**

   - Kubernetes クラスタ

   - サービスメッシュ（Istio / Linkerd等）

   - Load Balancer / Ingress 層

3. **ミッションクリティカルシステム**

   - 決済処理

   - 在庫管理

   - 予約システム

### コアコンポーネント

#### 1. HAN Gate Service（判定核）

**役割**：telemetryを受け取り、連鎖反応の兆候を検出して PASS/SILENCE を返す

**実装言語**：Python（Flask）

**核心ロジック**：

```python

# ※ これは概念説明用の簡略コードです。

# ※ 実装版（二重ゆらぎ対応・scope_key 引数あり）は gate/han_gate_service.py を参照してください。

def compute_R(telemetry, tau):

    """

    連鎖反応スコア R の計算

    retry × queue × timeout の同時発生を検出

    """

    retry = telemetry["retry_rate"]    # 再送率

    queue = telemetry["queue_depth"]   # キュー深度

    dep_to = telemetry["dep_timeout_rate"]  # 依存タイムアウト率

    

    # 正規化（軽微）

    r = (retry / 10.0) * (queue / 500.0) * (dep_to / 5.0)

    

    # τ（厚み）で保守性調整

    return r * tau

def should_silence(R, R_OP):

    """

    閾値判定（Fail-Closed）

    """

    if R >= R_OP:

        return True  # SILENCE（入口遮断）

    return False  # PASS（通過）

```

**重要な特性**：

- **決定論的**：同じ入力なら必ず同じ出力

- **Fail-Closed**：不明・欠損時は常に SILENCE

- **人間判断ゼロ**：閾値は設計時に一度だけ決定

#### 2. Telemetry収集（3パターン）

##### A. Envoy統合（推奨）

**役割**：Envoy admin stats から自動収集

```python

def scrape_envoy_stats():

    # Envoy admin endpoint (/stats?format=json) を取得

    stats = requests.get(f"{ENVOY_ADMIN}/stats?format=json")

    

    # 以下を抽出

    # - upstream_rq_retry（再送カウンタ）

    # - upstream_rq_pending_total（キュー深度）

    # - upstream_rq_timeout（タイムアウトカウンタ）

    

    # レート計算（差分 / 時間）

    retry_rate = (current_retry - last_retry) / dt

    

    return {

        "retry_rate": retry_rate,

        "queue_depth": queue_depth,

        "dep_timeout_rate": timeout_rate

    }

```

**配置**：Envoyと同一Podに sidecar として配置

##### B. Nginx統合

**役割**：OpenResty Lua で軽量メトリクス収集

```lua

-- 共有メモリでカウンタ管理

lua_shared_dict han_metrics 1m;

-- レスポンス後にカウンタ更新

log_by_lua_block {

    local metrics = ngx.shared.han_metrics

    local status = tonumber(ngx.var.status)

    

    if status >= 500 or status == 408 or status == 504 then

        metrics:incr("retry_count", 1, 0)

    end

}

-- auth_request時にレート計算してHeaderに注入

set_by_lua_block $retry_rate {

    local metrics = ngx.shared.han_metrics

    local retry = metrics:get("retry_count") or 0

    local dt = ngx.now() - last_update

    return retry / dt

}

```

### 具体的な運用比較

#### シナリオ：API遅延からの連鎖障害

**従来の運用フロー**：

1. 依存APIが遅延（5秒 → 10秒）

2. クライアントがタイムアウト → **再送**

3. 再送が増加 → キューが溢れる

4. 監視アラート発火（平均レイテンシ上昇）

5. 運用者が状況確認（5-15分）

   - ログ確認

   - メトリクス分析

   - 依存関係調査

6. 判断：「どのサービスを止めるか」

7. 操作：手動でトラフィック制限 or 再起動

8. **この間に全体崩壊**

**問題点**：

- ❌ 再送が連鎖を加速

- ❌ 判断に時間がかかる（人間の認知限界）

- ❌ 夜間・休日は対応遅延

- ❌ 「判断が遅い人」問題

---

**HAN Gate運用フロー**：

1. 依存APIが遅延（5秒 → 10秒）

2. クライアントがタイムアウト → **再送**

3. Telemetry収集（Envoy/Nginx）

   - `retry_rate` ↑

   - `queue_depth` ↑

   - `dep_timeout_rate` ↑

4. HAN Gate判定（**0.1秒以内**）

   - `R = compute_R(telemetry, tau)`

   - `R >= R_OP` → **SILENCE**

5. 入口で新規リクエスト遮断

   - 既存リクエストは自然終了

   - 再送を禁止（204 or 403応答）

6. **連鎖停止**（キュー減少）

7. `R < R_OP` 検出 → 徐々に再開

**人間の役割**：

- ✅ 事後ログ確認のみ

- ✅ 閾値調整（稀）

- ✅ **判断・操作なし**

### 技術的比較

#### 1. 監視・判断メカニズム

| 項目 | 従来（Prometheus/Grafana等） | HAN Gate |

|-----|--------------------------|----------|

| **観測対象** | 平均値・パーセンタイル | 連鎖の同時発生 |

| **メトリクス** | レイテンシp95, エラー率 | retry × queue × timeout |

| **閾値設定** | 静的（固定値） | 動的（τで保守性調整） |

| **判断ロジック** | if-then ルール（手動作成） | 連鎖反応関数（数学的定義） |

| **反応速度** | 数十秒〜数分 | 0.1秒 |

| **誤検知対策** | 複雑なルール追加 | Fail-Closed（安全側に倒す） |

**従来の問題**：

```python

# 従来の監視ルール例

if latency_p95 > 5000:  # 5秒

    alert("High Latency")

```

→ 平均が正常でも連鎖は起きる（見逃し）  

→ 単発の遅延でも発火（誤検知）

**HAN Gateの検出**：

```python

# 連鎖の本質を捉える

if (retry ↑) AND (queue ↑) AND (timeout ↑):

    SILENCE  # 3つ同時 = 連鎖開始

```

→ 単発では反応しない  

→ 連鎖開始を確実に検出

#### 2. 復旧戦略

| 項目 | 従来 | HAN Gate |

|-----|-----|----------|

| **基本方針** | 積極的復旧（リトライ・再接続） | 沈黙による連鎖停止 |

| **リトライ** | 推奨（Exponential Backoff） | 禁止（連鎖源になるため） |

| **サーキットブレーカー** | 個別サービス単位 | 入口全体（構造的） |

| **復旧判定** | ヘルスチェックOK | 連鎖指標の自然減衰 |

| **復旧速度** | 即時（Full Open） | 段階的（RECOVER状態） |

**従来のサーキットブレーカー問題**：

```python

# マイクロサービスAがBを呼ぶ

try:

    response = serviceB.call()

except Timeout:

    circuit_breaker.record_failure()

    if circuit_breaker.is_open():

        return fallback_response()

```

→ サービスBだけ保護（Aは詰まる）  

→ 連鎖は止まらない

**HAN Gate**：

```python

# Ingress層で一括防御

if R >= R_OP:

    SILENCE  # 全入口で新規停止

```

→ システム全体を保護  

→ 連鎖源を根本遮断

## ⚠️ 導入時の重要な理解事項

### 1. UXへの影響（正直な告白）

**HAN Gateは意図的にUXを犠牲にします**：

- 一部リクエストは **204 No Content** や **403 Forbidden** で応答

- ユーザーには「一時的に利用不可」と見える

- これは **仕様であり、バグではありません**

**トレードオフ**：

- 犠牲：一部ユーザーの一時的不便

- 獲得：全体崩壊の回避

### 2. 「頑張る復旧」の否定

従来の美徳：

- リトライで粘り強く

- 負荷分散で最適化

- サービス維持のために努力

**HAN Gateの思想**：

- リトライは連鎖の加害者

- 最適化は破断を見逃す

- **沈黙が正義**

これは **文化的な転換** を要求します。

### 3. 設計判断 vs 運用判断（重要な区別）

HAN Gateでは「判断」を2種類に厳密に分けます：

#### 設計判断（Design Decision）

**いつ**：週次・月次のレビュー  

**誰が**：SRE/基盤チーム（計画的）  

**内容**：

- R_OP / TAU 閾値の調整

- 対象スコープの追加・除外

- SILENCE率の目標設定

**これは許容されます**（むしろ必須）

#### 運用判断（Operational Decision）

**いつ**：障害発生時・リアルタイム  

**誰が**：誰も（システムが自動判定）  

**内容**：

- 「今この瞬間に止めるか」の判断

- リトライするかの判断

- どのサービスを遮断するかの判断

**これは完全排除されます**

---

**よくある誤解**：

❌ 「閾値を調整する = 運用判断」  

⭕ 閾値調整は**設計判断**（計画的レビュー）

❌ 「人間は一切関与しない」  

⭕ 設計時は人間が責任を持つ、運用時は関与しない

❌ 「完全自動化 = 思考停止」  

⭕ 設計時の深い思考が、運用時の即応を可能にする

この区別を理解しないと、「調整できるなら結局人間判断では？」という誤解が生じます。

---

### 4. 経営判断としての受容

導入には以下の覚悟が必要：

✅ 「止まること」を許容する  

✅ 「完璧なUX」より「構造安全」を優先  

✅ 短期的不便 vs 長期的安定のトレードオフ
