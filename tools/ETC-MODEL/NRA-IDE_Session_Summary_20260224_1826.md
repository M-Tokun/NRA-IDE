## 2. ドキュメント別 重要追加事項

### 2.1 Automotive Scope v0.2 への追加（◯２６〜◯２８）

**追加 3 点：**

```
① τ 設定根拠の文書化（Section 5.1）
   τ の数値だけでなく「なぜその値か」の根拠を
   物理試験・法規・インシデントデータで記録する義務

② Gear 連鎖の自動車版（Section 5.2）
   AND ではなく OR
   1 つの Gate でも R≥1.0 なら全系統停止

③ ISO 26262 との位置づけ（Section 5.3）
   時間軸が異なる補完関係
   ISO 26262 = 設計時保証
   NRA-IDE   = 実行時保証
```

### 2.2 Connection vs Mixing デモ（◯２５）

```
左（接続OK）: τ 固定・R≥1.0 で必ず FAIL-CLOSED
右（混用NG）: τ が動的変化・R が偽装される

同一スライダー入力で両者の動作差をリアルタイム可視化
「賢い安全装置が危険な理由」を体感できる構造
```

### 2.3 OTA Gate 検証プロセス（◯３０）

```
更新クラス分類（核心）:
  A: τ 変更        → Gate 全再検証
  B: Gate ロジック → Gate 全再検証 + 機能安全レビュー
  C: 制御層のみ    → 接続点確認のみ
  D: UI/ログ       → Gate 検証不要

Gate の更新は「ソフトウェア更新」ではなく
「安全保証の再発行」
```

### 2.4 AUTOSAR 統合 v0.2 への修正（◯３４）

```
v0.1 の問題:
  「禁止すべきは方向」という粗すぎる定義

v0.2 の修正:
  「禁止すべきは目的」

  τ・ロジックへの書き込み    → 禁止
  R 値・状態の読み取り        → 許可（診断に必要）
  開発ツールからの τ 書き込み → 開発環境のみ条件付き許可

  キャリブレーション・OBD 診断・前周期 R 利用が可能になった
```

### 2.5 V2X Gate 共有設計（◯３５）

```
核心原則:
  Gate は自車センサーのみを入力とする
  V2X 情報は制御層への入力として使うが
  Gate の τ・ロジックには届かせない

最大の発見:
  Gate が V2X に依存しない設計が
  最強のセキュリティ対策になる
  = 攻撃者が Gate を操作する経路が存在しない

通信断 4 レベル安全階層:
  Level 1: V2X 正常
  Level 2: 瞬断（キャッシュ利用）
  Level 3: 長断（制御層が速度補償）
  Level 4: 完全切断（Gate 単独自律動作）
  → どのレベルでも Gate の τ は固定
```

## 3. 会話から生まれた発見 / Discoveries from Discussion

### 3.1 トラクタ自動操舵の GNSS 断（◯３６〜◯３８）

```
10m で切れる設計:
  RTK 断 → 即時 FAIL-CLOSED（最悪ケース設計）

数十 m 走れる設計:
  RTK 断 → IMU 補間継続 → ドリフト限界で停止

「切れた瞬間」は設計時にしか決められない
実行時の切り替えは不可能
= どちらかしか選べない設計上の一択

τ 設定の「正解」は事後にしかわからない
→ NRA-IDE は正しい τ を与えない
→ 「決めた τ を裏切らない」だけ
```

### 3.2 医療における閾値（◯３９〜◯４０）

```
医療の実質的な Zone 再定義:
  R=0.65 前後が実用上限
  R=0.8 は「もう限界を超えている」感覚

なぜ R=0.8 が怖いか:
  患者急変は突然来る
  余裕 20% では急変速度に追いつけない

医療での NRA-IDE の正しい役割:
  FAIL-CLOSED の前に「医師への通知」を発動
  = 「いつ医師を呼ぶか」を構造的に定義する装置

R=0.8 を人間が設定したらその時点でアウト:
  → τ 設計の責任は NRA-IDE の外にある
  → Section 5.1（根拠文書化）が最大の抑止力
```

### 3.3 ログレコーダーの意義（◯４１）

```
フライトレコーダー: 「何が起きたか」を記録
NRA-IDE Discard Log: 「なぜその閾値だったか」まで遡れる

最大の効果は抑止力:
  「このログは証拠になる」と知っている状態で
  根拠なき τ 緩和はできない

NRA-IDE は「安全装置」ではなく
「責任の構造化装置」
```

### 3.4 小型核融合炉のプラズマ監視（◯４２〜◯４３）

```
NRA-IDE の適用限界の発見:

プラズマ崩壊（Disruption）:
  1ms 以内に崩壊
  FAIL-CLOSED が物理的に間に合わない
  δ・τ の決定論的計算が困難

NRA-IDE の貢献範囲:
  プラズマ本体 → Gate 不可
  周辺環境（冷却・磁場・真空・壁）→ Gate 可能

設計思想の転換:
  「プラズマを制御する」から
  「崩壊が起きても周囲が耐えられる状態を保つ」へ
```

### 3.5 福島原子炉の教訓（◯４４〜◯４５）

```
伝播経路の遮断が機能しなかった理由:
  多重防護の各層が
  同じ単一障害点（全電源喪失）に依存していた
  = 多重に見えて実は単一

NRA-IDE への追加原則:
  Rule F: Gate の動力・通信・判定ロジックは
          保護対象システムから独立させる

  Rule G: 複数 Gate が同一の単一障害点を
          共有していないか検証する

  Rule H: 「多重防護」は独立した障害モードを
          持つ場合のみ有効

守るべきものと守る仕組みを
同じ場所に置いてはいけない
```

### 3.6 最大の発見（◯４６）

```
リスクが高く緻密であるほど
周辺まで含めて最初から一体として設計しなければ
主役システムの設計自体が成立しない

今まで書いてきた設計の順序が逆だった:

書いてきた順序（誤）:
  主役システム → 周辺環境（後から）

本来の順序:
  「何が崩壊しうるか」の定義
      ↓
  「崩壊の伝播をどこで遮断するか」
      ↓
  「各遮断点にどの Gate を置くか」
      ↓
  「主役システムの設計」

NRA-IDE の根本再定義:
  Gate は「後から付ける安全装置」ではなく
  「世界の構造そのものの境界」

  Gate の位置から設計を始める
```
