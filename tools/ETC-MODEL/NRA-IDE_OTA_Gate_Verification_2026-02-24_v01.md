## 0. 本文書の目的 / Purpose



OTA（Over-The-Air）ソフトウェア更新は  

**「更新後に NRA-IDE Gate の保証が存在するか」**  

を破壊する可能性を持つ唯一の運用操作である。



本文書はその危険を構造的に防ぐための  

分類・手順・禁止事項・責任記録を定義する。



> **核心原則 / Core Principle**  

> Gate が動作中に Gate を変更してはならない。  

> You must not modify a Gate while it is operating.



---



## 1. なぜ OTA が Gate に危険か

## Why OTA is Dangerous to Gates



通常のソフトウェア更新とNRA-IDE Gateが共存する場合、以下の問題が発生しうる。



```

問題 1: τ 値の無断変更

  制御ソフトウェアの更新パッケージに

  τ の変更が「混入」する

  → 検証なしに保証の境界が変わる



問題 2: Gate ロジックの静かな置き換え

  「パフォーマンス改善」という名目の更新で

  Gate の判定アルゴリズムが変わる

  → 変更前後で R の計算結果が異なる



問題 3: 更新中の Gate 空白期間

  更新プロセス中に Gate が一時停止する

  → その間に物理的な危険が発生する可能性



問題 4: ロールバック時の Gate 不一致

  更新失敗でロールバックしたとき

  Gate のバージョンと制御層のバージョンが

  噛み合わない状態になる

```



```

すべての問題の根本:

  「Gate も普通のソフトウェアと同じ」という

  誤った前提で OTA を設計すること



正しい前提:

  Gate は物理的なブレーカーと同等に扱う

  ブレーカーの交換中に電流を流さないように

  Gate の更新中は Gate を止めない

```

## 2. 更新対象の分類 / Update Classification



OTA 更新パッケージを以下の4クラスに分類し、  

クラスに応じた Gate 検証プロセスを適用する。



| クラス | 更新内容 | Gate への影響 | 必要な検証 |

|--------|----------|-------------|-----------|

| **A** | τ 値の変更 | **直接** | Gate 全再検証 + τ 設定根拠の更新 |

| **B** | Gate ロジックの変更（R計算・閾値判定） | **直接** | Gate 全再検証 + 完全テスト |

| **C** | 制御層のみの変更（AI・最適化・経路計画） | 間接（接続点を確認） | 接続点の動作確認のみ |

| **D** | UI・ログ・通信フォーマットのみの変更 | **なし** | Gate 検証不要 |



> **クラス判定責任者：** ソフトウェアアーキテクト（Gate 設計者と兼務不可）  

> **判定記録：** 更新パッケージごとに分類根拠を文書化・保管必須

## 3. 検証プロセス手順 / Verification Process



### 3.1 配信前（Pre-deployment）



```

Step 1: クラス判定

  □ 更新パッケージの差分を解析

  □ τ 値・Gate ロジックの変更有無を確認

  □ クラス A / B / C / D を判定・記録



Step 2: ステージング環境での Gate 動作確認（クラス A / B のみ）

  □ 既知の入力値セットで R 計算結果を確認

  □ FAIL-CLOSED 発動条件が変わっていないか確認

  □ 変更前後の R 値を比較・記録

  □ τ 変更の場合は設定根拠ドキュメントを更新



Step 3: ロールバック条件の定義

  □ どの状態になったらロールバックするかを事前定義

  □ ロールバック後の Gate バージョン整合性を確認

  □ ロールバック手順をチェックリスト化

```



### 3.2 配信中（During deployment）



```

Step 4: Gate の安全停車確認

  □ 車両が停止状態であることを確認

     （クラス A / B の場合は走行中適用禁止）

  □ Gate の現在の R 値がすべて Zone A であることを確認

  □ 更新開始ログに Gate 状態スナップショットを記録



Step 5: 更新の適用

  □ 更新パッケージの整合性ハッシュを確認

  □ Gate 関連モジュールの更新完了を確認

  □ 更新完了ログを記録（タイムスタンプ・バージョン・担当者）



Step 6: 起動後即時確認

  □ Gate が正常に起動したことを確認

  □ 既知入力での R 計算結果を確認（ステージングと一致するか）

  □ Discard Log が正常に出力されているか確認

```



### 3.3 配信後（Post-deployment）



```

Step 7: 運用中の Gate ログ照合

  □ 更新前後 24 時間の Discard Log を比較

  □ 異常な Zone 遷移が増加していないか確認

  □ τ 変更の場合: R 分布の変化が想定範囲内か確認



Step 8: 問題発生時のエスカレーション

  □ Gate の異常動作 → 即時ロールバック

  □ ロールバック後もゲート異常 → 走行禁止・点検

  □ 根本原因分析（RCA）の実施と記録

```

## 4. 禁止事項 / Prohibitions



以下は NRA-IDE の設計原則から導出される OTA における絶対禁止事項である。  

いかなる業務上の理由があっても例外を認めない。



```

禁止 1: 走行中の Gate 更新（クラス A / B）

  理由: Gate が動作中に Gate を変更すると

        空白期間が発生する

        ブレーカー交換中に電流を流すのと同じ



禁止 2: τ 変更を制御層更新パッケージに混在させること

  理由: τ の変更がレビューを回避するリスクがある

        τ 変更は必ず単独パッケージとして分離する



禁止 3: ステージング未確認の Gate 更新の本番適用

  理由: Gate の動作確認なしの更新は

        保証なしの安全装置を運用することと同義



禁止 4: Discard Log を更新判断の根拠に使用すること

  理由: Log は構造検証のみ

        「前回の Log で問題なかったから更新してよい」

        という判断は因果ダイオードの逆流



禁止 5: Gate バージョンと制御層バージョンの不一致での運用

  理由: 接続点の整合性が失われると

        「接続（OK）」が「混用（NG）」に変質する

```

## 5. 責任所在の記録 / Responsibility Records



Gate に関わる更新はすべて以下の記録を残す。  

記録なき更新は「存在しない更新」として扱う。



### 5.1 必須記録項目



| 記録項目 | 記録タイミング | 保管期間 |

|----------|--------------|---------|

| 更新クラス判定（A/B/C/D）と根拠 | 配信前 | 永久 |

| τ 変更の場合: 変更前後の値と設定根拠 | 配信前 | 永久 |

| ステージング確認結果（R 値比較） | 配信前 | 永久 |

| 更新適用時の Gate 状態スナップショット | 配信中 | 永久 |

| 更新完了ログ（タイムスタンプ・バージョン・担当者） | 配信後即時 | 永久 |

| 配信後 24h の Discard Log | 配信後 | 5年 |

| 問題発生時の RCA レポート | 発生時 | 永久 |



### 5.2 承認フロー



```

τ 変更（クラス A）:

  提案者（制御設計者）

      ↓

  Gate 設計者レビュー（τ 設定根拠の確認）

      ↓

  ソフトウェアアーキテクト承認

      ↓

  配信



Gate ロジック変更（クラス B）:

  上記 + 機能安全担当者レビュー（ISO 26262 整合確認）

      ↓

  配信



制御層のみ（クラス C）:

  制御設計者 + Gate 設計者の接続点確認

      ↓

  配信



UI/ログのみ（クラス D）:

  通常のソフトウェアリリースフローに従う

```

## 6. ISO 26262 との関係における OTA 特記事項

## OTA-Specific Notes on ISO 26262 Relationship



`NRA-IDE_Automotive_Scope_0224_v02.md` Section 5.3 で示した通り、  

NRA-IDE は ISO 26262 の補完関係にある。OTA においては以下の点が追加で適用される。



```

ISO 26262 の変更管理プロセス（Part 8）:

  ソフトウェア変更には ASIL レベルの再評価が必要



NRA-IDE 追加要件:

  クラス A / B の更新は ISO 26262 変更管理と

  NRA-IDE Gate 検証の両方を通過すること



重複ではなく二重確認:

  ISO 26262 → 「設計として正しいか」

  NRA-IDE  → 「実行時の閾値が正しいか」

  どちらか一方では不十分

```

## 7. まとめ / Summary



```

OTA で失ってはならないもの:

  「R ≥ 1.0 のとき必ず止まる」という保証



失う原因:

  τ の無断変更

  Gate ロジックの静かな置き換え

  更新中の Gate 空白期間

  ロールバック時のバージョン不一致



防ぐ手段:

  更新クラスの分類（A/B/C/D）

  クラス A/B は走行中適用禁止

  ステージング確認の義務化

  すべての変更の責任記録



最終原則:

  Gate の更新は「ソフトウェア更新」ではない

  「安全保証の再発行」である

  それにふさわしい手順と記録が必要

```
