# 08 廃棄ログ — 計算へ戻さず、証言として残す

---

## ログは書き込み専用、ただし人間の監査は妨げない

06で確認した通り、NRA-IDEでは値の名称だけでなく、出所と更新経路を区別します。廃棄ログも同じです。

ここでいう**書き込み専用**とは、記録されたログを次回の構造判定へ自動的に戻さない、という意味です。ログを読めないという意味ではありません。人間の監査者は、停止や委譲が起きた理由を確認するために記録を参照できます。

禁止されるのは、次のような還流です。

```text
前回ログ → 結果からの推定 → δ・τ・Ropの自動更新 → 次回の構造判定
```

この経路では、前回の判定結果が次回のCause-Side入力を書き換えます。03で扱ったΠ⁻¹の経路です。

一方で、次の二つは区別します。

- **構造判定の実行系**：ログをδ・τ・Ropの更新根拠として再投入しない。
- **人間による監査・設計見直し**：ログを証言として読み、別途の検証・承認・版管理を通して設計変更を検討できる。

人間がログを確認することと、ログが自動的に次の構造計算を支配することは同じではありません。

## 廃棄するのは、次の遷移へ採用しない残差である

NRA-IDEの離散的な位相遷移では、次のような処理を置けます。

```python
raw_next_phase = prev_state.phase + prev_state.omega

next_phase_int = math.floor(raw_next_phase)

entropy_export = raw_next_phase - next_phase_int
```

`raw_next_phase`には、次の位相として採用する整数部分と、採用しない小数部分が含まれます。`next_phase_int`だけを次の離散遷移へ渡し、小数部分は`entropy_export`として記録します。

重要なのは、**すべての情報やすべての誤差を捨てるのではない**ことです。ここで扱うのは、事前に定めた離散化規則において、次の状態遷移へ持ち越さない残差だけです。

```text
次の遷移に採用する値：next_phase_int
次の遷移に採用しない残差：entropy_export
```

この処理は、採用しない残差が隠れた状態として次の位相へ再流入する経路を断ちます。残差を記録しても、計算入力に戻さない限り、記録そのものがΠ⁻¹にはなりません。

---

## `entropy_export`は熱力学的エントロピーの測定値ではない

`entropy_export`は、離散化で次の遷移へ採用しなかった残差を示す**実装上の記録項目**です。

これは、熱力学的エントロピーを直接測定した値や、物理的な熱量そのものを意味しません。したがって、本文書群で`S`を残存構造余裕の逆数として使う場合、`entropy_export`を同じ記号で表してはなりません。

```text
S = 1 / (τ · (1 − R)) = 1 / (τ − δ)
```

- **S**：残存構造余裕の逆数としての構造感度
- **entropy_export**：離散遷移で採用しなかった残差の記録項目

両者は役割も生成経路も異なります。

## 排出が保証することと、保証しないこと

残差を次の離散遷移へ持ち越さないことは、計算構造における明確な選択です。しかし、この処理だけで計算全体が無誤差になるわけではありません。

保証対象は、**この規則で採用しないと定めた残差を、次の状態遷移の入力へ再投入しないこと**です。

保証対象ではないものもあります。

- 計測器やCause-Side観測値が正しいこと
- 浮動小数点演算に関わるすべての誤差が消えること
- `math.floor`以外の実装箇所に数値上の問題がないこと
- 離散化規則そのものが対象ドメインに妥当であること
- 通常生成されたLLM出力が意味上正しいこと

したがって、廃棄は「精度を捨てる」ことでも、「誤差一般を消滅させる」ことでもありません。次の状態遷移に何を残し、何を残さないかを、事前に固定した規則として明示することです。

## 廃棄ログは、委譲と終端の根拠を残す

05・07で区別したとおり、通常出力を抑止する状態には二つがあります。

- **Ropへの到達**：相転移境界より前の、ドメイン固有の委譲点
- **R ≥ 1.0**：構造余裕が失われた相転移境界への到達または超過

ログは、どちらが起きたかを混同しないために必要です。事前に定めた記録形式には、少なくとも次の情報を残します。

```text
EVENT: HANDOFF_REQUIRED または FAIL_CLOSED
REASON: 発動した委譲条件または構造境界
OBSERVED: δ, τ, R, ω と必要な出所識別子
THRESHOLD: Rop（委譲時のみ）
DISCARD: entropy_export（該当する離散遷移がある場合のみ）
ACTION: 通常生成の抑止、人間への委譲、または最小FAIL-CLOSED処理
RULE_VERSION: 使用した観測・更新・委譲規則の版
```

たとえば、Ropでの委譲は次のように記録します。

```text
HANDOFF_REQUIRED
REASON: domain-specific handoff threshold reached
OBSERVED: δ, τ, R, ω
THRESHOLD: Rop
ACTION: generated response suppressed; human review required
```

R ≥ 1.0では、停止理由を説明するためにLLMへ新しい自由記述を生成しません。あらかじめ定めた最小限の標識、または保護されたログへの参照だけを返します。

```text
FAIL_CLOSED
REASON: structural boundary reached
ACTION: no further generated response; human handoff required
```

これにより、委譲点での通常生成抑止と、終端境界での最小FAIL-CLOSED処理を記録上でも区別できます。

## 記録は証言であり、次回の原因ではない

廃棄ログには、「何を出力したか」だけでなく、「何を構造計算へ採用せず、どの条件で通常生成を抑止したか」を残します。

記録が証言になるためには、少なくとも次の運用条件が必要です。

- 追記専用であること
- 記録後の改ざんを検出できること
- 観測・更新・委譲規則の版を対応付けられること
- 人間が監査できること
- 構造判定の実行系が、ログ内容を次回のδ・τ・Rop更新へ自動再投入しないこと

τを動的に変化させるCause-Sideの負荷履歴は、設計時に定めたτ更新規則の入力です。これは、前回の結果を記録した廃棄ログとは区別します。廃棄ログを、Cause-Side履歴の代用品として扱ってはなりません。

廃棄することと、記録することは矛盾しません。

```text
計算へは戻さない。
人間の監査には残す。
```

この二つを同時に成立させることが、廃棄ログの役割です。

## 次章への接続

廃棄ログは、構造判定の証言を残します。しかし、入力の出所、τの設定、ログの保護、三層構造の省略といった問題は、ログだけでは防げません。
